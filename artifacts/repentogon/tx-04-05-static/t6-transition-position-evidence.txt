T6 普通门切房 / StartRoomTransition 静态证据补充
====================================================

主审后补勘误（2026-10-24；下方原始推导保留）
-------------------------------------------
1. 第 3 节的 RVA 0x425F26/0x425F2E、0x426144/0x42614C 两批坐标写入来自 type=3、variant=238 的实体查询，不能据此描述为 PlayerManager 批量定位。另有 animation=11/20 的 PlayerManager 坐标写入，以及 animation=3 对选定 Player 调 0x3C3C40 的条件链。
2. 第 5 节的 API 参数链 UNKNOWN 已由主审后续证据补齐：Lua 注册 0x47AD08/0x47AD0E → bridge 0x49EEB0 → native 0x2F9710 → setter 0x423990；animation 为第三栈实参，在 0x423B05 写 RoomTransition+0x1C。所有路径最终 Player 定位时序仍 UNKNOWN。
3. 最新结论见 T6-supplement.md 与 docs/research/tx-04-05-static-confirmation.md；原始指令复核见 primary-ida-evidence.txt，不用本文件的旧未决状态覆盖后续证据。

范围与方法
----------
目标 IDB：v1.9.7.12 脱壳副本，镜像基址 0x00400000。下列地址同时给出 RVA 与 VA（VA=RVA+0x400000）。通过 ida-mcp 只读反编译、指令列表、xref 与函数范围内字段操作数搜索取得；未改写 IDB。

本补件仅核对普通 transition 相关函数及其直接前后调用，不声称穷尽所有间接副作用。已有 callback / pre-callback 证据见同目录 `t6_callback_order-ida-export.txt`、`primary-ida-evidence.txt` 和 `t6_post_load_player_followup.txt`；关键内容在下方索引复述。

1. 普通 Level::ChangeRoom 的 callback 前定位
-------------------------------------------
已有导出 `primary-ida-evidence.txt` 的指令窗口证明：

- RVA 0x003395B6（VA 0x007395B6）在 Room loader 中调用 RVA 0x00592A80（VA 0x00992A80）遍历 PlayerManager。
- PlayerManager helper 在 RVA 0x00592C8D 调 RVA 0x0039EA20（VA 0x0079EA20）。
- RVA 0x0039ED54/0x0039ED5A 与 0x0039ED5E/0x0039ED66 把两个 float 写到 Player 基址 +0x33C/+0x340；0x0039ED73 起另写 +0x360 等运动状态字段。
- 同一个 helper 在 RVA 0x00592EEB/0x00592EF3 对 Player +0x33C/+0x340 写相对位移，输入来自 `dword_C01358` 的二维表及距离/碰撞计算。该写属于同一遍历内的相对调整。
- Room loader 在 RVA 0x00339719 调 `sub_84B930`，其 callback id 为 19（MC_POST_NEW_ROOM）；相邻房间实体循环位于 RVA 0x003396B1..0x00339717。因此上述显式 Player 定位调用先于 callback。

正常 Level::ChangeRoom caller 的 callback 后顺序（已有导出中的原始窗口）：

```text
RVA 0x0033A739  call sub_7385F0     ; 大 Room loader；其中触发 MC_POST_NEW_ROOM
RVA 0x0033A744  lea  ecx,[ecx+1BAA8h]
RVA 0x0033A74A  call sub_993030     ; PlayerManager 列表后续处理
RVA 0x0033A74F  cmp  dword ptr [ebx+18304h],0
```

`sub_993030` 对 PlayerManager 中各 Player 调 `sub_79FD90`；既有静态扫描未发现其直接引用 +0x33C/+0x340。该结果只排除函数自身可见的直接字段写，不能排除其子调用或其它运行态路径的间接写入。

2. DoorNestedOwner 的 callback 后 Room update
---------------------------------------------
RoomTransition::ChangeRoom RVA 0x00425700 调 Game owner `sub_6FA0F0`。`sub_6FA0F0` 的 callback 后调用次序如下（VA / RVA）：

```text
VA 0x006FA171 / RVA 0x002FA171  call sub_739DE0 ; Level::ChangeRoom，含新房间 callback
VA 0x006FA176 / RVA 0x002FA176  mov  ecx,[esi+18300h] ; Game 当前 Room
VA 0x006FA17C / RVA 0x002FA17C  call sub_7F7F60 ; Room update
VA 0x006FA181 / RVA 0x002FA181  call sub_6EB4B0
VA 0x006FA19D / RVA 0x002FA19D  call sub_7E2350
```

`sub_7F7F60`（Room update）函数范围内确有 +0x33C/+0x340 的写指令：

```text
VA 0x007FB44E / RVA 0x003FB44E  mov   edi,[ebp-9A8h]
VA 0x007FB454 / RVA 0x003FB454  movss [edi+33Ch],xmm1
VA 0x007FB45C / RVA 0x003FB45C  movss [edi+340h],xmm3

VA 0x007FBCAC / RVA 0x003FBCAC  call  sub_7F7D30
VA 0x007FBCB1 / RVA 0x003FBCB1  mov   ecx,[eax]
VA 0x007FBCB3 / RVA 0x003FBCB3  mov   [esi+33Ch],ecx
VA 0x007FBCB9 / RVA 0x003FBCB9  mov   eax,[eax+4]
VA 0x007FBCC2 / RVA 0x003FBCC2  mov   [esi+340h],eax
```

此函数也遍历 Room 容器 `[Room+0x125C, Room+0x1264)`，并在多个位置读取实体 +0x33C/+0x340。上述写入目标的寄存器/局部变量未由当前静态证据归类为 Player；不能把它们认作 Player 最终坐标，也不能用它们证明 Player 没有 callback 后改位。故普通 DoorNestedOwner 路径的 callback 后 Room-update 是一个需保留的间接写点，目标身份 UNKNOWN。

3. RoomTransition::ChangeRoom 的普通 +0x1C==0 分支
--------------------------------------------------
IDA 反编译把过渡对象 `this+0x1C` 读入 `n11`。它与官方 `RoomTransition.zhl` 的 `_mode`（对象 +0x0）是不同字段；本补件只按 `this+0x1C` 数值描述，不将其称为 `_mode`。

```text
VA 0x008256D5 / RVA 0x004256D5  cmp dword ptr [edi+1Ch],0Ch
VA 0x008256E1 / RVA 0x004256E1  call sub_701AA0           ; +1C==12 特殊分支
VA 0x00825700 / RVA 0x00425700  call sub_6FA0F0           ; 其它值进入 DoorNestedOwner
VA 0x0082592F / RVA 0x0042592F  mov ecx,[edi+1Ch]          ; n11 = transition+0x1C
VA 0x00825932 / RVA 0x00425932  cmp ecx,3
VA 0x0082593B / RVA 0x0042593B  cmp ecx,0Ch
VA 0x00825944 / RVA 0x00425944  cmp ecx,0Dh
VA 0x0082594D / RVA 0x0042594D  cmp ecx,0Bh
```

该函数在 callback/owner 返回后，对 +0x1C==11 有显式坐标写（RVA 0x425B75/0x425B7F）；+0x1C==20 的维度2分支写 Player +0x33C/+0x340（RVA 0x425E8A/0x425E92），其另一路批量位置写在 RVA 0x425F26/0x425F2E；+0x1C==3 会进入临时坐标/实体 helper `sub_7C3C40`（RVA 0x42601A），随后对列表对象写 +0x33C/+0x340（RVA 0x426144/0x42614C）。这些路径均不能泛化为普通 +0x1C==0。

当 `this+0x1C==0` 时，以上 `==11`、`==20`、`==3` 特殊定位分支不成立，控制流到 LABEL_154；该汇合点的直接指令为：

```text
VA 0x00826168 / RVA 0x00426168  mov ecx,[Game+18300h] ; 当前 Room
VA 0x00826174 / RVA 0x00426174  call sub_803E20
...
VA 0x008261D6 / RVA 0x004261D6  mov ecx,[Game+18300h]
VA 0x008261DC / RVA 0x004261DC  call sub_804500
```

函数范围字段搜索结果：`sub_803E20`（VA 0x803E20..0x8044F3）没有 `+33Ch/+340h` 操作数；`sub_804500`（VA 0x804500..0x8080F0）仅命中两条读取：VA 0x806447 `movss xmm2,[eax+33Ch]`、VA 0x806457 `movss xmm3,[eax+340h]`，未命中这两个字段的直接写指令。函数名与调用参数显示这些是 Room/过渡表现路径；仍不据此排除更深层调用的副作用。

4. RoomTransition::Update 后续阶段
----------------------------------
官方 `RoomTransition.zhl` anchor 对应 ChangeRoom RVA 0x4254B0；`Update` 为 RVA 0x426430。IDA 的 `sub_8254B0` 代码 xref 仅有同一 Update 内三处：RVA 0x426AA6、0x426AC6、0x426BE9，属于不同过渡状态/分支。

`Update` 函数范围（VA 0x826430..0x82732A）对 +0x33C/+0x340 的直接字段搜索为 0 命中；RVA 0x4268E3/0x4268EB 可见对 +0x364/+0x360 的 float 写，属于速度/运动状态而非前述位置字段。其余间接 callees 的完整对象副作用没有被本轮全图穷举。

5. StartRoomTransition 的证据边界
--------------------------------
官方 SDK 暴露并使用 `Game():StartRoomTransition(...)`，测试 mod 可通过此 API 发起 transition；本轮 IDA 静态证据没有把该绑定的参数/状态写入逐字段连到 `RoomTransition::ChangeRoom` 的 `this+0x1C`。因此可复用上节对 ChangeRoom 各分支的判断，但“测试调用必然令 +0x1C==0”仍须由源码绑定/运行样本补证，不能仅凭 WALK/FADE 参数命名推断。

本补件不把 RoomUpdate 中未归属 Player 的字段写认作最终 Player 定位，也不把“ChangeRoom 普通分支没有直接坐标 store”扩成“整条调用链 callback 后绝无 Player 坐标变化”。
