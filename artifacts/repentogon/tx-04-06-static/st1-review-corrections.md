# ST1 主审与更正记录

日期：2026-10-25。主智能体在子智能体分析期间另行使用 IDA MCP 只读导出表、指令、调用方，并读取本地官方 REPENTOGON 1.1.3 源码。以下保留错误与修订经过，不将静态分析说成运行时观察。

| 项目 | 原记录 / 分析问题 | 主审处理 |
| --- | --- | --- |
| imagebase | 子智能体首次把 `min_ea=0x401000` 当 imagebase，读错了表位置，随后以 `imagebase=0x400000` 重导覆盖原文件 | 旧错误 JSON 已被覆盖，无法提供原文件；如实保留此事实。当前 raw JSON 同时记录 imagebase 与 min_ea，主审另行读取的三张表独立提供正确地址 |
| 槽 3 类型 | 原方案写为返回不会被当物理设备处理的“值”，未明确字符串合同 | 两种派生实现与 `0x5EDC10` 证明 EAX 返回名称指针；修订为常驻自有名称，禁止以整数码或空指针代替有效名称；名称本身不证明所有类型分支 |
| NEVER | 原迁移候选只覆写槽 0，槽 2 仍继承资源释放实现 | 主审读取 `0x5EC7B0` 与主动移除、Poll 失败、整体关闭的指令，确认先槽 2 后槽 0；新增槽 2 的保留资源覆写 |
| KeyConfig 槽 11 | 子智能体曾漏看等待按键分支，认为 `0x4B9AD0` 没有设备槽 11，怀疑主审混用了 InputManager 的槽编号 | 主审指明 `0x4B9D1A: call [edx+0x2C]`，后继比较 -1；子智能体确认遗漏。导航槽 9、等待 raw 槽 11、reset 槽 30、映射 setter 槽 33 分别记录 |
| UI 导出候选 | `ida-st1-ui-functions.json` 的请求 key `0x4B95C0` 实际落在函数起点 `0x4B8C70` | 保留该候选，不将其归为 `0x4B9AD0` 的更新函数；正确更新函数在主审原始导出中完整保存，子智能体另补正确分支证据 |
| 全映像 `+0x0C` 扫描 | 候选列表包含很多其他类型、锁对象的间接调用；另一份有界扫描为空 | 仅将已确认对象来源的调用归为设备槽 3。候选数、空结果均不证明全映像闭包 |
| 主审草稿调用点 | 草稿一度使用近邻地址描述 Join 槽 17、MenuManager 槽 27、公共更新第二次槽 18 与主动删除槽 2 | 回到原始指令后分别修正为 `0x591794`、`0x56207D`、`0x5ECA00` 与 `0x5EEC24`；最终报告引用这些精确地址 |
| Hex-Rays 类型 | 公共更新出现 bad-SP / 虚构 Poll 参数，槽 18 将全局默认值错误显示成调用方 `a4` | 保留原样输出；Poll 以虚调用前后的汇编确认无栈参数/AL 返回；槽 18 以两项栈参数、输出指针与 `retn 8` 描述 |
| 官方 Initialize Hook | tx-04-03 第 8 节概括“设备函数没有 Hook”，本次读官方 1.1.3 发现遗漏 | `MiscFixes.cpp:268` 与 `Input.zhl:33` 证明 Hook 可在原函数前读 `+0x3FC` 名称；补布局要求，不声称该选项实际开启 |
| 13 槽集合 | 直接观察不能证明原生要求这 13 个槽都由自有设备覆写 | 0/2/3/8/9/10/35 负责本设计的 NEVER、纯虚和业务输出；5/6/7/11/26/27 的固定中性是主审采纳的 DESIGN，防止 raw/缓存/菜单活动旁路，不标成原生事实 |
| UI 直接读尾部 | 菜单绘制函数 `0x4B8C70` 在选中设备分支直接读 `+0x48C/+0x498` | 主审补导同一函数并定位 `0x4B8D3D/0x4B8D46`；13 槽与名称预留不解决该直接读取，完整可达性/适配留 ST9 |
| 槽 0 清理方式 | 子报告初稿写“先调用 slot2”，容易误解为经 vtable 分派 | 主审确认 `0x5EC66C` 是直接调用 `0x5EC7B0`（与槽 2 目标相同）；因此 K 也不能透传原生槽 0，即使其自有槽 2 已覆写 |
| 中途工具中断 | 自动审批审查及子智能体曾因额度限制中断，第一次多文件同步仅方案文件落盘 | 用户要求继续后恢复原有子智能体并按实际文件状态补齐文档，不重复声称未执行的操作成功；没有发生游戏操作或测试 |

范围仍是 ST1。ST2–ST9、K 实现、运行时行为和 tx-04-06 整体 E2E 均未完成；没有以任何未知或候选扫描结果宣称通过。
