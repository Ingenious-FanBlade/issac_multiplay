# 项目规范、约定与要求

生效日期：2026-10-12。状态：现行规范，按用户要求修订。2026-10-24 tx-04-02 按用户决定修订第 4、7 节，新增第 14 节（REPENTOGON 适配）。2026-10-30 按用户要求修订第 2、5、8、15 节：tx 不再保留 artifact，E2E 默认不留 artifact，并连续修复、续测直至完成。2026-11-08 按用户决定新增第 17 节（原生二进制状态同步重构），并在第 2、15 节加注该重构的例外。2026-11-10 按用户决定将第三方 Mod 适配迁出二进制重构，当前先跑通原版内容，同步第 15、17 节。2026-11-12 第 17 节写入显示委托 Q1—Q8 及显示推进的调度；同日 RE-3—RE-5 审阅后追加 Q9（SpawnSeed）、Q10（Projectile 恢复作用域）和关闭插值时的相机节奏；RE-1 补遗与 RE-7—RE-9 审阅后追加 Q11（转场状态同步）、Q12（paused 位与终结分支枚举）及 Manager 尾部音频 tick（RE-10）。2026-11-16 第 17 节写入 Client 应用频率修复方案的六项用户决定，随后按用户指示实施方案顺序 0—4。

适用范围：`isaac_hook_reserach` 的项目推进、C/S 研究、逆向、实现、文档与测试。后续工作先读本文，再读具体任务资料。本文覆盖旧计划、主题索引、技能和历史记录中与本文冲突的流程要求；用户在会话中的明确指示优先。

## 1. 永不设定 gate，不校验哈希

- 永不新增、设定、维护或要求项目 gate、阶段门、证据门、准入门、预封门、promotion 门或解锁门，也不得换名恢复同一流程。
- 不以旧 `gate decision`、`formalDecision`、`promotionCount`、`*Unlocked`、矩阵完成率或 `BLOCKED_BY_EVIDENCE` 字段作为后续推进的前置条件。按当前任务目标、实际依赖与已有授权推进，直接说明完成情况和未决问题。
- 不校验任何哈希，包括目标 PE、构建、文件、artifact、source、manifest、候选、状态或 baseline 的哈希；不执行 SHA/hash 校验脚本，不要求 hash-bound 交接、哈希一致性、哈希链或重签。
- 旧哈希、gate 字段及历史判定可以保留在原始记录中，作为历史信息阅读，不再执行其校验或解锁流程。
- RVA、原始指令、特征字节、对象布局、ABI、线程、调用关系及实际状态仍用于理解和实现。它们不构成新的项目 gate。运行时输入合法性、边界保护和失败处理仍是功能行为。

## 2. 每次推进统一整体验收，E2E 连续修复与续测

- 推进的最小粒度为 `tx-0x-0x`，例如 `tx-00-01`。开始时说明该次推进的完整目标、范围及预期结果；历史 T0/工作包编号可继续作为内容索引。
- 例外（2026-11-08）：原生二进制状态同步重构（[`docs/design/binary-state/`](../design/binary-state/README.md)）的步骤直接用数字编号，从 0 开始，不使用 `tx-0x-0x`。整个重构是一个推进目标：0—14 步期间不运行任何测试，第 15 步是唯一的统一整体验收。本节其余规则照常适用，见第 17 节。
- 每一次推进只在整个目标完成后进入统一的整体测试验收。验收使用统一入口覆盖整个目标；“一次整体验收”指同一 tx 的完整验收过程，不限制其中因问题修复所需的继续执行或重跑。
- 进入整体验收前的探讨、分析、设计、逆向、实现和修改过程中不得进行其他测试。不得提前运行 smoke、probe、canary、harness、自测、mutation/负向批次、回归、verify-existing 或试跑验收。进入验收后的修复与必要续测按本节执行。
- 文档阅读、文件检索、静态反编译和代码阅读属于资料分析；为判定正确性或通过与否运行程序、实验、校验脚本，均计为测试，不得通过改名绕过本约定。带测试的构建脚本也计为测试。
- 不沿用旧“四组各一次”“每个子项分别验收”“先预封再验收”“多次 replay/comparison”流程，不把同一目标拆成多个编号来增加测试次数。
- E2E 如无特殊说明，应连续完成测试；遇到问题先定位并修复，再在同一 tx 的整体验收中继续必要测试，直至整个目标验收完成。不因失败默认结束工作、等待用户再次发出修复或测试指令，也不为修复续测另换 tx 编号。续测范围须覆盖修复影响及尚未完成的用例，不能只跳过失败项后宣称通过。
- 用户要求停止、需要尚未提供的必要配合或授权、或存在无法自行解决的阻塞时，可以中途停下，说明实际问题和继续条件。实机操作仍遵守第 8 节，不从连续测试要求推导额外授权。
- 每个 tx 任务本身不再保留 artifact，不再为推进单独归档日志、源码快照、报告包或执行材料。E2E 默认也不保留 artifact；仅在中途停下且需要记录信息以便后续继续时，保留必要的诊断、进度及恢复材料，并说明保存位置与用途。正常测试所需临时材料用后清理，不要求最终 artifact。
- 代码、设计、字段目录、schema 和功能本身要求的观测／录制能力仍按任务交付；不因默认不留 artifact 而删去产品功能或省略结果说明。最终说明实际覆盖、失败与修复、完成情况和未决问题。
- 文档任务的一次验收采用静态文档审阅，检查规则一致性、引用与修订范围；不运行游戏、构建或代码测试。

## 3. 取消逆向与测试必须独立的要求

- 逆向、实现和测试可以由同一智能体或主智能体完成，不要求不同子智能体、作者分离、独立 TEST/REVERSE、候选前预封或独立最终审计。
- 不强制创建子智能体。用户要求分工时再按明确任务分配；结果是否可信取决于实际观察、推理和唯一一次整体验收，而非作者身份。
- 操作同一游戏或调试器会话时仍须避免并发控制冲突；交接时说明进程、附着、断点和补丁状态。

## 4. 架构与产品隔离

- 首版采用真实 `isaac-ng.exe` 作为唯一权威模拟器的 Listen Server；房主与远端输入进入同一 scheduler，Authority 日常 tick 不等待全员输入。
- C/S 与原版 Online Lockstep、Isaac Sync 1.0.4 使用独立 session、协议、IPC、日志和可变状态。
- 2026-10-24 tx-04-02 起，不再延续 `ISCS` protocol 5、ABI 5、七项 `Isaac.Sync` Lua API、原版 channel `0` 和 Isaac Sync channel `0xFD` 的兼容约束。C/S 使用独立协议，不进入、不触及原版 Online 与 Isaac Sync。原约束的历史记录保留。
- C/S 不依赖或复用 Online Manager、`NetInputDevice`、`FrameStore` 或原有 all-slot ready 条件。旧同步机制名称中的 gate 只描述旧功能，不是项目推进规范。
- 当前 T0 范围是研究原型；可玩 Replica World、snapshot/baseline/delta apply、预测、rollback、late join 和 Dedicated Server 按后续实际任务处理，不从现有原型外推为已完成。

## 5. 事实、假设与记录

- 区分直接观察、静态推导、运行时观察、设计决定、用户接受的假设和 `UNKNOWN`；标签保留其真实含义，不因取消流程门而伪造功能已完成。
- 单次成功样本不外推为跨版本契约；静态伪代码不充当运行时观察。
- 结论附可读的文件/函数位置、RVA/字节、场景、实际行为与未决问题，不要求哈希或认证产物。
- 已有历史失败、反例和原始记录保持原事实，不因新结果改写。后续不再据此要求每个 tx 或 E2E 留存 artifact，留存范围按第 2 节执行；新结果说明对应的推进编号、失败与修复，不能以最终通过抹去实际失败。
- 历史报告中的“当前”“下一步”“必须独立”“正式入口”“未解锁”只代表原记录当时的语境，不恢复已取消的流程。

## 6. 输入、身份与生命周期

2026-10-30用户要求恢复**最多四名参与者**，在状态同步前以tx-04-09完成四人及一人多EntityPlayer支持，再以tx-04-10—tx-04-14补全各域观测。[连续计划](../design/observation-expansion/README.md)制定时仅编写文档；用户随后启动09，现已通过四参与者／八身体及指定形态的功能整体验收，结果和限制见[实现说明](../design/observation-expansion/four-participant-implementation.md)。下列T0-05固定A/B是原验收的历史命名，统一输入与生命周期规则适用于全体参与者；不得将参与者数等同Entity_Player数。

- T0-05 固定 A 为 ordinal 0、B 为 ordinal 1；`ClientId -> ordinal` 在 session 内冻结。
- `Player*`、device pointer、assignment key 和平台 handle 仅用于当前 generation 的临时关联，不进入 canonical 输入或网络身份。
- A/B 共用 canonical、sequence、target tick、queue、dedupe、resolve 和 apply；房主没有即时旁路，B 不直接写 Player/device/cache/world。
- 重复输入幂等，边沿动作 exactly-once；非法、过期或冲突输入不得改变世界。缺输入时按连续量时限和中性策略处理，不重复旧边沿。
- room、death/respawn、设备重分配使临时绑定失效；唯一重绑前不 apply。menu/run teardown 退休 session 与 generation，旧输入和旧对象关联不复活。
- pause、loading、menu 或未知绑定下保持中性，不把渲染帧、顶层 loop 或墙钟直接当作 Authority tick。

## 7. 线程、Hook 与失败处理

- 游戏对象和 Lua 的操作发生在已理解的主线程边界；网络线程只做有界接收、解析和入队。
- Hook 使用单一协调 owner：所有 Hook 只经统一的 Hook 清单注册。Hook 在启动时安装后常驻到进程结束，会话只做逻辑启停，未激活时原样透传，不做字节恢复（2026-10-24 tx-04-02）。观测 wrapper 保持 original exactly-once。
- 未知 ABI、对象关系、错误线程、事件丢失、绑定冲突或恢复不确定时停止相关修改，记录实际原因；不得猜测后继续写世界、强制卸载或盲目重注入。
- 正常停止时：关闭输入/publication，处理在途 callback，退休对象，然后回到透传；不恢复目标字节。自有 virtual device 的内存和模块按第 9 节的常驻策略处理。
- 2026-10-30用户明确要求：生产默认不启用世界录制、逐tick/query明细、查询一致性诊断和逐consumer重复全图读取；E2E显式启用。必要的生命周期／线程／设备归属检查保留，稳定窗口复用已核定拓扑，变化时立即撤销或重读。后续正式同步所需的纯值状态快照与调试录制分离，不能让输入／同步依赖录制或日志成功；Rust不得跨线程／跨进程直接持有原生Player对象。测试夹具和Rust harness不作为正式游戏模组发布内容。
- 不造成未经任务允许的 save、achievement、unlock、统计或其他持久副作用。最终 dirty=0 或文件未变不能代替对整个操作窗口的理解。

## 8. 操作授权与测试安排

- 2026-10-24 用户要求：每次实机测试开始前，先明确告知用户需要配合的操作和停止手动操作的时机；涉及多次游戏启动时分别提示；需要手动配合时先确认用户已经准备好，再启动。tx-04-04 当前需要用户跳过每次启动的开场动画，到标题页或选档页后停止操作，由 harness 接手。

- 阅读、静态分析与任务范围内的可逆编辑按用户请求推进。已有会话授权继续有效，不因旧 gate/哈希/独立角色要求重复询问。
- 游戏输入、注入、运行时修改与其他实机操作按用户实际授权范围执行；不从历史 PASS、工具可用或设计假设推导新的操作授权。
- 不沿用旧文档强制的逐场景授权编排；需要补充授权时只针对尚未授权的具体操作说明原因。
- 实机验收如依赖现有工具，提前阅读其使用方式；已存在的工具限制如实说明，不把它们升级为新的项目 gate，也不在本次文档修订中修改工具实现。
- 所有测试安排服从第 2 节：进入整体验收前零测试，E2E 默认连续完成，遇到问题修复后在同一 tx 内续测；仅在必要中断时保留所需 artifact。

## 9. 已采纳的 Virtual Device 设计

- 采用自有对象 vtable 加自有 control block、S2 action 层覆写；路线 A（虚拟设备触发原生 Join）为主，直接重绑路线 B 为备选。
- tx-01-45（2026-10-16）用户采纳：Authority-pre 发布 current，StandardRoom original 正常返回后提交 previous；poll 不写快照。正常退休停在 UNREGISTERED 并保留 root strong，不主动进入释放 root 的旧 ZOMBIE 路径；缺输入立即中性（max_input_age_ticks=0）。
- tx-01-50 输入修复补充：原生奇数帧 955241→6FD3F0 也是实际 Player 模拟；在原生暂停/状态检查后首次正常 Main Player 更新前执行 Authority-pre，helper 正常返回后提交 previous。特殊暂停/FSM 更新不推进 scheduler；不把顶层 loop 直接当 tick。该修复与 StandardRoom 共用原有 scheduler，不改变 poll 的只采样职责。
- tx-01-51 用户采纳启动例外：A/B 重新唯一绑定后，首个新鲜输入可经相同 codec/Submit/queue 用于 completed+1；同一新鲜样本的连续量以新 sequence 按正常 lead=2 排入 completed+2，edge 清零，消除下一步空档。普通输入仍 lead=2；旧 generation/旧 edge 不恢复，无新鲜输入仍中性。物理 poll 只采样，不写 current/previous；启动使用同一 loop、同一 exact pair 的新鲜源，查询仍只读 Resolve。
- tx-01-52 用户确认射击相反方向后按者优先；源转换按每条轴保存胜出方向，释放胜出键后回退仍按住的方向，全部释放才归零。无法区分同次采样先后时保留仍按住的旧胜出方向；没有历史时固定右／下。A/B 原始方向源共用转换、各自保存历史，再经相同 canonical/queue/Resolve；不修改移动相消语义或 V1 接口。
- tx-01-45 的交付限定为有效分配、对象/缓冲和主线程正常顺序路径；完整 OOM、EH、worker 并发及计数镜像的并发闭包不在本次范围。可识别的异常中性停用，不能据此声称这些异常已安全恢复。
- tx-01-54 跨房射击修复：无 Authority tick 或 pause/loading/lifecycle 阻断时，C/S 主动分派暂停原生 Shooting consumer，避免把中性查询当作武器松键；停用时同样暂停。正常无阻断 tick 的真实松键与缺输入仍执行中性消费，不保持旧攻击。A/B 共用，不改武器蓄力字段；观测 wrapper 和其他原生更新保持原调用，主动暂停的 Shooting original 调用次数为零。本次一次专项18/18 PASS，覆盖普通门往返及暂停恢复，不外推所有武器或 loading/换层。
- 2026-10-26 用户在 tx-04-07 采纳重绑恢复例外：唯一绑定后，从首个有效 Authority tick 起最多六个 tick，尚无可消费的新代次命令时可暂停 Shooting original；Authority 与其他更新正常推进，canonical 查询仍中性，不等待全员、不复用旧 held、不读写蓄力字段。首条新代次命令用于 current（包括真实中性/松键）立即结束恢复窗口，本代次不再重新开启；六 tick 到期也恢复中性消费。consumer 缺席不延长窗口，A/B 同规则。此例外只覆盖首条新命令前的握手空档，其余正常缺输入与真实松键仍按前述规则消费；原 tx-01-54 验收记录不追溯改变。
- tx-01-56 异常 Join 分支实现：自有 B 为完整 Type=1/Variant=0 Player；在同一 Game/manager/A、主线程和唯一 exact pair 的两 pass Join 内，三处原生 Baby 判断仅对自有 K 选择普通角色路径。原 predicate 各调用一次，其他设备保留原值，不改全局 run flags；普通工厂仍为唯一创建 owner，不接纳未经 owner 的 Baby/possessor。新增三处 Hook 纳入统一51槽事务；本轮唯一E2E专项21/21 PASS，实际Baby=true路径、完整B、宿主健康与51槽恢复已覆盖，旧tx-01-51具体来源仍为静态推断。
- 回收策略为 `NEVER`：进入 `BASE_CONSTRUCTED` 后，对象、control block 及其有效基类状态在进程生命周期内不释放。只有未执行原生构造的 raw allocation 可以回滚释放。
- 首次调用原生 base ctor 前固定 DLL；恢复后 DLL 常驻。退休输出中性，设备从 InputManager vector 移除，B 解绑或退出；每个 session 至多一次创建，失败不自动重试。
- Base 38 槽表和 control block 6 槽表按已理解的 ABI 实现；control 槽不析构或释放，保留原生 Mutex/CS 状态并维护影子计数及镜像。
- 旧 native alias universe 批次为背景资料，Batch 2 retry 暂停。全映像别名闭包、factory/release-thread 旧流程不再作为项目推进门。
- key 并发、Init 分配失败、remove 与 worker 并发、注册/assignment 窗口、COL/RTTI 等未决问题直接列入实现说明与该次推进的整体验收，不另设 gate 或提前测试。
- [协调器契约 v2](cs-t0/t0-05/07-virtual-device/design-revision/virtual-device-owned-abi-coordinator-contract-v2.md)中的具体功能约定继续适用；流程冲突以本文为准。

## 17. 原生二进制状态同步重构

- **2026-11-19 用户决定 P7 中的 grid_paths 阻挡位补同步**。见[预测插值设计 5.3.1](../design/binary-state/prediction-interpolation.md#531-寻路-cost-阻挡位同步p72026-11-19用户决定)。起因是 RE-P2 发现无 GridEntity 的格子由 `Room+0x76C` 寻路 cost 决定碰撞类别（≥1000 阻挡），而该表原定留 Host。
  1. Host 在采集窗口内由 `grid_paths` 推出每格 2 位碰撞类别（无／PIT／SOLID），作为 Room 派生字段随 World 普通流按字段增量发送；原始 cost 仍留 Host，不发送。
  2. 客机只存入预测自有影子表（按场景作键，换房作废），供本机移动预测的地形查询使用，不写入原生 `Room+0x76C`。
  3. 与 Body 每身体输入序号同在阶段 2 实施，同一次整数版本加 1。碰撞范围其余部分及 P2—P6、P8、P9 仍未定；运行验证归第 15 步。

- **2026-11-19 用户决定 P1：客机可为本机身体执行本地纯移动计算**。见[本机预测、显示插值与外推设计](../design/binary-state/prediction-interpolation.md)第 5、10 节。起因是同机联机时客机输入不跟手（按键到显示推算约 100—150ms）。本条与下列旧条款冲突时以本条为准：
  1. 客机可以为本机操控的身体执行“输入 → 速度 → 位置＋碰撞”的纯移动计算，用于本机预测与对账。计算结果只作显示：不回传 Host，不写入权威字段，不触发玩法回调、伤害、生成、拾取、随机消耗或持久副作用。
  2. 这修订本节 2026-11-17 E1—E11 条及[显示委托 2.4](../design/binary-state/client-display-delegation.md#24-不变的约束)中“客机不运行玩法 Update”的约束，仅限上述纯移动计算；原生 `Player::Update`、半帧更新及其他玩法入口仍拦截。射击、泪弹生成、拾取、受伤、击退、道具、开门、换房仍只由 Host 裁决。
  3. 这修订第 16 节和[状态同步总设计](../design/state-synchronization.md)中“gameplay 预测属可选扩展、不以客户端提前执行掩盖延迟”的表述：本机身体移动预测纳入当前范围；gameplay 回滚、Host 侧延迟补偿、host migration 与 Dedicated Server 仍不承诺。
  - 不变的约束：Host 唯一权威；显示委托 Q1—Q14；方案 B 帧号；E1—E11；L1—L8；Hook 常驻与逻辑启停；线程约束；C/S 与原版／Isaac Sync 的隔离；带宽与内存总额；稳态 World 30Hz、Body 60Hz、单帧应用 p95≤2ms／p99≤4ms。设计其余 P2—P9 未定；运行验证归第 15 步。

- **2026-11-18 用户决定平铺记录方案的八项（L1—L8）**。见[设计文档](../design/binary-state/10-flat-record-encoding.md)第 7 节，尚未实施。起因是 300 泪弹 r8 中编码线程每份 ordinary 38.5ms（建索引 14.3、编码 24.2），占用约 88%，World 与 Body 都只有 22.8Hz。本条与下列旧条款冲突时以本条为准：
  1. **L1**：记录主区为紧凑镜像，只含需求字段所在的复制段，合并时只跨填充字节，镜像偏移由生成器分配。
  2. **L2**：字段校验由客机在后台对收到的字段及其写入组执行；Host 只在诊断模式下运行同一套生成校验。
  3. **L3**：首批迁移实体（含子类与变体臂）、Player、Grid；Game、Room、Level、Run 与显示域等全局根暂留现有单元路径，两条路径按布局表标记并存。
  4. **L4**：取代[最终一致修订](../design/binary-state/eventual-consistency-revision.md) 10.7 节的 W1／W2；B1、B2、M2 照做；M1 的资源槽改为以原生指针为键、带见证值的跨帧资源缓存。
  5. **L5**：整消息 zstd，首版不加异或差分。原定的块差分已由 L8 改为字段差分。
  6. **L6**：引用沿用两步翻译：主线程地址→身份（写本份引用目录序号），编码线程每帧以“身份→标号”散列表原位改写为成员标号；资源同样两步，改写为资源表内序号。
  7. **L7**：客机与 Host 同轮改造，客机直接按镜像写入，不做中间转码层；已迁移布局退出字段暂存、Describe、10.5 静止记录与 10.6 快速路径，这些部件只服务未迁移的全局根。
  8. **L8**：取消块，差分、上线与比较都以字段为单位（设计 3.2）。
     - 记录头改为 `member u16 | layout u16 | record_bytes u32 | set_mode u8` 加字段集合；字段集合在两级位图（16 字段一组）与序号差列表间按记录取短，`set_mode=2` 表示全部字段。**撤销 2026-11-11“保留 u32 块掩码和 12B 记录头”**。
     - Host 每帧对本帧与上一帧镜像做一次向量化逐字节比较（SSE2 为基础，运行时检测到 AVX2 时切换；AVX2 内核单独成文件），只遍历差异位图中置位的位、经字节→字段号表定位变化字段，以每字段版本戳为各 Peer、各流选字段；不再保留每个 Peer 的基线镜像。E1、E2 的基线语义不变。
     - 客机把收到的字段覆盖进完整镜像，按生成器推出的写入组写原生对象；写入组推不出的在布局源手工声明。
     - 容器、长字符串、owner／Weapon 槽首版各算一个字段，整段比较和上线；按元素差分视第 15 步带宽再议。
     - 布局源退役 `blocks[]`、块号、32 块上限、预留空块和 Sprite `#k` 投影，字段自带 world／body 流属性。

    - 原生在阈值处对 Client 本地字段做的清理，由安装点按同步值的变化补做，例如震屏倒计时归零时清掉本地相机写入的偏移。
    - 相机、ANM2 动画、FXLayers，以及 HUD／Minimap 自身的动画仍在 Client 本地推进。
  - **SpawnSeed 与 Projectile 恢复（2026-11-12 追加，Q9／Q10）**：
    - 当前房间描述的 SpawnSeed 同步 Host 当前值，按变化更新；原生 Render 在房间年龄 30 时读它，为 0 即崩溃。其他 seed 和全局 RNG 游标仍留 Host，写入 SpawnSeed 不授权 Client 运行任何生成路径。
    - `client_entity_draw_projectile` 保留，作为 Projectile PositionOffset 的保存／恢复作用域，不再提供绘制输入。
  - **转场、暂停与 Manager 尾部（2026-11-12 追加，Q11／Q12／RE-10）**：
    - **Q11**：RoomTransition 的显示字段（mode、counter、duration、progress、direction、roomIndex、dimension、animation、Boss 标记）同步 Host 当前值，随 world 原子安装。Client 不运行 Start／Update，也不写自有 FSM 驱动；本地只做旧／新 surface 捕获（旧的在安装新房间 world 前、新的在安装后）、滚动补偿、versus／肖像动画和原生 Render。转场内声音全部作为 Host 事件。
    - **Q12**：`client_entity_draw_paused` 保留，向 `Game::IsPaused` 的原生调用者返回 Host 同步的 paused 位。Host 每个 world 帧还发送按原生优先级算出的终结分支枚举，Client 据此选显示批次序列，不在本机重算分支谓词。Pα 由已安装的 primary alpha 判定。本地菜单阻断的合并由第 13 步决定。
    - **RE-10（同日静态完成）**：[调用分类与音频交接](../design/binary-state/client-display-delegation/RE-10/README.md)已列全 50 个业务 call site，另有 3 个栈保护点。音乐 `0x7D7DA0` 在有效 Manager 尾部周期更新，不受相机 paused 条件限制；`0x908340` 已核为 SDK `SoundEffects::ClearVolumeModifier`，是条件性混音刷新，撤销通用 SFX tick 猜测。显示推进根承接音乐与本地混音维护；Host 当前 SFX 乘数与本地 dirty 刷新分开，不搬运原生恢复生产段。输入复用现有 ClientPollInput、光标属本地，其余混合调用继续拦截；实际采集／布局／接线仍待后续步骤。SFX 回放传 FrameDelay=0 之外，还须处理同 id 本地声音已留下的节流截止，不能把 0 当作绕过既有截止的开关。
    - 同次审阅还定为：HUD 可见性 `Game+0x22E90` 按 Q8 同步；诅咒同步 raw 字段，不注入有效值；SFX 回放时 FrameDelay 传 0。
    - **Q13（同日追加）**：地图拾取图标沿用 Host 摘要；Client 包装地图缓存构建 `0x9635B0`，在作用域内把 descriptor 的 SavedEntities／保存 Grid 指针临时指向按摘要合成的最小条目，调用后恢复。不常驻镜像，不在构建后修补纹理。
    - **Q14（同日追加）**：第 4 步布局收缩用需求清单 `demand.json` 直接列出同步量（整类型照旧或只留字段），生成器剥离未列入的 wire，域文件只为新增字段改动；Room 显示子结构默认照旧、差异驱动删减；版本 72 只补 D1—D8，事件队列、表现状态与注入值随第 8／9／13 步分批。
  - **切房与回调（2026-11-12 追加，Q5／Q6）**：
    - **切房走原生过渡**：Client 用 Host 已决定的参数回放原生转场，不重新选路。换房点改由 Client 构建 Host 的新房间目标；目标未就绪时，转场停在换房点。这取代下面“资源与显示”条中的“直接切换”。（2026-11-12 Q11 修订：“回放”改为同步转场字段的当前值，Client 不调用启动入口；“停在换房点”由 world 原子安装天然得到，见上条。）
    - **回调分派放行**：Client 放行路径上的 Lua 回调分派一律放行，不再按 tx-04-17 的结论逐个隔离。前提是当前范围不含第三方 Mod，本项目自己的 Lua 不在 Client 注册玩法回调；第三方 Mod 按 Mod 适配方案处理。
    - “资源与显示”条中“纯显示生成不放行玩法Update／随机／Lua”的限制，按此理解为不放行玩法路径。
  - **验收**：不另开编号，第 15 步仍是唯一的统一整体验收。验收要求双方看到同一个权威结果，不要求像素相同。

- **当前范围（2026-11-10）**：先跑通原版内容的采集、二进制传输、Client 应用与整体验收。第三方 Mod 的自定义状态、角色／资源／绘制、StageAPI 等具名适配移至[Mod 适配后续方案](../design/mod-adaptation.md)，不作为本轮实现或完成条件。这里的“原版”指游戏内容；官方 REPENTOGON 加载器、目标 J273、必要的官方扩展 owner 与隔离约束继续沿用。本项目自带界面与 E2E 夹具仍按原职责管理，不借此纳入第三方 Mod 兼容。
- **资源与显示（2026-11-11）**：尽量不传输原始图像、音频或音视频内容；默认发送本地资源引用、文字、有限显示描述、状态和播放控制，由Client本地生成／播放。横幅／fortune传实际文字与必要样式，本地生成缓存；当前Client切房在合法完整目标就绪后直接切换，不要求前后surface平滑动画；hallucination采用本端历史画面与同步效果参数的本地生成路线，不要求Host反馈像素相同。不得以blob／压缩媒体兜底掩盖来源缺口；确有特殊需求按具体用途分析，不推导为原始媒体普遍必发。纯显示生成不放行玩法Update／随机／Lua或持久副作用；其余必要内容、提交／ACK、隔离及带宽指标保持。现行合同及后续实施边界见[资源本地生成与当前显示范围](../design/binary-state/local-media-presentation.md)，本次仅设计修订，既有布局／代码事实和UNKNOWN保留。2026-11-12 起，“本地生成”改由原生显示委托实现：Client 的原生 Render 和显示更新自己生成显示内容，文字和音频改走事件队列，资源协议收窄为资源引用；“不传原始媒体”的原则不变。同日起切房改走原生过渡，见上方“显示委托与按需采集”条。
- **采集方式**：Host 在 C++ 侧按生成的复制计划直接读取游戏对象内存。正式同步路径不调用 Lua getter，也不构建 JSON 树。2026-11-12 起，字段按需选择：布局源配一份需求清单 `demand.json`（Q14 取代原“每个字段标需求属性”），只为清单列出的字段生成复制计划（Q2）。原条款“不采用‘白名单字段＋兼容补丁’的适配方式”到此为止；按需选择仍由布局源和生成器管理，不改回手写 Lua 白名单。
- **HUD本地化（2026-11-12）**：低血周期闪烁、Holy Mantle显示资格、普通主动／饰品图标、材料与法术队列绘制、Drop渐变、基础属性格式化及多人HUD排版改由Client纯显示生成，优先复用已提交状态、本地资源与显示时钟。完整生命栏、三色触发闪烁、特殊图像／选择结果、有序库存／History、属性变化相位和概率结果不随之取消同步；基础属性格式化不要求恢复Player玩法属性或本地重算属性。公共绘制状态此前八项保留同步。具体输入、Drop驱动、派生依赖与第8—15步迁移见[HUD本地生成合同](../design/binary-state/hud-local-presentation.md)。初稿仅文档；随后布局70与纯值模块已按用户要求实施，当前范围与未接通的正常采集／发布／原生显示见[实施说明](../design/binary-state/hud-local-implementation.md)。2026-11-12 起，HUD 改由 Client 原生 `HUD::Update`／`PlayerHUD::Update` 和 `Game::Render` 产生，所需输入从已同步的 Player／Run 状态读取。版本70纯值模块中原生 HUD 能产生的部分进入退役评估，只保留原生做不到的项。产品纯编译不表示本地化实机实现或验收通过，第15步仍唯一统一整体验收。
- **状态形态**：每个类型按固定的二进制布局连续排布：类型标识，然后是父类字段，再后是子类字段。原生内存中相邻的已知状态字段合并成一次复制。Host 先复制到自有缓冲区，再用 memcmp 判断变化；Client 按同一布局解码、校验并写入。
- **完整性**：2026-11-12 起按需求清单判定（Q1）。每个类型列出 Client 需要的字段及其消费方证据：读取它的原生显示函数、返回它的 getter，或需要它的结构 owner。字节归属账本保留，作为定位和语义参照，不再是完成条件；UNKNOWN 默认不采集、不阻塞，第 15 步发现差异时再补查。原规则为：按字节归属判定，每个类型从 0 到对象大小的每个字节都有归属类别和证据，未知字节必须列出，不能宣称完整。当前范围不包含 Mod 域，也不保留正式 Lua 采集例外；迁出的 Mod 适配另按其声明的 schema 设计。
- **Baseline**：Baseline 与增量使用同一种二进制格式，Baseline 就是已确认版本为 0 的状态帧。布局兼容只比较整数布局版本，不计算哈希。
- **带宽（2026-11-11用户修订）**：总上行目标仍为10Mbps，允许模组占90%，持续总额9Mbps＝1,125,000B/s，三远端各375,000B/s。实际封装、ACK、重传、准备／恢复均计费；首次准备每Peer仍≤1MiB／≤10秒，不因放宽带宽而放宽必要内容或提前ACK。旧7.5Mbps记录保留原时点，当前精确容量／时间合同见[第9步预算](../design/binary-state/9-budget-capacity.md)。
- **布局表格**：每个产生状态的类型都要画原生字节归属表和状态二进制布局表，都是单行表格，每一格写明类型和语义；线格式结构同样要画。2026-11-12 起，状态布局表只画进入同步的字段；字节归属表保留，作为参照。
- **步骤与验收**：步骤编号与验收方式见第 2 节的例外：数字编号，第 15 步是唯一的统一整体验收。
- **其余规范不变**：第 1、2、5、7、8 节，以及 C/S 与原版 Online、Isaac Sync 的隔离，全部继续适用。
- **历史文档**：tx-04-21 及更早文档的事实与失败记录保留；其中与本节冲突的采集和同步设计，以 `docs/design/binary-state/` 为准。
