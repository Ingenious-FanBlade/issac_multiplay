# 同步

本文说明 Host 采集到的状态怎样变成网络消息、怎样做增量和确认，以及客机怎样判定可以使用。采集本身见[采样](capture.md)；客机拿到批次以后怎样写入原生对象，见 [Client 端设计](client.md)。

## 1. 合同

同步遵循“最终一致、最新值覆盖”：

| 编号 | 原则 |
| --- | --- |
| C1 | 客机应用能解码的最新 World，中间帧可以跳过。出错的对象由后续帧纠正 |
| C2 | ACK 表示“已收到”：完整解码并保留为差分基线时就 ACK，与原生应用是否成功无关 |
| C3 | 客机在主线程 Manager 边界一次调用内把整帧写进活对象，Render 看不到写了一半的状态 |
| C4 | 后台完成解码和全部纯值校验；主线程只核对目标对象仍存活，敏感字段走具名原生写入器 |
| C5 | 按对象隔离失败：单个对象失败只跳过它及依赖它的对象，达到阈值才请求完整基线 |
| C6 | 结构在同一次应用里协调：删除、回收、Morph 或重建、写字段、清理 Init 附属实体、挂引用 |
| C7 | 成员身份随帧携带；资源表走可靠通道，缺资源只延后用到它的对象 |
| C8 | 在途窗口按帧数加字节数控制，客机保留同深度的已确认快照环 |
| C9 | Host 采集按根隔离失败，单个根读坏只标记“沿用” |

## 2. 两条状态流

| 流 | 内容 | 频率 | 采集窗口 |
| --- | --- | --- | --- |
| World | 整个世界：实体、格子、房间、楼层、整局、显示值和事件 | 约 30Hz | 普通帧在原生 `Game::Update` 返回后采集。普通房间及楼层转场跳过玩法 tick 时，在 Manager 返回后采集显示状态 |
| Body | 逐个玩家身体的快变字段（位置、速度、动画等） | 约 60Hz | 该身体的 PlayerPost 窗口 |

两条流各自维护版本序列和确认进度，互不阻塞。一个字段属于哪条流，由布局源中该字节段的 `sequence` 决定。

死亡中的玩家仍可由普通 World 采集。Host 依据当前名册、先前的 Player 更新证言以及一致的实例、形态和 InitSeed，继续发送动画所需的值。输入和 Body 快流仍按各自的绑定规则处理。

### 楼层过场

楼层淡入淡出使用 World 中的 GameRun 字段。进入原生 Nightmare 后，Host 通过当前路由单独发送画面，客机用本地 ANM2 资源绘制并在新楼层就绪后接回 World。每帧至多 64 个图层，整包正文和信封合计至多 8 KiB，更新的帧可替换丢片的旧帧。

| ICSR 类型与序号 | 空值 | 过场帧 | 帧内资源项 | 帧内绘制项 |
| --- | --- | --- | --- | --- |
| `Nightmare`（26），连接内递增序号 | 结束过场 | `f32` 宽、高及黑幕透明度，后接资源表和有序绘制表 | `string` ANM2 路径、动画名及可选替换贴图路径 | 资源索引、图层 ID、原生图层帧、翻转位，后接 `f32` 变换、裁切和颜色 |

## 3. Host 侧

### 3.1 来源快照

采集后台线程（`BinaryEntities::Background`）从 `CaptureExchange` 取出采集包，交给 `HostStateCapture`（`mod/src/state/host_publish.cpp`）：

1. **成员索引**：把采集包里的成员身份映射为 u16 成员号。成员号由在途或已收到的快照保留，不会过早复用。
2. **比较**：平铺记录（实体、Player、Grid）按字段与上一份镜像比较，每个字段记录“最后变化版本”；块记录（全局根、控制组）按布局拆成块逐块 memcmp。Mod 记录由 `state/mod_codec.cpp` 用同帧成员目录填写引用、排序 map，整条比较后记录其最后变化版本。
3. **资源导出**：本帧新出现的资源登记进资源目录，目录按 run 递增，编号不复用。
4. **封存**：生成不可变的 `HostStateSnapshot`，发布到 `HostStatePublication`。

快照只拥有规范字节和数字身份，三个 Peer 共享同一份，不按 Peer 复制。

### 3.2 按 Peer 组帧

网络线程为每个 Peer 持有一个 `HostStatePublisher`：

- **基线**：每帧相对该 Peer 最新 ACK 的快照做增量。尚无 ACK 时发完整快照（base=0）。
- **增量规则**：帧中带上“最后变化版本”晚于基线的全部字段（平铺记录）或块（块记录）。丢包后下一帧仍会带上它们，Host 不需要保存每个 Peer 的历史快照；“变了又变回”的值也不会漏掉。
- **在途窗口**：每条流最多 8 帧在途，在途正文不超过 64 KiB（`wire.json` 的 `world_send_window`、`dynamic_send_bytes`）。超过 500 ms 未确认的帧不再占窗口（`sent_age_ms`）。
- **空帧**：场景静止、没有任何变化时仍然发送空帧，用来推进客机帧号。
- **编码共享**：确认版本相同的 Peer 共用一份编码结果（`EncodingCache`）。
- **Mod 记录**：按该 Peer 确认的实际发送值判断是否要补发；私有记录只进入接收者的帧。完整基线携带已经成功采集的全部适用记录。普通帧预算先留给原生正文与表现事件，必要时由可靠基线承载较大的 Mod 记录。

### 3.3 沿用与离开

“沿用”和“离开”分开编码：

- **沿用**：成员仍在，本帧没有新值（采集失败或资源暂缺）。帧中的沿用列表是一串递增的 u16 成员号，客机保留该对象的上次值。
- **离开**：成员从成员目录中移除，客机删除对应对象。

不能用“本帧没有记录”同时表示两者，否则客机会把没采到的对象删掉再重建。

## 4. 线格式

### 4.1 消息

二进制状态消息由外层 ICSR 封装承载（分片、重组、可靠重传见第 7 节）。消息类型（`mod/src/state/wire_protocol.h`）：

| 编号 | 类型 | 方向 | 通道 |
| --- | --- | --- | --- |
| 21 | Frame：状态帧 | Host → Client | 不可靠；World 或 Body |
| 23 | Resources：资源表 | Host → Client | 可靠 |
| 9 | AppliedAck：接收确认 | Client → Host | 不可靠，定期补发 |
| 10 | Resync：请求完整基线 | Client → Host | 控制，每 250 ms 重发直到 Host 响应（`resync_repeat_ms`） |
| 27 | ModManifest：版本、启用清单、声明及内容 ID | 双向 | 握手控制通道可靠交换 |
| 28 | ModIntent：声明意图 | Client → Host | 授权 World 路由，连接内有序重发 |

通道（`StateLane`）：Control、Baseline、Context、World、Body。

### 4.2 帧结构

每条消息以 50 字节公共头开始：

| +0x00 u16 layout_version | +0x02 u64 session | +0x0A u64 run | +0x12 u64 floor | +0x1A u64 dimension | +0x22 u64 room | +0x2A u64 scene |
|---|---|---|---|---|---|---|

`layout_version` 必须与本地完全相等。其余六项是稳定的作用域身份；客机据此拒绝属于旧 run、旧房间的帧。

状态帧随后是帧头（`section_count`：1 为单流，2 为 World 加 Body 的共同提交），然后是一到两个分段。分段头的主要字段：

| 字段 | 含义 |
| --- | --- |
| `stream` | 0 为 World，1 为 Body |
| `flags` bit0 | 基线帧，当且仅当 `base_version` 为 0 |
| `member_epoch`、`resource_epoch` | 引用的成员目录和资源表版本 |
| `base_version`、`target_version` | 本 Peer 本流的继承起点和目标版本 |
| `source_revision` | Host 封存的来源修订 |
| `game_frame` | Host 的原生帧号，客机按帧号方案 B 写入 |
| `record_count`、`group_count`、`event_count` | 记录数、沿用成员数、事件数（Body 的事件数必须为 0） |
| `event_watermark` | 该 World 覆盖的连续事件水位 |

记录有两种格式，同一帧里可以混排。解码器读记录头前 4 字节里的 `layout`，按布局号判断用哪一种：

**平铺记录**（实体、Player、Grid），9 字节记录头：

| +0x0 u16 member | +0x2 u16 layout | +0x4 u32 record_bytes | +0x8 u8 set_mode |
|---|---|---|---|

正文依次是字段集合、值区、附加区：

- **字段集合**：`set_mode=0` 为两级位图（每 16 个字段一组，先写组位图，再写各置位组的 u16 组内位图）；`set_mode=1` 为 LEB128 编码的序号差列表；`set_mode=2` 表示全部字段、不带集合，用于 base=0、新建和换身份。编码器在 0 和 1 中取较短的一种。
- **值区**：按字段序号升序拼接各变化字段在镜像中的定长字节；容器类字段写规范化的头模板。
- **附加区**：变化的容器、长字符串、owner 槽的整段内容。
- 字段序号、镜像偏移和写入组都由生成器生成（`state_flat.inc`），原生偏移不上线。

**块记录**（Game、Room、Level、显示域等全局根和控制组），12 字节记录头：

| +0x0 u16 member | +0x2 u16 layout | +0x4 u32 block_mask | +0x8 u32 record_bytes |
|---|---|---|---|

`block_mask` 的每一位对应一个块（0—31），后面依次是置位块的正文。块的划分来自 `binding/state/legacy-block-layout.json`。

两种格式的字段顺序、宽度和容器编码都由生成的表决定，双方用同一份生成结果。

分段之后携带成员目录增量；基线帧和无法用增量表达的换号携带完整目录。全部结构的逐字段布局见生成文档 `mod/binding/layouts/09-wire-format/`。

`StateFrameHeader` 中的 `mod_bytes`、`mod_result_bytes` 分别给出帧尾的 Mod 状态记录区和私有意图结果区长度。两区随 World 或联合帧发送。Mod 记录头依次是 u16 Mod 序号、u16 声明序号、u16 目标、u8 接收者和 u32 字节数。目标按作用域表示 global、参与者序号或实体成员号；公开记录的接收者为 255。有效结果携请求序号，正文最多 256 B，随发起者的 World ACK 确认。

布局 94 为原生显示保留 Mod 序号 65534，承载 Player Plus 与权威查询结果、楼层名称、Boss 血条和 PGD 查询镜像。[声明值格式](archive/design/mod-adaptation.md#声明类型的采集与编码)也说明保留段的采集和安装。

### 4.3 字段编码

- 标量按小端原样字节；记录正文不保留原生对齐，解码一律用 memcpy。
- 引用编码为成员号，Null 为 `0xFFFF`。
- 资源编码为资源表中的句柄。
- 容器编码为元素数加元素，元素数有上限。
- 锚点和换算字段按 Host 帧空间编码，见[采样](capture.md)第 2.5 节。

## 5. 成员身份

成员身份由 run、space、id、use、shape、layout 组成：

- `use`：同一原生对象被复用为不同实例时递增，防止把新实例当成旧实例。
- `shape`：对象的 type／variant／subtype 形态版本。形态前进时，客机对支持原生 Morph 的类型原地变形，其余删掉重建。
- 成员号（u16）只是线上压缩编码，客机按完整身份查找本地对象。

客机收到 World 时不等待单独的成员表；成员目录增量随帧携带。

## 6. 资源与事件

### 6.1 资源表

资源指 ANM2 文件、动画、图像、音效、配置等不可变内容：

- 资源目录在 run 内只增不改，编号不复用，走可靠通道。
- 线上只传资源引用（VFS 相对路径、配置编号等），不传像素或音频数据。客机用本机游戏文件装载。
- World 引用的资源还没就绪时，只延后用到它的对象，整帧照常应用。
- 资源装载在新条目到达后、主线程空闲预算内执行，不绑定在某一帧的安装流程里。

资源协议的类型和字段见 `mod/binding/layouts/09-wire-format/Resource*.md`。

### 6.2 事件

瞬时内容（音效、横幅文字、fortune 等）走有界事件队列：

- 每个 Peer 一条队列，事件带序号，随 World 重复携带，直到该 Peer 的 ACK 覆盖它。
- 客机按序号去重，同一事件只播放一次。外观类事件超过有效期就丢弃。
- 音乐请求、循环音效和持续全屏演出按当前值同步。Mod 调用的过场走 World 事件 6；清场请求使旧 World 提前退休时，可靠 Retire 补携同一请求序号和资源 ID。
- 客机放行的原生显示代码自己发出的音效在本地播放，Host 不发送。

## 7. 确认与恢复

### 7.1 ACK

- 客机完整解码一帧、并把结果保留进快照环以后，立即发送 AppliedAck，报告收到的最新目标版本。不等原生应用完成。
- Mod 结构校验失败只丢弃该条记录，沿用上一份有效值；主线程 setter 失败同样与 ACK 分开。私有意图结果在接收时交给连接邮箱，主线程在本轮应用后派发。
- ACK 每 50 ms 补发一次（`ack_repeat_ms`），丢一个 ACK 不会卡住后续帧。
- 客机保留最近 8 个已确认快照（`decode_snapshots`）。只要 Host 选的基线还在环里，丢包和乱序都能解码；比当前目标更旧的帧直接丢弃。

### 7.2 Resync

客机在以下情况发 Resync，Host 为该流重建 base=0 的完整帧：

| 原因 | 触发 |
| --- | --- |
| Base | 基线不在快照环里 |
| Table | 成员目录或资源表无法衔接 |
| Dependency | 依赖无法满足 |
| Budget | 超出解码或内存预算 |
| Apply | 对象失败达到阈值：同一成员原生失败 3 次（`native_object_failure_limit`），或同一成员连续 30 帧池满（`pool_object_missing_limit`） |
| Event | 事件水位无法衔接 |
| Lifecycle | 生命周期变化 |

请求完整基线期间，客机继续显示当前画面。

### 7.3 连续失败

- 客机后台解码失败、且同一原因连续 3 帧（`decode_failure_limit`）时，才请求完整基线。
- Host 全局采集连续失败（`capture_failure_limit` 30）后，有新来源时发完整基线。

## 8. 传输

传输层在 `mod/src/replica/stream_transport.*` 和 `mod/src/net/`：

- **UDP 数据报**：1200 字节，分片正文 1136 字节。多个小条目合包发送。
- **可靠发送**：`ReliableSender` 和 `Reassembler` 负责资源表等可靠消息，重传超时 100—1000 ms。
- **压缩**：World 和 Body 正文各自独立 zstd 压缩（级别 3）。
- **心跳与超时**：心跳 250 ms，Peer 超时默认 3000 ms。
- **握手**：双方交换能力声明，精确匹配二进制状态和布局版本。随后比较启用 Mod、版本、规范化声明和内容 ID，匹配后继续 Ready；拒绝原因送到大厅。

## 9. 预算

预算的唯一来源是 `wire.json` 的 `budget_policy`，生成到 `state_budget.inc`：

| 项目 | 值 |
| --- | --- |
| Host 总上行 | 1,125,000 B/s（9 Mbps，按 10 Mbps 链路的 90%） |
| 每 Peer | 375,000 B/s |
| World／Body | 各 150,000 B/s |
| 可靠通道 | 50,000 B/s |
| 控制 | 25,000 B/s |
| 普通消息上限 | 64 KiB |
| 首次准备 | 不超过 1 MiB；发送 8 s、总计 10 s 内完成 |

运行时配置 `isaac-cs/config.json` 的 `stream` 段可以把这些上限调低，不能调高；协商时远端只能收紧保护上限。内存按三池记账：值池 512 MiB、线上池 128 MiB、工作区池 128 MiB，所有 owner 共享总账本。

## 10. 版本演进

- 布局源或任何影响互通的合同变化，`version.json` 的 `version` 加 1。握手精确匹配，不做向下兼容。
- 当前布局为 94，紧凑正文和输入记录使用 schema 3。扩展按键按冻结清单升序编号，输入携带两个 u64 位图表示按住和边沿。
- 编码格式历史：84 及以前全部为块编码；85 为平铺记录试验合同；86—89 回到块编码；90 起实体、Player、Grid 正式使用平铺记录。`mod/src/state/flat_layout.h` 的 `UsesFlatRecordContract` 对 90 及以后的版本返回真，Host 发布、线格式和客机影子／安装都按它判断。

## 11. 扩展

- **新增同步字段**：按[采样](capture.md)第 7 节修改布局源。线格式由生成器自动更新，无需改编解码代码。
- **新增消息类型**：在 `wire.json` 的 `protocol_constants` 登记编号，在 `state/wire_protocol.*` 实现编解码，再在 Host 发布器和客机接收器里接线。不要复用已退役的编号（6、8、22）。
- **调整预算或窗口**：只改 `wire.json` 的 `budget_policy`，不要在代码里写常数。
