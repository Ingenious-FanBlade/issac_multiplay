## 1. 问题与目标

第 15 步四身体高负载窗口中，Client 的 World 与 Body 应用频率同时落在约 20Hz（run112、113、117、120、123、124、127），空场景可达 30／60Hz（run101）。直接原因有两个：

1. 成员表或资源表一变，Host 就改走 World＋Body 联合事务，并停等真实 ACK。
2. Client 主线程每批的准备和安装成本按整个场景计，不按变化量计。

两者叠加的方式：一次联合事务的完整往返只能落在 60Hz 的 Manager 边界上，周期不是 2 帧（30Hz）就是 3 帧（20Hz）；主线程越重，越容易滑到 3 帧。

目标保持现行指标不变：高负载下 World 30Hz、Body 60Hz，动态安装 p95≤2ms、p99≤4ms。带宽、期限、内存总额、5 份表快照、每流一票据、唯一主线程写段、真实成功 ACK 均不放宽。

## 2. 原因定位

### 2.1 换表触发联合事务

| 原因 | 位置 | 说明 |
| --- | --- | --- |
| 成员代次是全局单一计数 | `host_publish.cpp:193-195` | 成员列表与上一帧不完全相同即加一；成员含全部实体根，短寿命实体的生灭都算换表 |
| 资源代次同理 | `host_publish.cpp:197-201` | 目录追加一项即加一 |
| 代次不同即联合 | `host_publish.cpp:328-330` | 不区分变化是否触及 Body 依赖 |
| 表全量重发 | `host_publish.cpp:320-322` | `previous_epoch` 固定填 0，成员表和带 payload 的资源目录每次整张发送 |
| 资源表未变也要重发 | `client_receive.cpp:449-456` | 只有收到 Resources 才产生 ContextReady |
| 三段串行停等 | `live.cpp:255-285`、`host_publish.cpp:325` | Members 等可靠回执，Resources 等回执和 ContextReady，联合帧等 AppliedAck |
| 等待期间零下发 | `host_publish.cpp:332-343, 401` | `awaiting_joint` 期间 `Next()` 返回空 |
| Body 的 60Hz 采集被丢弃 | `host_publish.cpp:344` | 联合帧只用 ordinary 阶段的 `table_source` |
| Client 联合独占 | `client_receive.cpp:84-97, 320-322, 402-406` | 联合帧到达即清 Body 等待位、撤回准备中的普通票据，其后普通帧全部被挡 |

高负载下成员几乎每个 ordinary 帧都变：run117 编号复用 28686 次／180 秒，约每帧 5 个新成员。于是发布器基本一直处在“换表→联合→等 ACK”的循环里，World 与 Body 被同一个联合周期绑在一起。

### 2.2 主线程准备与安装偏重

| 原因 | 位置 | 说明 |
| --- | --- | --- |
| 计划按完整目标展开 | `client_plan.cpp:297-300, 327` | 每条记录用完整 mask 遍历，不只变化块 |
| 描述遍历全部字段和标量 | `client_atomic_install.cpp:571-605` | 高负载每次安装约 2.9—3.6 万条原始操作 |
| 未变化跳过只对普通 Body 生效 | `client_atomic_install.cpp:316-321` | World 与联合批次逐条预检、取原值、写入、发布前读回 |
| 每批从零重建 | `client_binary_scene.cpp:117` | 每张票据新建安装器，索引、排序、读回表全部重做 |
| 切片让出的代价是一整帧 | `client_preparation.cpp:403, 418, 459`、`client_binary_scene.cpp:504-511` | 超片即返回等待，而同一票据每个 Manager 只给一个准备片 |
| 准备阶段有平方级查找 | `client_preparation.cpp:285, 298, 309, 312, 316` | 对每个对象在实体、格子、描述符列表里线性查找 |

量级参考（四身体）：run127 的 World 安装 3.3ms（写入 2.0、发布读回 0.44、排序 0.66、Seal 绑定 0.51），run112 的描述 3.8ms。准备加安装合计约 8—10ms。

## 3. 方案总览

| 编号 | 改动 | 针对的原因 | 是否改合同 |
| --- | --- | --- | --- |
| A1 | 表增量下发；资源表未变时不重发 | 全量重发、多一次往返 | 否，沿用现有 `previous_epoch` 字段 |
| A2 | 表与帧流水发送，普通流不再等 ContextReady | 串行停等 | 是，修订“未准备表不发帧” |
| A3 | Body 闭包兼容时，World 单流换表 | 代次不同即联合 | 是，修订“成员表变更一律联合” |
| A4 | 成员号借用下限回报 | 包 65 的 `client_member_index_still_borrowed` | 是，ContextReady 加字段，整数版本 81→82 |
| A5 | 收窄 `Preparing` 与 episode 的范围 | 普通换表被当成准备期 | 否，随 A3 调整 |
| B1 | 准备片在同一 Manager 窗口内续做 | 让出即丢一帧 | 否 |
| B2 | 平方级查找改为后台封存的索引 | 准备偏重 | 否 |
| B3 | World 未变化块跳过预检、写入和读回 | 成本按全场景计 | 是，修订 13-incremental 第 4.5 节的保守范围 |
| B4 | 场景级持久安装索引 | 每批从零重建 | 是，落实 13-incremental 第 2.2 节的拟定结构 |
| B5 | 后台计划按记录复用 | 后台切片 6—8ms | 否 |

A 组解决“为什么只有 20Hz”，B 组解决“为什么安装超过 2ms”。A3＋A4 是频率问题的主修复；A1、A2 即使 A3 不采纳也能单独缩短联合周期。

## 4. 问题 1 的修复

### 4.1 A1：表增量下发

- 成员表：以 Client 已确认收到的上一份表为基准，只发 Join／Reshape／Leave 操作，填真实 `previous_epoch`。Client 侧 `client_tables.cpp:176-188` 已按 `previous` 合并，无需改格式。
- 资源表：目录只追加，增量就是新增条目。Client 侧 `client_tables.cpp:203-211` 同样已支持。
- 资源代次未变时不发 Resources。Client 在成员表安装成功且已有当前资源表时直接给出 ContextReady。
- 基准选择：只用可靠回执已完成的上一份表。发生 Recover、传输取消、新路由或 base=0 时退回全量（`previous_epoch=0`）。
- Client 遇到 `previous` 与当前代次不符时，现行为是终止（`client_member_previous_epoch`）。保留这一行为，由 Host 的基准规则保证不触发。

### 4.2 A2：表与帧流水发送

现状是 Host 必须先收到 ContextReady 才发使用新表的帧。改为：

- 表交给可靠发送后，Host 即可生成并发送使用该表的普通 World 帧，不等 ContextReady。
- Client 对缺表的 World 帧已有暂存路径（`client_shadow.cpp:742-748` 返回 Wait，进 World 等待槽）。表到达后正常解码。
- 缺表的 World 帧等待到期时，只丢候选，不请求恢复。现状到期会走 `Recover(Dependency)`，在表分片丢包重传（RTO 起步 200ms）时会把一次丢包放大成完整重建。
- base=0 的基线和恢复仍保持“表确认后才发帧”，因为它们体量大，受 1MiB／10 秒的 episode 约束。
- ContextReady 保留，用于基线、诊断和 A4 的下限回报。

**备选**：把“从已确认基线到目标”的累计成员增量直接放进 World 帧。优点是丢包时没有队头阻塞，也不需要独立的表消息；代价是改帧格式和公共线合同。建议先实施流水发送，在带延迟和丢包的代理场景下如果观察到表重传造成的 World 停顿，再评估这一备选。

### 4.3 A3：World 单流换表

**判定**。定义“闭包兼容”：对一组记录自身的成员条目和它们的块实际引用到的成员，在表 A 和表 B 中的编号与完整身份（space、layout、id、use、shape）逐项相同。

Host 的联合条件由“代次不同”改为下列任一成立：

- 冷启动、恢复、任一流无确认基线。
- `structure_revision` 变化（P6／P7 拓扑或绑定变化，现有规则）。
- Body 已确认状态在其确认表与新表之间不满足闭包兼容，例如玩家加入、离开、换形，或被 Body 引用的实体换了编号。

其余成员或资源变化走普通 World 单流帧，携带新代次。资源目录只追加，旧条目不变，资源代次变化本身不构成联合理由。

**Body 的表代次**。Body 帧使用 World 已确认的表代次，不使用最新代次。发送前对本帧携带块和继承块做同一个闭包兼容检查；不满足时本周期不发 Body，等 World 确认后再发，并单独计数。这样 Body 永远不会引用 World 尚未安装的成员。

**Host 需要补的数据**。`HostStateRecord` 记录编码时实际解析到的成员编号集合（排序去重）。包 65 加过这份存储，包 69 撤回；本方案恢复它，按实际容量计入 Values。

**Client 配套**。

- 影子解码：World 单流候选在新表下解码时，对两表间发生变化的成员条目，用现有反向索引（`client_shadow.cpp:415` 的 `MemberConsumers`）找到消费块；消费块未随帧携带则拒绝，返回 JointRequired。Body 侧对称处理。
- 主线程发布：`client_binary_scene.cpp:131-160` 的 `CompatiblePeer` 已做对侧成员兼容核对，保留。
- 前代解码基线：`client_shadow.cpp:512-517` 要求基线、当前和报文三者代次相同。换表频繁后这一条件几乎不成立，Body 单槽等待（13-incremental 第 10.4 节）会失效。改为代次不同但闭包兼容时也授予资格。
- 联合帧到达时的独占、撤回和排空规则不变。

**联合期间的 Body**。联合帧继续只用 ordinary 来源。A3 落地后联合只出现在真正的结构变化上，不再是常态，暂不为它引入 Body 阶段来源。

### 4.4 A4：成员号借用下限

包 65 失败的首因是 `client_member_index_still_borrowed`：Host 依据两流 ACK 认为旧目录已无人使用并回收编号，而 Client 主线程的安装计划、退休批次或 Render 仍持有旧成员表快照。包 106 用“收表前先回收”缓解了联合路径上的时序，但没有消除这个推断本身。单流换表下两流代次交错，这个窗口会更宽。

修复方式是让 Client 明确告知，而不是让 Host 推断：

- Client 后台线程在回收点计算“仍被引用的最小成员代次”，即 `client_tables.cpp:94-98` 中引用计数大于自身持有的快照里最小的那个；没有旧借用时等于当前代次。
- 该值随 ContextReady 回报。下限变化时立即发一次，其后按现有 50ms 周期重发。ContextReady 增加一个 `member_floor` 字段，整数版本 81→82，拒绝混用旧版本。
- Host 为每份已发出的成员表保留目录租约，直到 Client 回报的下限越过它。编号只有在所有租约都释放后才回到空闲池，沿用现有 `HostMemberIndex::ownership` 计数。
- 不把 AppliedAck 用作载体：它是目标凭据，Host 按整体相等匹配（`host_publish.cpp:412`），加字段会破坏匹配。
- 资源表不需要下限：资源键稳定，目录只追加，不复用编号。

**表快照上限**。Client 每类表最多保留 5 份。单流换表后同时存活的代次会增多。Host 用下限做背压：已发出但未被下限越过的成员表达到 3 份时，暂不发新表，World 帧等下一周期，届时直接发相对上一份已发表的累计增量。背压次数单独计数，不提高 5 份上限。

**Client 的 `Index()` 检查保留**。它仍是真实冲突的最后防线，下限机制只是让它不再被正常时序触发。

### 4.5 A5：收窄准备期

`HostStatePublisher::Preparing()`（`host_publish.cpp:430-432`）目前在代次不同或 `awaiting_joint` 时为真，连带开启 episode 计费、期限检查，并让上行切到重建速率（`worker.cpp:214`）。A3 之后，闭包兼容的换表不属于准备期：

- `Preparing()` 只在冷启动、恢复和真正需要联合的结构变化时为真。
- 增量表走可靠通道的常规额度。按每秒 30 条、每条几十到几百字节估算，远低于 50KB/s；实际值需实测。

### 4.6 预期的时序变化

| | 现状（高负载） | A1—A5 之后 |
| --- | --- | --- |
| 每个 ordinary 帧 | Members 往返 → Resources 往返 → 联合帧 → AppliedAck | 增量表与 World 单流帧连续发出 |
| World | 等联合周期，2—3 帧一次 | 每个 ordinary 帧一次，受主线程安装成本约束 |
| Body | 与 World 同周期，PlayerPost 采集被丢 | 独立 60Hz，使用 World 已确认的表 |
| 联合事务 | 几乎每帧 | 仅玩家拓扑、结构变化、恢复 |

## 5. 问题 2 的修复

### 5.1 B1：准备片在同一窗口内续做

现状：`StageObjects` 超 2ms、`StageFields` 超 4ms、原生资源超 2ms 即返回等待；`client_binary_scene.cpp:504-511` 对同一票据每个 Manager 只调用一次准备，于是一次让出等于多等 16.7ms。

改动：

- `ClientStateNativeStep` 增加“主动让出”标记，与“被阻塞”（CPU 借用未清、资源未就绪、借用未排空）区分开。
- Manager 的准备循环对主动让出的票据，在 8ms 窗口内继续给片；每片之间先让另一通道已就绪的提交执行，保持 Body 不被 World 的长准备挡住。
- 被阻塞的票据仍然等下一帧。8ms 窗口和“提交段不可穿插”不变。

### 5.2 B2：消除准备阶段的平方级查找

`DescribeObjects` 对每个对象在 `Entities()`、`Grids()`、`Descriptors()` 中线性查找，事件 owner 也在 `Objects()` 中线性查找。改为后台构建计划时封存“对象下标→实体／格子／描述符条目”的整数索引，主线程直接取用。索引是纯值，随计划计入 Values，不含原生地址。

### 5.3 B3：World 未变化块跳过

**2026-11-16 World 应用节奏任务二第 3 步**。符合 B3 的 World 独占实体和格子根可从固定叶地址配方省略未变块操作，共享根沿用下述逐操作路径。片段和生成的操作共同参与漂移读回。[M1b 实施](13-client-world-cadence.md#m1b-未变的块不生成操作)

把现有只对普通 Body 生效的 `unchanged` 判定推广到 World 记录。一条操作同时满足以下条件时，跳过预检、取原值、写入和发布读回：

- 所属对象是复用（Reuse），不是加入、换形或重映射。
- 所属块不在该记录的值变化、结构变化、依赖变化掩码里（`client_plan.cpp:315-318` 已逐块算出）。
- 是根对象的直属定长字段，或已保留承载的容器；操作类型为原样复制、容器或掩码写。
- 本批执行的原生回调都没有把该字段列入写集。

最后一条需要先建一张**回调写集表**，列出 `Initialize`、`PrepareFieldOwners`、`InstallMembers`、显示重建、事件回放各自可能改写的字段（按布局和字段编号）。已知的例子：显示重建会重置 Backdrop 的几个 Sprite，地狱背景初始化会覆盖 Room 的活动标量（`client_atomic_install.cpp:290-293`）。写集未知的回调按“可能写任何字段”处理，该批不跳过。

| 事件回放 | Boss 和 RoomTransition 历史事件分支只验证或由 World 基线覆盖。`PlaySelected` 的直接写入涉及样本强引用及声道参数，`9F7B20` 可经 `BECA14` 进入持有者释放路径 | 实际单次 SFX、道具横幅、fortune 以及未知种类走完整安装。音频后端虚调用、队列冲刷和 HUD 回调的完整写集尚未核定 |

边界：

- 操作仍然生成并保留在本批索引中，滚动漂移检查继续覆盖它们。跳过的只是本批的写和读。
- 联合批次、带显示重建的批次、base=0 批次不启用。
- 本地显示代码写脏的权威字段仍由漂移修复恢复，这一职责不变。

收益上限取决于每帧变化块占比。现有 `stream.binary.world.*` 已输出值变化、结构变化、依赖变化和复用块数（`client_plan.cpp:320-323`），实施前先读这组计数确认。

### 5.4 B4：场景级持久安装索引

**2026-11-16 World 应用节奏任务二第 2 步**。写集资格决定本批怎样执行 B3，World 固定内嵌叶的配方由根实例、结构、依赖和承载核对决定。显示重建继续撤销配方。此项更新下方 B4 原设计中的回调失效条款。[World 应用节奏设计 4.5 节](13-client-world-cadence.md#45-改动项)

B3 省掉写入和读回，但描述（3—4ms）、排序和 Seal 仍按全量做。要把这部分也降下来，需要让索引活过单个批次：

- 由场景 owner 按流保管一份“已发布字段索引”：每条记录的字段归属、操作模板（对象下标、相对根的偏移、宽度、类型、优先级、执行顺序）和读回分组。
- 每批只为变化块、结构变化的记录和新加入的对象重建对应片段，其余沿用。执行顺序稳定时不重排。
- **不缓存绝对地址和页见证**。每批仍由 `InspectStaged` 核对根对象的真实地址和实例代次，绝对地址在本批内按“根地址＋模板偏移”现算；经过动态容器或晚绑定的路径照旧每批重新解析。
- 失效条件：对象实例代次变化、记录的结构或依赖掩码非空、布局或条件臂变化、容器换承载、原生回调写集触及。失效只作用于对应记录。
- 滚动漂移检查改为读这份持久索引，不再依赖“最后一次写入该流的安装器”。

这是 13-incremental 第 2.2 节拟定的 `StructurePlan`／`NativeBindingSet` 的落地，改动面最大，放在最后。

### 5.5 B5：后台计划按记录复用

后台每批为完整目标重建路径、字段和标量表，约 3.5—4.7 个 2ms 片。对块引用、结构和依赖都与上一份已接受计划相同的记录，直接沿用其计划片段，只为变化的记录重新遍历。它和 B4 共用同一套“记录是否可沿用”的判定，建议一起做。

### 5.6 不改动的部分

- 每个 Manager 的滚动漂移检查预算、旧批次退休排空、`InspectStaged` 的对象与资源核对保持。只补计量，确认它们在高负载下的实际占比后再决定是否处理。
- 新成员的原生构造成本不在本方案内压缩。B1 让它不再额外丢帧；是否需要进一步处理看实测。

## 6. 实施顺序

同一二进制重构目标内的顺序，不是新增步骤编号或独立验收。

| 顺序 | 内容 | 主要落点 | 完成后应观察到 |
| --- | --- | --- | --- |
| 0 | 补计量 | `net/live`、`client_receive`、`client_binary_scene` | 联合帧与单流帧各自的次数；表发出到 ContextReady 的耗时；因主动让出而跨帧的次数；上行令牌阻塞次数 |
| 1 | A1、B1、B2 | `host_publish`、`client_receive`、`client_preparation`、`client_binary_scene` | 联合周期缩短；准备不再因让出跨帧 |
| 2 | A4，然后 A3、A5、A2 | `wire_protocol`、`host_publish`、`client_tables`、`client_shadow`、`net/live` | 高负载下联合占比降到结构变化的水平；Body 回到独立节奏；无借用冲突 |
| 3 | B3 | `client_atomic_install`、`client_atomic_bindings` | 写入与读回字节随变化块数下降 |
| 4 | B4、B5 | `client_plan`、`client_atomic_install`、`client_binary_scene` | 描述、排序、Seal 和后台切片随变化量下降 |

顺序 2 中 A4 必须先于 A3，否则会重现包 65 的失败。

### 顺序 0、1 实施记录

- Host 状态中 `stream.peer.<ordinal>.binary_{joint,world,body}_sent` 计完整发送的帧，可靠重传不重复计。`binary_context_ready_{count,total_us,max_us,last_us}` 从同一目录对的第一张表首次完整发出，量到 Host 收到匹配的 ContextReady。取消会结束本次计时。同页 `budget_blocks` 计各上行令牌桶拒绝的发送尝试。
- Client 的 `stream.binary.world.joint_frames` 和各流的 `single_frames` 计完成收包与帧结构检查的候选。两流各有 `wait.prepare_yield_frame`。公共资源邮箱使用 World 页的 `wait.resource_yield_frame`。计数只在一个 Manager 窗口结束时仍有因主动让出而延后的工作增加。
- Host 用可靠完整回执确认上一版成员、资源增量基准。途中恢复、取消后重发、新路由和 base=0 按全量表处理。成员操作无法表达同一身份键的换号时，改发完整成员表。双方通过现有握手声明 `state-table-delta-v1` 后启用增量和省略未变化的 Resources。旧的同布局端仍经完整表交接。Client 安装 Members 后可以用已有资源回报，Host 只用已完整发出的精确目录对推进。取消重发后，接收器按同路由表消息的序列丢弃迟到的旧传输。
- Manager 先服务已就绪的提交，再在同一 8ms 窗口续做主动让出的对象、字段和资源准备。原生调用及完整写段各自连续执行。实体、格子、描述符和事件 owner 的索引在后台封存，使用原计划的 Values 账户。

### 顺序 2 实施记录

- **A4**。布局 82 的 ContextReady 带 `member_floor`。Client 在后台回收后立即回报变化，再按 50ms 补发。Host 从可靠 sender 接管成员表起持有目录租约，按本路由单调下限释放较旧租约。未越过的成员表达到三份时延后换表，下一次从可靠回执确认的表计算累计增量。`stream.peer.<ordinal>.binary_member_backpressure` 按普通来源修订累计受阻周期。
- **A3**。Host 按实际编码引用比较成员编号和完整身份，并检查 Body 需要的资源前缀。兼容换表走 World，Body 以 World 已确认的目录组帧，不兼容的 Body 当前周期跳过。`stream.peer.<ordinal>.binary_body_dependency_blocks` 计因发布依赖而跳过的 Body 来源。旧成员项改变时，Host 携带受影响记录的消费块。Client 的影子用反向索引拒绝缺少消费块的单流，现行主线程配对复查仍按实际已发布根进行。Body 的唯一成功前代可跨兼容目录解码。
- **A5、A2**。兼容换表使用常规额度，一张可靠目录可与一个普通帧并行传输。所需目录全部交接给可靠发送后即可发送普通 World。Client 在原有等待槽中收取缺表的 World，缺表到期计入 `stream.binary.world.wait.table_wait_expired` 并仅丢弃该候选。冷启动、恢复和真实联合路径继续等待可靠回执和精确的 ContextReady。
- 第 15 步续验覆盖下限迟到、丢失和乱序、三份表背压和跨代 Body 前代、丢表分片时的 World 超期、事件水位跨表以及真实联合的完整恢复。

### 顺序 3 实施记录

实施前读取已有四身体记录中 Client 最后一份 World 计数。四项为累计计数，变化掩码可以重合。`reused_blocks` 只表示结构复用，包含可能有新值或依赖变化的块。

- Stage 仍生成全部操作和冲突索引，先核静态区间重叠。普通 World 中根对象为 Reuse、值／结构／依赖掩码均未标记的直属原样写、固定数组／保留容器元素及掩码写，延到 Seal 决定是否进入真实范围预检。Init 前缀、首次需要保存撤场原值的范围、附件接合、引用 setter 和专用字段保留完整路径。
- Seal 按实际承载和回调写集决定略过项。进入原生 Init、成员重登记和显示前按现场重验相应条件。需要回退时，在原生调用前补齐预检、原值与写入，使用已预留的撤销空间。跳过项继续参与滚动漂移检查。

### 顺序 4 实施记录

- **B4**。场景按流发布字段索引。每条记录按完整成员身份和原生实例号借用相对根的操作模板，稳定块沿用字段归属、操作宽度、掩码及优先级，变化块重新描述。布局、条件臂、结构、依赖及容器换承载会撤销对应记录的复用资格。已知回调写集命中的记录不会把模板交给后继，写集未知的批次撤销本批模板。动态容器、晚绑定和具名处理器继续解析当前承载。
- 执行键和读回分组键逐项相等时共享同一顺序。发生变化时按当前数字键重新组合，原生指令按数值下标执行。静态及晚绑定写重叠仍以当前批绝对区间判断。Seal 按描述期封存的具名字段清单物化绑定，原对象、资源、附件和生命周期复核保留。
- 漂移从场景当前流的分组索引出发，按精确已发布的影子目标借该流原生保管。内嵌字段从真实根及实例号加相对偏移定位，动态字段和专用修复仍交给当前具名 owner。纯索引不保存绝对地址、页见证或旧目录引用。
- **B5**。后台按流记录最后真正接受的计划，只在它与候选的实际应用基线完全一致时短暂借用。沿用相同块的字段、路径、标量和引用片段，给当前批次重新编号。域关系校验、按目标表的依赖核对和事件仍走当前路径。完成后释放旧计划的借用。
- 每流诊断新增 `plan_reused_records`、`native_reused_templates` 和 `native_reused_order`。为第 15 步对照后台 Plan、主线程 Describe／Order／Seal 以及滚动漂移提供复用计数。动态字段、相对位置重算、实际地址冲突和原生发布仍有每批开销。

## 8. 第 15 步补充覆盖

以下是这些改动可能出错的方式，实施后在同一整体验收中覆盖，当前均未执行。

| 改动 | 可能的失败方式 |
| --- | --- |
| A1 | 增量基准与 Client 当前表不一致；取消或恢复后仍按增量发送；迟到的旧增量破坏全量重发；资源未变时 ContextReady 未产生；旧资源与新成员的临时回报提前放行帧 |
| A2 | 帧先于表到达后超期；表分片丢包重传期间 World 停顿；缺表帧到期误触发恢复；基线被误放行 |
| A3 | 闭包判定漏掉某类引用；Body 引用了 World 未安装的成员；玩家加入、离开、换形、服装拓扑变化没有升级为联合；Host 与 Client 的兼容判定不一致导致反复 JointRequired；前代基线在跨代次下误用 |
| A4 | 下限回报丢失或迟到；下限倒退；Host 在下限越过前回收编号；长期读者使下限不前进，触发背压并饿死 World；表快照达到 5 份 |
| A5 | 普通换表误开 episode；真正的联合没有开 episode；上行速率模式来回切换 |
| B1 | 续片挤占 Body 提交；过了 8ms 仍开始新片；被阻塞的票据被当成主动让出而空转 |
| B2 | 事件 owner 已退出或换形却借错对象；Body 因缺少无关实体描述拒绝复用；数字索引取错域 |
| B3 | 回调写集漏项导致权威字段保留旧值；复用对象实际已换实例；跳过的字段被本地显示写脏后未恢复；撤销日志缺原值 |
| B4、B5 | 模板在结构变化后未失效；根对象换址后沿用旧偏移；容器换承载；漂移检查读到过期模板；退休后仍被引用 |

正向覆盖：四身体高负载 180 秒窗口分别报告联合与单流次数、World／Body 实际应用频率和间隔、安装分位数；带延迟和丢包的代理场景；装备变化、普通角色与卡牌、四身体重建、zero-empty、既有的联合安装后故障、World 安装后故障、静态写重叠和晚绑定冲突注入。

## 9. 未证实与风险

- 3 帧周期内各段的墙钟占比是由代码推出的，没有逐段实测。顺序 0 的计量就是为了补这一项。
- 成员变动多的轮次，每次安装的操作数也更多（3.3—3.6 万对 2.8—2.9 万）。仅凭现有记录分不开两个问题各占多少，所以不承诺单做 A 组或单做 B 组即可达标。
- 可靠通道突发额度 8192B，20Hz 时每周期约 6.7KB，接近上限；是否有令牌桶阻塞需要看计数。
- B3 的实际收益取决于块划分。如果高负载下多数实体每帧都有变化块，收益有限，需要靠 B4。
- A1 复用 Client 已有的成员表、资源表增量合并路径。此前 Host 始终发全量，增量路径仍待第 15 步实机覆盖。
- A1 的基准一旦与 Client 当前表不符，Client 会以 `client_member_previous_epoch` 终止会话，不是可恢复错误。因此 4.1 节“传输取消或恢复后退回全量”是硬性规则。
- A3 中“Body 引用到的成员集合”依赖编码期解析结果完整。包 65 的实现已撤回，需要重新核对所有引用类型（实体引用、待定引用、事件 owner）都经过同一个解析入口。
- 本方案没有处理新成员原生构造本身的耗时，也没有处理 Host 侧 ordinary 采集仍超过 2ms 的问题；后者见[第10步性能方案](10-native-capture-performance.md)。
