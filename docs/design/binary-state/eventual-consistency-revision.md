## 1. 为什么修订

### 1.1 现象

| 场景 | C/S（J273＋REPENTOGON，布局 83） | isaac-lan v0.7.2（J460） |
| --- | --- | --- |
| 300 静止泪弹、两参与者四身体 | 第一轮客机掉线；修复后 World 18.25Hz，Body 23.07Hz | World 30.00Hz，Host 采集 4.67ms，客机应用 6.90ms |
| 100 移动敌怪 | World 28.678Hz，收包至发布 41.687ms，Manager 超过 8ms 的窗口 1,013／1,802 | 未测 |

来源：[300 静止泪弹对照与续验](15-e2e-acceptance.md#2026-11-17-300-静止泪弹对照)、[恢复直接调度续验](15-e2e-acceptance.md#2026-11-17-恢复直接调度续验)。两边游戏版本和种子不同。300 泪弹那轮的采样器没有导出 Host 采集耗时和客机分阶段计时，所以 1.2 节对瓶颈的划分有一部分是推算。

### 1.2 原因

问题不在单个热点，而在合同本身。现行合同要求两件事：

- **ACK 等于原生安装成功**：Host 只能把“客机已原生装好”的目标当作差分基线（9-acceptance-recovery「Finish 的三种结果」）。
- **写前失败可完全回退**：任何一步失败时，当前显示的世界都不能被改动（FailedBeforeWrites）。

为满足这两条，客机必须：

1. **先建离线副本**：新对象先占池槽并构造好，容器字段在旁边单独构造，资源先装载（`client_preparation_native.cpp:308` 起，`client_field_staging_native.h`）。
2. **跨帧切片**：准备工作切成 2ms／4ms 的小片，分到多个 Manager 帧（`client_preparation.cpp:459`、`:507`）。
3. **一次性原子写入后读回核对**（发布读回、`PublishReadBytes`）。
4. **维护借用、保管、排空账目**：保证离线副本和旧场景的析构顺序正确（12-client-contract 第 5 节，13-client-incremental-apply 第 3 节）。
5. **成员表、资源表先可靠送达**：引用这两张表的 World 才能安装（9-public-wire-contract 第 4、8 节）。

后果：

- 一帧 World 要隔好几个渲染帧才装好。M0 分段中排队超过一半：本流忙等待 20.1ms，接票等待 8.1ms，准备完成至提交等待 6.5ms（13-client-world-cadence 4.12.1）。
- ACK 要等主线程安装完才发出，而 Host 只允许 2 帧在途（`wire.json` `world_send_window=2`，`host_publish.cpp:575`），所以 World 频率约为 2 ÷ 往返时间。300 泪弹下 18.25Hz，对应往返约 110ms（推算）。
- 严格校验把可以容忍的问题升级成断线。300 泪弹第一轮就是这样：J273 的 Tear 池只有 512 槽，新旧两套场景同时占着，于是报 `binary_stage_entity_pool_capacity`，接着 `binary_prepare_install_deadline`，最后断开。
- 换形态这类结构变化要走成员表变更、可靠上下文、联合目标和 Body 等待，是最慢的路径之一。

### 1.3 成熟做法

服务器权威、客机只负责显示的引擎，普遍采用“最终一致、最新值覆盖”：

- **Quake 3／Source**：快照对客机最后确认收到的快照做增量，走不可靠通道，丢了不重发；客机在网络阶段直接写实体。
- **Unreal**：属性只保证最新值最终到达；对象引用暂时解析不了就先挂起，到了再补。
- **Tribes／Halo**：状态与事件分开；服务器按优先级和预算分配带宽。

这些方案共同的是：ACK 只表示“收到”，与客机渲染进度无关；一帧内直接应用，Render 看不到写了一半的状态；单个对象出错，下一帧纠正。只有确定性锁步和回滚类方案需要严格一致，因为客机自己跑模拟。我们不属于这一类。isaac-lan 采用的也是这套做法：

- 视图对已确认的依赖版本做增量，压缩时以已确认版本为前缀；
- 至少 8、最多 16 帧在途，另有 64KB 上限（`src/net/world_transfer.h:148`）；
- 回执只报告最新收到的状态；
- 客机在一帧内删除、生成、写字段、挂引用（`src/bridge/sync/entities.lua`）；
- 玩家泪弹缺失可以容忍。

### 1.4 我们的特殊之处

我们写的是闭源原生对象的内存，里面有指针、容器和资源，写错会直接崩溃，而不只是显示不对。这需要**写前校验**，不需要**写前准备与回退**。安全由三件事保证：

- 后台校验输入；
- 指针、容器、资源字段走具名原生函数；
- 写入前确认目标对象仍然存活。

## 3. 传输与确认

### 3.1 World／Body 帧

- **基线**：每帧相对一个**客机已 ACK 的快照**做增量。Host 取它收到的最新 ACK 作为基线；还没有任何 ACK 时发完整快照（base=0）。
- **快照环**：客机保留最近 K 个已 ACK 的纯值快照，即解码后的影子值，不含原生地址。K 不小于在途窗口，基线落在环外时回 Resync。
- **在途窗口**：Host 按“帧数不超过 N，且在途字节不超过 B”控制，建议 N=8、B=64KiB（决定 E2）。超过 500ms 未确认的旧帧不再占窗口，参照 isaac-lan 的 `lostStateAge`。
- **回执**：ACK 只报告收到的最新目标号，每 50ms 补发一次（沿用 `ack_repeat_ms`）。丢一个 ACK 不会卡住后续帧。
- **快照之间不串链**：只要基线还在快照环里，丢包、乱序都可以解码。比目标号更旧的帧直接丢弃。

### 3.2 成员身份

World 记录头自带成员键（run／space／id／use／shape／layout），客机按键查找本地原生对象。现在的成员号压缩（u16 member 加成员表）可以保留作线上编码，但要满足两条：

- 成员表增量随 World 一起携带，或者 World 写完整键；
- 客机收到 World 时不再等待可靠的 Members 上下文。

具体编码在实施第 1 步定：优先在记录头写完整键，字节开销计入预算；超出预算时再改为随帧携带表增量。

**联合（joint）**只保留给 base=0 的完整快照。Body 引用的成员客机还不认识时，只跳过 Body 中的这部分，不等待联合。

### 3.3 资源表

资源仍然是 run 内不可变、编号不复用的目录，走可靠通道。World 引用的资源还没就绪时，只延后用到它的对象，整帧照常应用。资源装载（ANM2、贴图、音效）作为独立的预载任务：在新资源条目到达后、主线程空闲预算内执行，不再绑定在某一帧 World 的准备流程里。

### 3.4 事件

事件队列和水位语义保持：按 Peer 有界、带序号、重复携带直到 ACK。改动有两处：

- **ACK 时机**：事件水位随接收 ACK 推进，不再等原生成功。
- **回放时机**：事件在主线程应用到“包含它的最新 World”时按序回放。被跳过的中间帧所带的事件不会丢，因为后续帧会重复携带未确认的事件。客机按序号去重，同一事件只播一次。外观类事件超过有效期就丢弃（沿用 15 帧规则）。

### 3.5 大批新建

默认在一帧内完成，接受可能卡一帧。如果实测单帧应用超过阈值（建议 8ms，决定 E5），再加 Host 侧分摊：每帧新建成员数设上限，玩家和近处对象优先，其余顺延到后续帧。顺延的对象不在快照里，Host 下一帧还会认为它有差异，所以会自动补发，不需要额外账本。

### 3.6 Host 采集配套

**必须改（C9）**

1. **按根隔离失败**。现在普通采集在提交前逐根复核，任一根不再有效即整帧丢弃（`binary_entities.cpp:844-848`、`:865`）；写入器任一字段 `Fail` 也使整份采集失败。改为：
   - 实体、格子等对象根失败时，回卷该根已写内容，记录首因并按对象计数；
   - 该根在本帧标记为**沿用**，客机保留上次值；
   - Game、Room、Level、Run 等全局根以及成员集合本身失败时，仍丢整帧。
2. **“沿用”与“离开”分开编码**。沿用表示“成员仍在、本帧没有新值”，离开表示删除。不能用“本帧没有记录”同时表达两者，否则客机会把没采到的对象删掉再重建。同一根连续沿用超过阈值（建议 30 帧）时按离开处理还是继续沿用，由 Host 生命周期观察决定，不由采集失败推断。
3. **Body 不再转去等 joint**。`NeedsOrdinaryJoint` 的四处来源（`binary_entities.cpp:350-357`、`capture_exchange.cpp:171`、`entity_source.cpp:354`、`capture_executor.cpp:614`）改为：
   - 形态与普通采集确认的不一致：Body 省掉该成员，等下一帧普通 World 带上新形态；
   - Body 超过大小上限：这一拍不发 Body，只发 World。
4. **同一游戏帧保持**。一帧采集仍在同一个原生读取窗口内完成，客机不会看到不同游戏帧的状态拼在一起。

**性能方案的调整**（[性能方案](10-native-capture-performance.md)第 14 节已实施的部分）

- **J（Player 的 World 与 Body 共用读取来源）**：共用来源保留。“第二流或最终复核失败，整个普通采集候选作废”改为只作废该 Player 根；“奇数帧 Body 发现新结构走 `NeedsOrdinaryJoint`”按上面第 3 条改。
- **K（Body 从同帧普通采集批量克隆）**：保留。这里的“联合”指同一读取段内两条流共用来源，不是线上 joint；实施时改名，避免与线上 joint 混淆。

## 4. 客机应用

### 4.1 每帧统一协调

主线程 Manager 边界，World 安装点的步骤如下：

1. **选帧**：取后台已解码、已校验的最新 World，比它旧的未应用帧直接丢弃。
2. **删除**：本地存在、但新帧里没有的成员，排除本地显示特效后执行 Remove，回收池槽。
3. **身份核对**：成员键已有本地对象时，核对地址、实例代次和 type／variant／subtype。
   - 一致：转第 6 步写字段。
   - shape 前进，且该类型支持原生 Morph：原地 Morph（4.3 节）。
   - 其他不一致：删掉后重建。
4. **新建**：在 Init 隔离作用域里取池槽、执行原生 Init。池满时先回收，仍满就按优先级跳过：可缺的玩家泪弹最先跳过。计数后下一帧再试。
5. **清理 Init 附属实体**：Init 顺带生成的、不在快照里的实体，在本次应用内删除。
6. **写字段**：相对“该对象上次成功写入的值”求差，只写变化的字段。新建和重建的对象写全部字段。
   - 纯值：直接复制。
   - 指针、容器、资源：走现有具名原生写入器（13-client-apply 13.1 节）。
   - 资源未就绪：该对象延后，标记为待重写。
7. **挂引用**：Parent、Child、Target、Spawner 以及布局里的其他引用字段，按成员键解析；目标缺失的先挂起，目标出现后补挂。
8. **全局状态**：Game／Room／Level／显示标量（Q8、Q11、Q12）、方案 B 帧号、注入值照现有安装点写入。
9. **回放事件、ACK 记账**：只记已应用的帧号，供诊断和漂移检查使用，与网络 ACK 无关。

整个过程在一次调用内完成，不跨帧，也不读回核对。读回只在 E2E 诊断时抽样做（决定 E7）。

### 4.2 换房与换层

沿用 Q5／Q11 的原生转场：客机同步转场字段的当前值，做旧／新 surface 捕获和原生 Render。新房的 World 本身也走 4.1 节的协调，只是成员几乎全部替换。旧场景先删后建，不会出现两套场景同时占池槽的情况。

### 4.3 换形态

Host 侧的形态版本规则不变（`binary_entities.cpp:337`）。客机侧：

- **拾取物和 NPC**：游戏有原生 Morph，客机调用原生 Morph 原地变化，对象地址、引用、渲染排序和插值都不受影响。需要逆向 RE-11（第 8 节）。
- **其他类型，或 Morph 失败**：删掉重建，引用在第 7 步重新解析。

### 4.4 漂移

放行的显示代码可能改写已同步的字段。第 6 步只写“相对上次写入的变化”，所以漂移检查仍需保留：沿用现有的滚动漂移扫描，发现不一致就把该对象标记为待重写。

## 6. 失败处理

### 6.1 分类

| 情况 | 处理 | 是否请求基线 |
| --- | --- | --- |
| 解码或纯值校验失败（坏数据、越界、非有限值、未知布局） | 丢弃该帧并计数，按原因具名 | 同一原因连续 3 帧时请求 |
| 基线不在快照环内 | 丢弃，回 Resync | 是 |
| 目标对象不存活，或地址、实例代次变化 | 跳过该对象，标记重建 | 否 |
| 资源未就绪 | 该对象延后 | 否；资源确定缺失属于 Terminal，沿用现规则 |
| 池满 | 先删后建，仍满就按优先级跳过 | 否；同一对象连续 30 帧（约 1 秒）缺失时请求 |
| 原生调用异常（SEH）或写入器返回失败 | 删除该对象，下一帧重建；记录首因 | 同一对象连续 3 次时请求 |
| 引用目标缺失 | 挂起，目标出现后补挂 | 否 |
| 路由、房间、会话、生命周期变化 | 丢弃全部未应用帧和快照环，按现有生命周期 owner 退休 | 按现规则 |
| 漂移 | 标记该对象待重写 | 否 |
| Host 单个对象根采集失败 | 回卷该根，本帧标记沿用，计数 | 否；同一根连续 30 帧沿用时按 3.6 节第 2 条处理 |
| Host 全局根或成员集合采集失败 | 丢整帧，下一帧再采 | 连续 30 帧时 Host 发完整基线 |

以上阈值都是建议值，实施时集中放进 `wire.json` 预算，便于在第 15 步调整。

### 6.2 完整基线

完整基线就是 base=0 的普通帧，走 4.1 节同一路径，不再需要预先排空和冷建两套场景：旧对象在第 2 步删除，新对象在第 4 步建立。基线帧体积大，走可靠通道；首次准备每 Peer 1MiB／10 秒的预算不变。

### 6.3 放弃的保证

本修订明确放弃“写前失败绝不动当前画面”这条保证。可能出现的显示后果：

- 一帧内，部分对象已是新值，个别对象仍是旧值或暂时缺失；
- 引用暂时未挂上；
- 大批新建时卡一帧。

这些都应在后续帧收敛。崩溃安全不放宽：写入前核对存活状态、敏感字段走原生函数、SEH 兜底这三条硬约束都保留。

## 7. 实施前列出的失败方式

1. 快照环深度小于实际在途帧，Host 用的基线已被客机淘汰，造成持续 Resync。
2. ACK 提前到接收时发出，Host 基线前进，而客机原生侧某对象还停在更早的值。如果第 6 步按“快照差”而不是按“对象上次写入值”求差，该对象就永远不会被修正。
3. 被跳过的中间帧带着唯一一次出现的事件，后续帧不再携带，事件丢失。
4. 同一事件经多帧重复携带，客机去重失败，播放两次。
5. 删除后同帧重建时池槽还没真正释放，生成失败，或者覆盖了仍被引用的槽。
6. Init 附属实体清理误删了本地显示特效，或者漏删导致残留。
7. 原生 Morph 的副作用（音效、生成、随机数）没有被隔离。
8. 布局外的原生指针仍指向已删除对象，引发悬空访问。
9. 引用挂起表无界增长：目标永远不出现。
10. 资源延后的对象一直不显示：资源装载失败却没有转为 Terminal。
11. 单帧应用时间过长（大批新建、基线），拖慢客机帧率，Body 的 60Hz 被挤掉。
12. 成员键随帧携带增加了字节数，触及 World 带宽，频率反而下降。
13. Body 引用了还不认识的 World 成员，Body 内容被跳过，玩家姿态卡顿。
14. 漂移扫描预算不够，被本地代码改写的字段长期不修正。
15. 对象级失败阈值太宽，坏状态长时间显示；太窄则频繁触发完整基线。
16. 换房时旧场景对象的删除和转场 surface 捕获顺序颠倒，导致捕获到半个场景。
17. 退役借用账目后，某个原生回调仍持有已删除对象。
18. 新旧版本混连没有被握手拒绝。
19. 快照环与在途窗口占用的内存超出 Values 池。
20. 去掉读回后，写入器的静默失败（返回成功但未写入）不再被发现，只能靠漂移扫描兜底。
21. 采集侧把“沿用”和“离开”编成同一种形式，客机把没采到的对象当成删除，反复删除重建。
22. 单根失败只回卷了部分已写内容，残留的半个记录被编码发出。
23. 该根失败后，其他根引用它的字段仍按本帧采集写出，客机挂到了一个本帧沿用的旧对象上（应当可接受，但须核对引用解析不把沿用当缺失）。
24. 整体未变跳过（H3）漏掉了经指针到达的变化（Sprite 帧、容器内容），静止实体的动画停住。
25. Body 省掉形态变化的成员后，下一帧普通 World 迟迟不到，玩家相关实体显示停在旧形态。

26. 放松逐根复核和每次读取的检查（H5）后，读取到已释放对象而崩溃。
27. 可读区表（H1）与按根隔离相互作用：命中旧条目失败时整表作废重试，结果被误记为该根失败。

### 10.1 第 1—3 步当前进度

协议整数已切到 84，握手继续精确匹配版本。帧尾携带相对本流接收基线的成员目录增量，成员目录未变时省略，基线和无法用增量表达的换号使用随帧完整目录。沿用成员用分段内独立的有序 u16 编号序列表示。普通 World 与 Body 各自按 8 帧、64 KiB 正文计入窗口，500 ms 后释放窗口占用。可靠传输仍单独计费。线上 ACK 沿用原报文编号，发送时机移到完整解码、接管事件并保留纯值快照之后。应用成功值单独保存，事件重放从本地队列按序读取。Host 的实体、格子对象根已接入回卷和沿用，连续全局采集失败后在下一份有效普通快照上请求完整基线。

客机可在一次 Manager 调用内更新稳定复用的对象。普通纯值按上次应用的块差异选择，引用经过原生写入器。字符串、键值映射、集合、扁平无引用标量 vector，以及元素为 Vector／AfterImageFrame／EffectTrailNode 的 deque 已接入原位变长处理，重分配后重新定位元素。稳定对象路径取消了发布读回，保留滚动漂移检查。

可靠资源目录晚于普通帧采集时，Host 按 Peer 已收到的资源前缀组帧，沿用受影响对象的旧值并延后尚无值的新根。后续增量以该 Peer 实际收到的块求差，目录前缀推进时也能补发同一采集修订。资源目录到达即排预载，本地物化未完成时沿用已有对象的值，或延后尚未创建且可隔离的新根。冷基线仍先取得完整资源目录。目录和成员同时变化且旧引用无法在当前目录解析时，仍有等待路径。

第 2 步已接入普通 World、Body 和完整基线。单次 Manager 调用内完成应用。同实例仅在上一批确实写过该记录时按块求差，重建、缺席后补写和完整基线仍写全量。值向量、带原生 EntityPtr 的 deque、绘制节点链表可在原承载上变长，写元素前重新定位。独占向量需要换承载时，在写段构造并接入新的原生容器，再写元素。Shared holder／Weapon 槽的重建也移到写段，沿用原生构造、引用和析构入口。由其他原生 owner 提供的图层等字段仍使用现有具名写入器。

### 10.3 第 4 步对象失败、阈值与漂移

World、Body 和完整基线共用单根拒绝路径。构造、Init、字段定位、容器和具名写入器失败时记录成员键、实例与首因。已开始写入的对象先从各发布批次拆边和附件，再摘表、释放原生 owner；其余成员继续同帧应用。后续帧重建缺席成员。已确认无法判明归属的写入前缀和共享原生承载异常仍使用场景级安全恢复。玩家缺席时，其专属道具提示按消逝的外观事件消费，因为 J273 多人 HUD 对无玩家的查询返回无效槽号。

`wire.json` 集中设置同一成员的原生失败阈值 **3 次**、同一成员连续池满阈值 **30 帧**。连续计数独立于接收 ACK，成功应用、成员离开或换形态会结束该计数。达到阈值的应用回执先完成本帧，再由接收线程请求基线，当前可用画面继续显示。后台坏帧沿用同一原因连续 3 帧的阈值，资源暂缺和实例过期不累加原生写入失败。

正式发布只查 owner 和已执行的结构步骤。滚动漂移扫描把不一致的记录标成待重写，同一实例在下一份适用帧写全该根。E2E 编译保留有界发布读回抽样和 `binary-object-write` 故障注入点，供第 15 步核对其余成员推进和单根重建。

### 10.5 客机按变化量安装：静止记录（2026-11-17，用户要求实施）

起因：布局 84 第 3 轮 300 静止泪弹实测，客机每份 World 主线程 44ms、渲染 20.8 FPS。每份 World 描述约 8.97 万条指令，实际写入只有约 40KB；第 2 步的块差分只省掉了纯值写入，描述、排序、遍历和委托写入器仍按全部状态执行。

**判定**：满足以下全部条件的记录称为静止记录，本批不为它生成纯值叶和可跳过的委托指令：

1. World 流的 Entity 或 Grid 记录，非事件，记录 base 非 0；
2. 对象已存在且本批借用（同一原生实例），无对象失败；
3. 上一份已发布索引按同路由、同应用基线找到同一实例的记录，且未被漂移标记待重写；
4. 相对应用基线的值、结构、依赖块掩码全为 0；
5. 该记录的全部原生暂存字段都是沿用的旧承载，且本批不改值、不变长、不新建；
6. 不在本批的轮转刷新范围内：按记录号加 World 目标版本对 32 取余为 0 的记录照常描述，使每个静止记录约每 32 份 World 进入一次漂移扫描和委托写入器。

**静止记录仍保留**：容器附件指令（沿用承载的保管转交依赖它）、实体引用叶（退休拆边依赖它）、到期帧换算叶（剩余帧随展示帧变化）、引用型委托（BorrowedEntity／BorrowedPlayer）以及分类表列为必须保留的委托（FXCount、Time 等）。可跳过的委托只限 Sprite 文件、动画、图层、图像、配置、文本、门显示位等由原生对象自行持有、已提交后撤销不回写的类别。

**实施前列出的失败方式**：

1. 块掩码相对的是网络基线而非对象上次写入值，静止判定把从未写入的值当作已写，对象停在旧值。条件 3 要求已发布索引的版本等于本批应用基线，与第 2 步纯值跳过同一前提。
2. 静止记录缺少容器附件指令，旧批次排空时摘掉仍挂在活对象上的容器，对象读到已释放内存。保留附件指令。
3. 引用目标退休时，最新安装器没有静止记录的引用指令，拆边漏掉，留下悬空指针。保留实体引用叶和引用型委托。
4. 到期帧被跳过，Effect 剩余帧不再随展示帧更新。保留到期帧换算叶。
5. 委托写入器写入的值被本地显示代码改写（漂移），静止记录长期不进入扫描。轮转刷新兜底，代价是漂移最长约 32 份 World 才修正。
6. 新建、重建、Morph、基线、缺席后补写的对象被误判为静止。条件 2、3 要求同一实例且上一份已写，Morph 换形态后身份不同。
7. 全局记录（Game／Room／Level／显示描述）被判静止，显示描述索引查不到字段而抛异常。只放行 Entity 和 Grid。
8. Body 流或 Player 记录被判静止，Body 引用补挂依赖的指令缺失。只放行 World 流，Player 不在放行域。
9. 计数器口径变化：`world_write_operations`、`native_operations` 下降不代表写入变少，新增 `quiet_records` 计每批静止记录数。
10. 上一批该对象按对象隔离失败、只写了一部分，下一批因块掩码为 0 被判静止，对象长期停在半写状态。发布索引前把失败对象的记录标为待重写；这同时补上第 2 步未变块跳过的同一缺口。

运行验证归第 15 步，测试按用户要求由 Sonnet 子智能体执行。

### 10.6 客机快速路径：成员写程序、整批快速帧与吸收（2026-11-17，用户要求实施一期和二期）

起因：10.5 实施后 r5 实测 World 安装 26.4ms、23.4Hz，仍未达 29Hz。剩余大头是原生写段 14ms、主线程准备 5.8ms、原子描述 4.3ms，都与成员总数成正比。用户 2026-11-17 决定：先不管文档限制，纯值每帧全量写；具名写入器只在指纹变化时调用，并有 32 份 World 的强制刷新；用对象有效性加 SEH 代替逐页预检；一期和二期一起做。

**成员写程序**：场景持有一张按成员身份排序的写程序表，内容来自最近一份发布的 World。每条记录登记以下内容：

- 纯值叶：静态地址或晚绑定重定位信息、宽度、写法（整字节或 32 位掩码），以及 ABI 转换（原样、到期帧、服装下标、队列位、飞行、水面）；
- 记录内哪些值、哪些字段是“必须相等”的（委托、暂存容器内容、引用、结构节点）；
- 叶所在的私有承载链（容器 header 槽位和承载句柄），每次执行前逐个核“仍接在活对象上”；
- Time 计时器作为帧换算叶，按本批帧号重算。

只有 Leaf 实际生成的纯值指令才登记为纯值叶；动态容器元素叶、Map／Innate／Seeds、文本、具名字段一律按必须相等处理。

**一期：整批快速帧**。只有满足以下全部条件，World 票据才不经过 Prepare、Stage、描述和退休，直接在当前已发布的 World 安装器上执行写程序：

1. 只含 World 流；应用基线等于当前发布的 World 版本；当前发布者就是 `world` 槽的安装器，该安装器已发布、为单流 World、无失败、无不确定；
2. 计划级结构完全相同：对象表（身份、域、描述号）、World 拓扑、实体、玩家、控制组、锚点、格子、描述符、原生需求、暂存对象；
3. 非事件记录逐一同形（字段、叶、引用的数字形状一致，下标相同），结构与依赖块掩码为 0；事件记录只能追加在末尾，路径表只能在原表后追加；
4. 每条记录在写程序表中有同实例条目，必须相等的值和字段字节与上次写入的计划相同；Level 和 Descriptor 记录要求全部值相同；
5. 新计划所需资源都已在当前安装器的资源表中；显示目标同房、无转场，房型与图形注入不变；
6. 距上次非吸收事务不足 32 份 World（强制刷新）；
7. 全部对象仍是同一安装实例，全部承载仍接在活对象上（在写入前于同一 Manager 窗口内核验）。

任一条件不满足就记录首个原因，走原事务路径；判定发生在任何写入之前，不影响原路径。

快速帧执行顺序：先预约发布表；再捕获显示；然后全量写非显示纯值叶，重算到期帧和 Time，安装帧号；之后把安装器的当前计划换成新计划，并更新字段索引版本。接着依次安装显示、写显示叶、捕获、恢复 Boss、音频、事件回放，最后发布。提交时 `world` 槽保留原安装器和原票据，只把当前计划记成新计划。安装器换计划后，漂移扫描跳过纯值指令（每帧全量写已覆盖），只抽查委托字段。

**二期：吸收**。非强制刷新的事务中，满足条件 3、4、7（承载换成“本批沿用同一原生承载”）、且属于 Entity／Grid 的记录称为被吸收记录。它按静止记录处理：不生成纯值叶和可跳过的委托。它的纯值由新安装器在纯值段末尾执行写程序全量写入，晚绑定叶用新安装器重新定位。轮转刷新沿用 10.5 条件 6。根与承载的所有权仍按批次转交（借用加沿用），不迁到写程序表。写程序表在每次发布时刷新：被描述的记录用本批 Leaf 登记的新条目，被吸收或静止的记录沿用旧条目（同实例且承载沿用）。缺条目的记录不判静止，以便本批补登记。

**实施前列出的失败方式**：

1. 写程序的静态地址指向已被原生重新分配的容器，写进已释放内存。每次执行前核对象安装实例和承载链仍接在活对象上，失败就不走快速路径；动态容器元素叶不进写程序。
2. 具名写入器消费的字节变了，快速帧没有调用它，显示停在旧值。凡委托、暂存容器、引用和结构节点都按必须相等比较，字段级字节也比较。
3. 依赖帧号的具名值（Time）在快速帧不更新，计时器冻结。Time 按帧换算叶登记。到期帧照常重算。FXCount 和 Daily/Ascent 必须相等。
4. 快速帧触发房间构图重建，Backdrop Sprite 被原生重置而没有重装。条件 5 排除常见触发；`ClientDisplayInstall` 报告 `rebuilt` 时快速帧按写后失败处理（撤显并请求完整基线），代价是罕见的一次恢复。
5. 安装器换计划后，旧计划字节被释放，指令的借用值悬空。原票据仍由 `world` 槽持有，旧计划保持存活；漂移扫描不读纯值指令。
6. 发布表、`Control()`、Body 依赖和诊断仍指旧计划，控制视图消失。`world` 槽记录当前计划，`Plan()` 返回它；漂移扫描按安装器当前计划核目标。
7. 快速帧失败（SEH、显示失败）留下半写对象。写前失败回落原路径；写后失败按原协调器撤显并完整恢复，和原路径写后失败一致。
8. 被吸收记录的承载在新事务中没有沿用（内容变化或换承载），写程序仍按旧承载写。吸收要求每个登记承载在新事务中是同一原生句柄且标为沿用、不改值、不变长、不新建。
9. 写程序表缺条目（刚恢复、刚新建、上批静止）时把记录判为被吸收，纯值没人写。没有条目一律不吸收也不判静止。
10. 强制刷新缺失，具名字段的本地漂移永不修正。最多连续 31 份 World 不走非吸收事务；第 32 份强制走事务且不吸收。代价是约每秒一份慢帧。
11. 根标量首次写入没有快照，撤场无法还原菜单值。写程序登记根标量叶，执行前补快照。
12. 计数口径：新增 `fast_path_hits`、`fast_path_misses`、`absorbed_records`、`store_records`、`fast_write_leaves` 和阶段 `fast_check`、`fast_write`；快速帧不计入 `native_operations`。慢路径首因写在诊断页 `stream.binary.fast.miss.<原因>`。

二期与原计划的差异：原计划把被吸收成员的根和承载所有权从批次迁到写程序表。实施时保留按批次转交，因为渲染成员表、绘制顺序、房间名册和退休拆边都按批次维护，迁移所有权需要整体重写这些结构。目前的写法同样省掉被吸收成员的描述、指令和具名写入，但事务仍对全体成员做对象描述和暂存描述（主线程准备阶段与成员数成正比）。

**实施记录（2026-11-17，已构建，未实测）**：

- 写程序表 `ClientSceneMemberStore`（client_atomic_install.cpp）：由场景持有，传给 World 安装器。`Leaf`／`CaptureTime` 登记，发布时由 `RefreshStore` 刷新。
- 一期入口：
  - 场景 `FastEligible` 判条件 1、5、6 的场景侧部分，以及发布状态。
  - 安装器 `FastCheck` 判条件 1—5。
  - `FastInstall` 在写段入口只复查可变状态（发布者、写程序表、对象失败），再核条件 7。结构比较只在准备时对同一张不可变票据做一次。
- 二期：吸收在 `ClassifyQuiet` 中判定，在 `InstallNow` 纯值段末尾由 `RunAbsorbed` 写入。
- 补充的规则：
  - 含显示路径叶的记录不吸收，照常描述，因为吸收只走非显示写段。
  - 写程序表在用时，静止记录也要求有同实例、同形的条目，否则这一批照常描述并补登记。
  - 换过计划后，漂移扫描还跳过委托的 Time 字段：它的具名写入器记的是旧批帧号。
  - 失败方式 4 的 `rebuilt` 来自 `ClientDisplayInstall` 原有的 `capture_initial`，显示层未改。
  - SEH 写入是 `ClientAtomicFastWrite`。帧号由绑定的 `AdvancePublished` 安装，渲染钩子同时改看新计划。

### 10.7 Host 编码线程提速与 Body 60Hz（2026-11-17，用户同意，未实施）

**2026-11-18 注记**：用户已决定（规范第17节 L1—L8），[平铺记录设计](10-flat-record-encoding.md)取代下文 W1／W2，M1 的资源槽改由指针键缓存实现；B1、B2、M2 照做。客机的 10.5、10.6 只继续服务未迁移的全局根。

**起因**：10.6 实施后 r8 实测客机 World 安装 3.6ms、59FPS，但 World 仍为 22.8Hz，Body 也是 22.8Hz。用户要求 World 跟上 ordinary，Body 尽量达到 60Hz。

**r8 clear 段数据（30 秒）**：

| 位置 | 数值 | 说明 |
|---|---|---|
| Host 主线程 | ordinary 895 份，每份 12.1ms，其中实体采集 9.9ms；Body 采集 1790 次（约 60Hz） | 游戏仍 59FPS，不限频率 |
| 编码线程 | 处理 ordinary 686 份，每份建索引 14.3ms、编码 24.2ms，共 38.5ms；占用约 88% | 其余 ordinary 被替换，World 只有 22.8Hz |
| 单独 Body | 编码线程整轮只编出 54 份（ordinary 773 份） | 客机收到的 Body 是 ordinary 夹带的玩家 Body 记录，与 World 同频 |
| 主线程整根复用（H3） | `unchanged.checks=0`，复用槽 124 个 | 从未生效 |
| 主线程跨帧资源缓存（H4） | 每份 animation／config／file 各解析 300 次以上，跨帧命中接近 0；资源槽 123 个 | 键含实体身份，300 颗泪弹 × 3 类远超槽数 |

**原因**：

1. 编码器固定开销大：
   - 每根先对约 300 个采集单元做带路径比较的排序，再对每个字段二分查找（`CapturedBodySource`）；
   - 引用、资源解析线性扫描成员表和资源目录；
   - `Capture` 中查成员、查旧记录、查重复都是逐根线性查找（O(N²)）。
2. 单独 Body 要求编码线程最新 ordinary 正是主线程刚采的那份：
   - 取包时不满足就推迟（`capture_exchange.cpp` `Take`）；
   - 编码时不满足就丢弃（`host_publish.cpp` `Capture`）。

   编码线程总落后约一份，Body 不是被推迟就是被替换。
3. 编码线程串行，有两处会堵住 Body：
   - 一份 ordinary 编码 38ms，期间 Body 只能排队；
   - 编完后 ordinary 读票据一直持有到网络线程接走事件（`BinaryEntities::Background`）。持有期间 exchange 不出包，Body 也被堵住。
4. H3 要求编码线程已发布的上一份就是主线程上一份采集，编码线程跳份时条件永不成立；而且槽数不够。

**方案**（按顺序一次实施，B3 视 r9 实测再定）：

- **W1 编码线程按输入复用整根**。每个成员保留上一份已编码时的规范化采集输入：
  - 内容包括单元头（不含偏移、路径编号）、路径内容和值字节；
  - 引用和资源句柄换成解析出的身份（space/local/use）或资源句柄。

  本份输入与上一份逐字节相同时，复用旧记录，跳过建索引和编码，成员编号变化的引用照 `RetainRecord` 改写。比较的是完整字节，不用哈希。
  - 只用于 ordinary 的 World 实体和 Grid 根；
  - 以下几类照常编码：Player（layout 197）、事件记录、沿用记录、主线程 H3 命中记录，以及换局或换 scope 后的第一份；
  - 新输入串先暂存，与 `s.ordinary=out` 同时提交。
- **B1 Body 不再要求最新 ordinary**。编码线程现有 ordinary 与 Body 同 scope、同代号，且该玩家 World 记录的拓扑、绑定与 Body 一致，就编码。不一致或引用未入表时，软跳过这一拍并记原因，不抛异常。取包时不再为等 ordinary 推迟 Body。
- **B2 ordinary 编码完成即释放读票据**。只保留一条回执（会话、局、事件水位），网络线程接走后再交给主线程。主线程回收事件副本的时机不变。
- **W2 降低编码器固定开销**：
  - 采集单元已有序时不排序：先 O(n) 检查，乱序才排；
  - 查找用顺序游标，失败时退回二分；
  - 解析器用"成员身份 → 编号""资源句柄 → 目录位置"两张直接表；
  - `Capture` 中三处逐根线性查找改为按编号或身份的索引。
- **M1 主线程复用槽扩容**：根复用槽 ≥512、资源槽 ≥1024，`shared_value_bytes` 预算相应增加约 5MB（用户已同意）。H3 的基准条件不改，W1 后编码线程不再跳份，它就自然成立。
- **M2 诊断计数**：
  - 编码线程 `reused_roots`、`input_mismatch`、比较耗时；
  - Body 丢弃原因：基准不符、拓扑不符、引用未入表；
  - 读票据持有时长；
  - H3 未命中原因：基准不符、槽冲突、输入不同。
- **B3（视 r9 实测）客机 Body 快速帧**：仿照 World 写程序，同形 Body 不经准备直接写，并允许同一帧装 World 和 Body。只有 r9 显示客机侧成为 Body 瓶颈时才做。

**实施前列出的失败方式**：

1. 输入串没覆盖编码实际用到的上下文（资源目录前缀、FrameContext 等），复用了过期正文。逐项核对编码依赖，依赖输入串以外数据的布局不进复用。
2. 引用目标身份相同，但成员编号被回收后改指别人。沿用 `RetainRecord` 的 SameReference 检查。
3. `Capture` 中途抛错或被撤销，暂存的输入串却已提交，下一份拿错误基准比较。输入串只与 `s.ordinary` 同时提交。
4. 主线程 H3 命中的记录没有采集单元，覆盖了该成员的输入串。H3 命中时不更新输入串。
5. 换局、换 scope、Reset 或 Invalidate 时没清空输入串。
6. 排序跳过的有序判断写错，查找报 `missing_captured_value`。
7. 扩容后预算不足，预留失败。原逻辑允许不开缓存，只退化不出错。
8. Body 基于较旧 ordinary 编码，引用了还没进成员表的实体，解析失败抛异常并计为 worker 故障。改成软跳过这一拍并记原因。
9. 客机收到的 Body 所依赖的 World 尚未安装，报 `client_plan_world_context_missing`。r7 卡死时出现过此错，随后客机本地恢复并断线。客机对这种 Body 改为跳过或等最新一拍，不触发恢复；同时查清 r7。
10. 提前释放读票据后，主线程过早回收事件副本，事件丢失。回收仍以网络线程接走后的回执为准，释放的只是 exchange 读位。
11. 玩家换形态或换拓扑的那一拍，Body 与 World 不一致。沿用拓扑、绑定比对，不一致就跳过。
12. Body 在途窗口 8 份在 60Hz 下只覆盖约 133ms，延迟线路往返更长时 Body 被窗口限住。先在 r9 的 delay 段观察，再决定是否给 Body 单独加大窗口。

**预期与验收**（r9 三段对比 r8，以下数值为估算，未实测）：
- 编码线程每份 ordinary 降到 20ms 以下（W1 估算 5—8ms）；
- clear 段 World 约 29—30Hz，Body 50—60Hz，客机仍 59FPS；
- loss、delay 段 Body 不明显低于 clear 段；
- 主线程每份 ordinary 约 4ms。

## 11. 第 15 步验收调整

目标指标：

- 稳态 World 30Hz、Body 60Hz，不变；
- 稳态单帧应用 p95≤2ms、p99≤4ms，不变；
- 大批新建与基线帧的单帧耗时单独统计，阈值由 E5 决定。

新增或改写的覆盖：

| 场景 | 必须观察的结果 |
| --- | --- |
| 300 静止泪弹，同房四身体 | World ≥29Hz；从接收到 ACK、从接收到应用分别统计 |
| 进房一次生成 300 颗泪弹 | 单帧耗时有记录；池不足时只缺可缺泪弹，不断线；后续帧补齐 |
| World 下行随机丢包 10%，以及注入 60ms 延迟 | 频率按窗口推算达标；无持续 Resync |
| 道具底座、宝箱、NPC 换形态 | Morph 类型原地变化、地址不变；其他类型重建；引用正确 |
| 引用目标晚到 | 先挂起，到达后补挂，挂起表不残留 |
| 事件随被跳过的帧到达 | 每个事件只播一次，不丢 |
| 坏数据注入 | 只丢该帧；连续时请求基线；不崩溃 |
| 原生写入器失败注入 | 只影响该对象；达到阈值请求基线 |
| 换房、换层、断线重连、新旧版本混连 | 沿用现有覆盖；混连握手失败 |
| 漂移 | 本地改写的同步字段在一轮扫描内被修正 |
| Host 单根采集失败注入 | 只有该对象本帧沿用，其余对象照常更新；客机不删除该对象 |
| 静止实体整体未变跳过 | Host 采集耗时下降；实体发生任何变化（下落、动画帧、颜色）时下一帧即被采到 |
| 300 静止泪弹 Host 采集 | 记录每帧普通采集耗时，与 isaac-lan 的 4.67ms 对照（版本、种子不同，只作参照） |

## 12. 未证实与风险

- 1.2 节的往返时间划分来自窗口公式和 100 敌怪 M0 读数，300 泪弹的分段没有实测；2026-11-17 用户决定不做修订前补读数，改动效果以修订后第 15 步实测为准。
- 一帧内完成大批新建的耗时没有读数。isaac-lan 的 6.9ms 是 J460 加 Lua setter 的读数，不能直接套用。
- 随帧携带成员键会增加字节数，增加量没有估算。
- RE-11 的静态可用范围见 10.4 节。商店、分叉底座和 Delirium 保留重建，已接入的原地 Morph 仍待第 15 步观察实际副作用。
- 退役借用账目以后，原生回调持有已删除对象的风险只能靠第 15 步覆盖发现。
- 本修订影响面大，按第 10 节分步实施期间会有新旧路径并存。并存期间的版本和开关管理在实施第 1 步时定。
