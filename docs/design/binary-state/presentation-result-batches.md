## 1. 已确定的方案B

采用**统一批次合同、按实际owner管理、按依赖共同提交**。显示结果属于同一二进制状态模型，继续使用现有world／body两条序列，不增加独立Presentation传输／确认序列，也不增加模拟tick。

- 批次内部按Room、身体HUD、History、StatHUD、地图、屏幕／转场等实际owner分组。分组规定数据所有权、变化比较和依赖范围，不授权Client收到一组就部分安装一个不完整目标。
- 必须共同提交的world内容保持共同提交：Room几何、描述拓扑、L2、地图焦点、相关资源及必要显示批次不能错配。身体结果沿用成员／资源及P0—P6绘制拓扑的窄依赖，不笼统依赖完整地图或所有显示资源。
- 每个具名adapter在正式布局中声明所属序列、必要依赖和共同提交范围。需要与某个body状态严格一致的结果随该body目标或其明确配对依赖消费；不能把world结构／HUD缓存随意夹入body，或借分组扩大body对整个world版本的依赖。
- Authority不等待显示批次、资源传送或任何Client ACK；各Peer的接收和准备进度互不形成全员等待。
- baseline与增量继续使用同一种格式，baseline的base=0；变化比较使用规范自有缓冲的memcmp，不计算哈希。资源、布局号、精确字段宽度和预算由第8／9步纳入唯一源后生成，本文的语义目录不是可接受报文。

## 2. History、StatHUD和参与者的含义

HistoryHUD是已获得道具／熔炼饰品的图标记录栏。原生单个HistoryHUD有0、1两个身体显示槽；本地REPENTOGON Wiki的`HistoryHUD.GetPlayer`明确槽1主要用于Jacob／Esau这类twins。槽号不是Peer编号，两个槽也不是整个C/S系统的参与者上限。最终列表保留有序完整i32 visual_id及实际Image；不恢复Player原始获得历史作为正式下行输入。

StatHUD是速度、射速、伤害、射程、弹速、幸运及房间概率等数字栏。当前已核原生结构有两组身体缓存；每组绑定实际身体，不能解释为Peer1／Peer2。同步0—8当前可绘行的value／delta／countdown及必要显示资格，previous／threshold留Host，官方星象房行保留。

参与者、控制组、身体、原生roster位置、HUD实例和显示列分别表达。一个参与者只有一份canonical输入意图；多个身体按Host已提交归属及原生角色资格消费。四参与者不等于四身体，也不要求把原生两个显示槽直接扩成四个Peer槽。

## 3. 各端详细HUD默认跟随本端控制组

这是用户采纳的产品行为，适用于Listen Server房主和所有远端Client：

| 本端控制组 | 本端详细HUD默认主体 | 角色选择规则 |
| --- | --- | --- |
| 普通单身体角色 | 自己的当前角色 | 使用该组实际显示身体和已确认结果，不取全局roster第0项代替 |
| Jacob／Esau等双角色 | 自己组内两个角色的必要显示 | 保留各身体独立心量／装备以及双角色History、Stat等原生显示语义，不合并数值或只留根 |
| Forgotten／Soul、Flip及其他关联形态 | 自己组内实际应显示的当前身体及必要关联身体 | 显示资格由Host角色结果及关系确定；备份不因存在就全部可见，也不从body_role名称单独猜选择 |
| 其他参与者 | 公共多人HUD中的心量、主动等必要内容 | 场景角色按其实际绘制资格正常显示，公共HUD不因本端详细主体变化而丢人 |

HistoryHUD、StatHUD的默认主体跟随本端控制组；各组的详细显示结果仍由Host提供。视口、HUDOffset、显示偏好和排版由各端按同版本UI合同处理，world隐藏／curse／资格限制继续生效。本文不新增切换他人详细HUD或观战操作；死亡、复活、换形时仍保持本端组身份，按其当前合法显示结果选择身体，不静默回退为房主。

本端控制组从已确认会话分配与participant／group关系解析，ordinal只用于会话内查找，不能替代身体Key/use/shape。显示焦点变化不改原生PlayerIndex、roster顺序、ControllerIndex或输入归属，不调用原版Online本地性判断。Client角色仍不绑定原生设备以取得“本地玩家”外观。

Host应为全部当前参与者提供公共多人HUD，以及各组个人详细HUD所需的合法最终结果来源。只复制Host当前HistoryHUD两槽／StatHUD两组不足以完成此合同；原生单个对象的容量不作为系统支持范围。是否共享同一不可变结果、采用多个显示承载实例或自有固定adapter，由具体来源与生命周期决定，不能复用一个可变槽造成跨身体污染。

这些结果优先取正常Host已完成的生产／消费；可证明由已下行事实唯一确定的部分可以用已核纯值投影。各组尚无合法结果来源时继续记具体Gap，不为凑齐四组额外调用getter、Lua、HUD Update、History／Stat Recompute、概率／分数重算或随机生产器。各组完整来源仍是实现工作，不能因主体策略定稿就标记完成。

## 4. 生产者、subject与应用owner分别登记

例如心格由Host PlayerHUD正常生产，subject是某个身体，由Client身体HUD adapter安装；不因描述Player就恢复Player玩法生产字段。Host原生地址只作主线程当前代次临时关联，不进入网络身份。

| 内容 | 数据owner与subject | 依赖／消费归属 |
| --- | --- | --- |
| 心格、主动／饰品／Pocket、库存／crafting图像 | Presentation身体HUD组；真实身体及具体HUD实例／用途 | 身体Key/use/shape、显示归组、所需状态与资源；公共HUD和详细HUD可引用同一合法不可变结果 |
| History | Presentation History显示owner；组内实际有序身体选择及各自图像列 | 保留visual_id、实际Image和顺序；每组详细主体独立，不按库存count重排 |
| StatHUD | Presentation属性栏owner；组内实际身体及行选择 | value／delta／countdown、合并概率方式、world资格与资源；本地偏好不替代Host资格 |
| 地图资源、徽标、挑战32焦点、最终震动 | Presentation地图组；楼层／维度及两配置的具体用途 | 复用L0—L3、300—303和资源唯一owner；Host展开输入不决定他端查看 |
| 水、光、波纹、世界强制焦点 | 沿用Room owner | Presentation只引用；不新建重复writer或另一份同值负载 |
| 消息、fortune、Prompt、屏幕效果、转场、Nightmare、死亡显示 | 各具名显示实例及其显示代次 | 实际资源、最终有序贡献、坐标语义及相关结构事务；世界内容与个人界面分开 |
| Pickup／Familiar随机显示覆盖 | Presentation具名实体用途；当前实体及贡献 | 真实状态依赖、pass及调用身份；只用正常已产生资格／alpha，不传随机流 |
| 音频 | 逻辑voice用途／实例／代次 | 持续状态与Start／Stop等事件分别维护；采用Options前最终参数，生产混音树不重复下发 |

每项结果目录至少明确：具名producer／正常来源点、数据owner、subject及use/shape、固定用途／结果布局、有效条件、失效条件、所属序列／必要依赖、Client消费adapter。已有唯一owner的字段、时钟与资源引用复用，不能为“批次完整”重复发送同一数据。

## 5. 批次身份与缓存有效期

以下是语义字段要求，整数宽度／完整封装由第9步同源登记；布局版本、来源修订和传输版本不混用：

| 层次 | 必须表达的归属 |
| --- | --- |
| 批次公共上下文 | session／run、实际world／房间实例、Host来源状态修订、显示批次号、member／resource epoch及必要绘制拓扑修订 |
| 本批显示时钟 | 实际采用的GameFrame、D0 Manager相位与paused；复用唯一字段，subframe按既有规则派生 |
| 结果组 | 数据owner／显示代次、subject/use/shape、具体用途，以及确切的身体／地图／资源依赖和共同提交范围 |
| 缓存来源与有效性 | 初次生产来源修订、仍成立的依赖和失效条件、当前引用的不可变内容；不能只记最后一个数值 |

Host来源状态修订先于逐Peer发布存在；各Peer的base／target_version由发布端映射，不能把采集缓存身份直接绑成某一个Peer的target_version。GameFrame相同不足以证明两个结果属于同一状态／资源批次。

已核正常生产／消费点立即复制瞬态结果到自有缓冲。封存前确认来源及必要关系在对应窗口内一致，随后网络／后台只持自有不可变值和内容。不能在普通后态窗口用当前对象值替代早先绘制栈结果，也不能因为字段数值恰好相同而给旧结果补一个新来源修订。

持久文字图像、有序列表等缓存，可在其来源资格及所有依赖仍成立时由后续批次显式引用；无需每帧重制图像。每次调用才形成的随机alpha、临时变换和颜色栈结果只属于其明确贡献，不自动沿用到下一次状态。内容memcmp不变与来源有效是两回事；批次身份与内容变化分别管理，避免仅批次号递增就重发全部资源。

切房／换层、维度／配置替换、Hourglass／Ascent／合法Continue、身体use/shape或控制绑定变化、显示owner／用途退休、资源内容替换，都按实际影响撤销依赖和旧候选。旧strong或纯值快照仍在内存，不代表它可归给新身体或新房间；在途／已提交借用退出后再回收资源。

## 6. 明确贡献身份，保留同帧多次结果

贡献由**subject/use/shape＋固定用途＋pass＋分支／层／主叠加身份＋本批贡献身份**定位。Host在正常生产／消费时封存有序贡献；同一对象同帧被多层、多pass或递归使用时分别保留。批内序号只在明确的贡献列表／调用上下文中有意义，不能是Client的本地访问计数。

| 场景 | 必须保留的差异 |
| --- | --- |
| versus同一个肖像Sprite被不同layer使用 | 各layer实际临时位置／旋转／缩放／完整颜色及主叠加姿态，不能只采函数返回后的最后Sprite |
| Nightmare同一个progress Sprite逐项SetFrame | 实际各次路线／指示器／条件内容贡献及顺序；最终贡献承接后不再重复发送生产数组／Scene帧／Dogma生产体 |
| hallucination snapshot多次叠加 | 各用途的内容、alpha／颜色及有序位置，不合并成“最后alpha” |
| Pickup／Familiar多个pass或递归 | 每次具体资格及正常已产生alpha，不按Client renderEL或第N次访问分配Host样本 |

Client按Host声明的贡献及固定消费合同定位结果。额外本地调用没有对应合法结果时报告具名Gap，不能挪用相邻贡献。重复绘制已提交画面可复用同一不可变批次，不再次抽取、推进动画事件或累加生产游标。

贡献列表的元素类型、字段、顺序语义和容量都在唯一布局源固定登记，采用具名有界adapter；不引入任意函数／参数字典、GPU命令流或全量getter查询接口。各用途局部坐标／视口锚定语义继续核定，不能将Host绝对屏幕像素当作跨分辨率通用坐标。

## 7. 缺结果处理规则保持不变

| 情况 | 语义与处理 |
| --- | --- |
| Host确认隐藏、Null、无随机覆盖或合法空集合 | 编码对应固定布局的合法状态；无效分支不读旧payload |
| 必要用途未正常产生、来源未核或无法覆盖 | 具名来源Gap；不填false／0，不伪装隐藏、Null或空列表 |
| Host结果已确定，Client资源尚未准备 | 对应依赖Wait；保持原目标资源身份，不改Null |
| 读取失败、生命周期／归属冲突或候选越界 | 相关候选失败，按所属完整目标拒绝／恢复，不留下半条记录 |

**任何必要结果／资源／结构依赖未完整时，不安装该不完整目标、不回复其AppliedAck。** 可以继续展示仍合法的旧完整目标；不能一边显示新world，一边把旧身体／房间结果当成新目标补齐。原world／use退休后不能继续贴旧批次。接收、解码、资源就绪和原生应用成功仍分别处理。

仅保留有界的构建中／候选／已提交缓冲与必要引用，积压淘汰按所属序列恢复；不通过缓存无限历史等待凑批，也不让Authority等待。分组不改变这些规则，个人UI偏好不关闭必需来源检查。

Host视口没有覆盖、但Client可能看到的必要用途是明确的来源覆盖问题。已核确定性用途可由合法纯值投影承接；随机用途仍须落实具体来源，不能额外Render／抽取或用缺席推导“应当无覆盖”。同理，Host个人关闭HUD／画质不能抹掉其他Peer需要的world资格及个人详细HUD结果。
