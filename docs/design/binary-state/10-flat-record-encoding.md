## 1. 问题与依据

### 1.1 数据

300 泪弹 r8 clear 段（30 秒；见[最终一致修订 10.7](eventual-consistency-revision.md#107-host-编码线程提速与-body-60hz2026-11-17用户同意未实施)）：

| 位置 | 每份 ordinary | 折算每颗泪弹（推算，按 300 根平摊） |
|---|---:|---:|
| Host 主线程实体采集 | 9.9ms（整份 12.1ms） | 约 33µs |
| 编码线程建索引 | 14.3ms | 约 48µs |
| 编码线程编码 | 24.2ms | 约 81µs |

编码线程占用约 88%，所以 World 只有 22.8Hz；Body 夹在 ordinary 里，频率也一样。

run128（四身体混合负载，2026-11-16 计数）：每份 ordinary 约 3.3 万次小复制，平均每次约 7.7 字节；约 3.5 万次 bound write。

### 1.2 成本结构

现在一份 ordinary 要经过三道工序：

1. **主线程写单元**：每个字段写一个 `CaptureCell`（`capture_values.h:10`），包含 path、offset、bytes、count、layout、field、aux、depth、kind、scalar，共 24 字节元数据，另有路径表。每次读取都要经过 `Good()` 等检查。
2. **编码线程建索引**：`CapturedBodySource` 构造时，按路径比较把每根的单元排序、去重（`capture_values.cpp:532`）。
3. **编码线程编码**：生成的 codec 按布局逐字段取值，每个字段用 `lower_bound` 加路径比较查回单元（`capture_values.cpp:554`），再逐字段校验，然后写成线格式。

第 2、3 步的主要开销来自**中间格式要自带描述**：采集端按 handler 的顺序写，编码端按布局的顺序取，两边没有约定顺序，只能先排序再查找。W1（输入未变时整根复用）只在对象静止时有效，泪弹在动时帮不上忙。

## 2. 思路

由同一个生成器为每个类型同时生成**采集程序**和**应用程序**，字段位置在生成期就定死，不写进线上：

- Host 主线程按复制段把根对象内存整段复制到自有缓冲区，然后原位补丁指针和换算字段，得到这个根的**平铺记录**。采集和编码在这一步合成一步。
- 编码线程只做按字段比较（向量化逐字节比较，再经字节→字段号表定位变化字段，3.8.1）、组装记录、整消息 zstd，不再排序、查找或逐字段编码。
- 线上不再有块：记录只带变化字段的集合与这些字段的值（L8）。
- 客机按同一张表定位字段，把变化字段扩展到写入组，按写段写回活对象，再执行补丁表里的原生操作。

这其实回到了规范第17节“状态形态”原本的要求：“相邻的已知状态字段合并成一次复制，Host 先复制到自有缓冲区，再用 memcmp 判断变化”。现有实现偏离成了逐字段写单元，本方案把它改回来。

## 3. 设计

### 3.1 类型描述

生成器为每个进入同步的类型生成一份描述：

```
类型描述 = 定长镜像 + 补丁表 + 间接子项
  定长镜像：大小、复制段 (原生偏移, 镜像偏移, 长度)
  补丁表：  按镜像偏移升序的槽位，每槽一个类别（3.3）
  间接子项：补丁表中“容器／owner／Sprite 子数组”类槽位指向的元素类型描述

扁平化(T) = 按复制段复制 T 的定长镜像
          → 按补丁表顺序处理每个槽
          → 遇到间接子项时，把子项镜像追加到附加区，并对每个子项递归扁平化
```

**按值嵌套的类型**（Vector、ColorMod、ANM2……）字节就在父对象内存里，它的定长镜像是父镜像的一部分，复制段可以跨类型边界合并。**容器**（vector 等）的定长镜像只有头部，元素是间接子项。两者走同一套递归，唯一区别是字节在父对象内存里就原位复制，在别处就追加到附加区。

`ANM2[13]`、`ANM2[4]` 这类定长数组按值嵌套处理。

**合成字段**（布局源 `synthetic_fields`）没有原生偏移，例如 Player 的控制组、参与者，以及 Grid Sprite 的部分选择值。生成器把它们排在该类型复制段之后，作为定长槽，由 ⑧ 换算 handler 写入。首批范围内只有 Player（13 个）和 Grid（8 个）有合成字段，实体子类没有。

### 3.2 字段与记录结构（L8）

L8 取消块：差分、上线、客机写入判断都以字段为单位。布局源的 `blocks[]`、块号、32 块上限、预留空块和 Sprite 的 `#0/#1/#2` 投影一并退役。

#### 3.2.1 字段表

生成器为每个布局生成一张**字段表**，按字段序号排列，每项为：

```
字段 = 序号 u16、镜像偏移、镜像长度、流（world／body）、类别（复制／3.3 节补丁类别）、写入组号、单字段校验
```

- **字段的粒度**：展开后的最小布局源字段。
  - 标量、合成字段各为一个字段。
  - 按值嵌套的类型（Vector、ColorMod、ANM2、AnimationState 等）展开为其自身字段；`ANM2[13]` 这类定长数组按元素展开。
  - 引用槽、资源槽各为一个字段。
  - **容器、长字符串、⑤ owner／Weapon 槽各为一个字段**：主区里的头模板（3.4）加上它在附加区的整段，作为一个整体比较和上线。首版不做容器内按元素差分，见 3.5。
- **字节→字段号表**：每个布局另生成一张表，主区每个字节对应一个 u16 字段号，不属于任何字段的字节（清零字节、填充）记 `0xFFFF`。所有成员共用，泪弹约 2—4KB。用于从差异位图直接定位变化字段（3.8.1）。
- **序号**：父类型字段在前，同一类型内按镜像偏移升序。握手时版本必须完全一致，所以序号不需要跨版本稳定；原生偏移仍不上线。
- **规模（按布局源粗算，容器计 1 个字段）**：Effect 约 117，Pickup／NPC 约 205，Tear 约 250，Player 约 888，ANM2 45。
- **流**：每个字段固定属于 world 或 body。迁移时继承原块的 `sequence`；`world-or-player-body` 由生成器按具体布局落定，Player 的运动、外观和 Sprite 字段仍走 Body。生成期检查：每个字段恰好属于一个流。

#### 3.2.2 写入组

客机写原生对象时，有些字段必须一起写；原来这层约束隐含在块里。L8 后改由**写入组**表达，每个字段恰好属于一个写入组，默认自成一组。生成器按下列规则自动合并：

1. 同一个 ⑧ 换算或具名写入器读写的全部字段；
2. 同一个 ③ 资源 owner 处理的字段，例如 ANM2 的 file_name 与 loaded、AnimationState 的动画号与帧；
3. ④ 容器字段自身（头模板加附加段），以及布局源 `count_groups` 关联的各容器；
4. ⑤ owner 槽及其子记录；
5. 布局源 `conversions`、`validators` 中跨字段引用的字段。

自动规则推不出的，在布局源里用 `write_groups` 手工声明。生成期检查：任何 handler 的输入、输出字段不在同一写入组时，生成失败。

线上的粒度和客机写入的粒度彼此独立：客机先把收到的字段覆盖进完整镜像，再按写入组从镜像整组写入（3.9）。

#### 3.2.3 记录结构

```
[记录头 9B][字段集合][值区：变化字段的镜像字节，按序号升序拼接][附加区：变化的容器类字段的整段，按序号升序]
```

- **记录头**：`member u16 | layout u16 | record_bytes u32 | set_mode u8`。取消 `block_mask u32`，撤销 2026-11-11“保留 u32 块掩码和 12B 记录头”的决定（L8）。
- **字段集合**：编码器对每条记录计算下面两种编码，取较短的；长度相同时取位图。
  - `set_mode=0`，**两级位图**：按序号每 16 个字段为一组，先写顶层位图，每组 1 位，共 ⌈组数/8⌉ 字节；再对每个置位的组依次写一个 u16 组内位图。
  - `set_mode=1`，**序号差列表**：先写变长整数（LEB128）表示的个数，再依次写首个序号和后续各项的“序号减前一序号减 1”，同样用变长整数。
  - `set_mode=2`，**全部字段**：不带集合，值区包含该流的全部字段。用于 base=0、新建、换身份等情况。
  - 集合只列出本流的字段；序号必须严格递增，并小于该布局的字段数。
- **值区**：每个变化字段写它在镜像中的定长字节；容器类字段写主区里的头模板。
- **附加区**：只含本记录列出的容器类字段的附加段（3.5）。
- **规模（推算）**：运动中的泪弹每帧约变 6—10 个字段，字段集合约 7—10 字节。原来 E1 块要发 44 字节，改后只发 position、velocity 共 16 字节。

#### 3.2.4 镜像、差分与压缩

- **镜像**：Host、客机都在内存里为每个成员保存一份完整镜像，包括主区全部字节和附加区。镜像的大小和形状只取决于布局号（附加区还取决于各容器的计数）。主区仍按 L1 的紧凑镜像排列，按原生偏移顺序，不需要按块重排。
- **差分**：Host 按字段比较本帧与上一帧，用每字段版本戳决定对每个 Peer 发哪些字段（3.8）。基线规则仍是[最终一致修订](eventual-consistency-revision.md)第 3 节的 E1、E2：每条流相对该 Peer 已 ACK 的快照做增量。
- **压缩**：沿用整消息独立 zstd（[第9步 zstd](9-world-body-zstd.md)），不加异或差分。

### 3.4 容器头模板

生成器按容器类型套用头模板，不逐字段手写。头部原有的指针字和分配细节字要么改写为核对用的元数据，要么清零；**客机一律不按字节写回容器头**。

| 容器（布局源记载的头长度） | 镜像中的规范形式 |
|---|---|
| `std::vector`（0xC：first／last／end） | `+0 count`、`+4 tail_bytes`、`+8 0` |
| `vector<bool>`（16） | 位数＋tail_bytes，其余清零；位按字节展平 |
| `std::string`（0x18：16B 联合缓冲＋size＋cap） | **按 size 判断，不按 cap**：size≤15 时文本内联、零填充；否则文本放附加区，缓冲清零，size 原样。cap 一律清零 |
| `std::deque`（0x14） | 只保留 size；tail_bytes 放在 map 字；其余清零。元素按逻辑顺序展平，不按分块顺序 |
| `std::map`／`set`／`list`（8：head＋size） | head 字改为 tail_bytes，size 原样；元素按迭代顺序展平 |
| `unordered_map`／`unordered_set`（0x20） | count＋tail_bytes，其余清零；元素按键排序后展平，保证同一内容只有一种编码 |
| ANM2 层数组（`+0x7C layer_states` 加 `+0x80 layer_count`） | `+0x7C` 改为 tail_bytes，`+0x80` 原样 |

- tail_bytes 写的是本段长度，不是附加区偏移。偏移会随前面各段长度变化，静止对象也会出现假差分。
- 原生头按 [RE-13 核定偏移](#81-原生容器头)读取。原生 `std::string` **按 cap 选数据地址**，先核 `size <= cap`；读到有效字节后再按 **size** 选择镜像的内联或附加表示。原生短字符串可能仍使用已保留的堆缓冲。

### 3.5 附加区

附加区存放根对象经指针间接拥有、长度可变的数据，排在主区之后。

**顺序**：Host 和客机按同一张补丁表做深度优先遍历。
1. 处理到一个容器或 owner 槽时，先把它的全部元素镜像连续追加；
2. 再按顺序对每个元素跑它自己的补丁表，元素的间接数据继续往后追加。

客机用一个读游标按同样顺序消费，结束时游标必须正好停在 `record_bytes` 处。各段之间不需要偏移表，tail_bytes 用来核对边界。

**字段归属**：一个容器类字段（容器、长字符串、owner／Weapon 槽）连同它递归拥有的全部附加数据，构成该字段的**整段**。字段有变化时整段上线，没变时不发。记录里的附加区只含本记录列出的容器类字段的整段，按序号升序。

**首版粒度**：容器内只要有一个元素变化，整段就上线；不做按元素差分。如果第 15 步测得 Player 库存、Weapon、costume 等大容器的整段重发占带宽比例明显，再考虑加一层元素序号列表。

**客机重组**：客机的新镜像在附加区上按序号重组：收到的字段用新的整段，其余字段沿用基线镜像中的旧整段。各段长度可能变化，所以附加区不能原位覆盖，要重新拼接。

**规范化**：附加区内容同样按 3.3 节清零，否则静止对象会产生假变化。

### 3.6 Sprite 子程序

布局源中实体、Grid、Player、Room、HUD 的 Sprite 成员**全部按值内嵌**，类型为 `ANM2`（0x114），没有 `ANM2*` 成员。例如：

| 所属对象 | 内嵌的 Sprite |
|---|---|
| Entity | `+0x48` |
| EntityTear | `+0x4AC`、`+0x5C0`、`+0x6D4` |
| EntityPickup | `+0x410`、`+0x5D0` |
| EntityPlayer | `+0x41C`，`ANM2[13]` |
| GridEntity | `+0x40`（GridSprite） |

堆上的 Sprite 只出现在两类地方：
- **容器元素**：Player `_costumeSpriteDescs`（`vector<CostumeSpriteDesc>`，ANM2 在元素 `+0x0`）、AbyssLocust 的两个 `vector<ANM2>`、RoomTransition `extra_portraits`（`map<int,ANM2>`）；
- **共享 owner 的附属数据**：IsaacsBodyData（5 个 ANM2）、UmbilicalBabyData、MrMeData、PickupGhostData（`ANM2[4]`）。

所以 Sprite 子程序只写一份，有三个入口：内嵌、容器元素、owner 子记录。ANM2 的补丁槽（偏移来自布局源 `base.json`）：

| 偏移 | 字段 | 类别 |
|---|---|---|
| `+0x0` | file_name（string） | ③ 文件资源句柄；`loaded=false` 时写空句柄 |
| `+0x18` | default_animation_name（string） | ④ 有界字符串；保留当前需求清单的字段，见 [RE-13](#84-sprite-槽位) |
| `+0x30`／`+0x50` | main_state／overlay_state（AnimationState） | 内嵌：`animation_owner` ⑥；`active_animation` ③，写动画序号；`layer_frames`／`null_layer_frames` ④，帧选择器数组，元素个数分别取所选 **AnimationData** 的 `+0x1C`／`+0x24` |
| `+0x74`、`+0x78` | animation_data、animation_count | ⑦ |
| `+0x7C`、`+0x80` | layer_states、layer_count | ④，LayerState 数组，元素 0xA0 |
| `+0x84`—`+0x90` | null_layer_names、event_names 及其计数 | ⑦ |
| `+0x109` | loaded | 本地位，并入 file_name 的可空资源号（沿用版本 32 规则） |

LayerState 元素内：`layer_data` 为 ⑦，`animation_owner` 为 ⑥，`spritesheet_path` 和 `image_selection` 为 ③，其余字段为状态字节，直接复制。

`loaded=false` 时跳过层数组和帧选择器数组，对应槽写 0。即使 `loaded=true`，仍沿用各资源和数组的读取资格。层数为 0 时不追随旧层指针，空层指针也不解引用。

**L8 后的 Sprite**：布局源原来用 `sprite#0/#1/#2` 把一个 ANM2 拆成外观、动画、图层三个投影，分别放进父类的三个块。L8 后不再需要投影：ANM2 直接展开为字段，各字段的流继承所在父字段。例如 Player 的 13 个内嵌 Sprite 走 Body，实体的主 Sprite 按 Entity 的规则落定。layer_states、layer_frames、null_layer_frames 是容器类字段，按整段比较和上线。

### 3.7 引用与资源翻译

- **引用**：线上的值就是**成员标号**，和记录头 `member` 是同一套编号。不同 space（实体、Grid 等）共用一张成员表。翻译沿用现有的两步，分在两个线程上做：
  1. **主线程：地址→身份**。补丁处理到引用槽时，读出镜像里的指针，调用 `identify_or_reserve`（`nested.cpp:265`），得到目标身份 `space/local/use`，登记进本份引用目录（`CaptureReferenceEntry`），再把目录序号原位写进槽。身份按采集时刻地址上实际存在的对象确定，与 Host 原生代码此刻解引用看到的是同一个对象。
  2. **编码线程：身份→标号**。标号要等本帧成员表确定后才知道（沿用、回收、epoch 推进都在编码线程，`host_publish.cpp:290-300`），所以主线程写不了标号。编码线程每帧用“身份→标号”散列表把引用目录整体解析一遍，得到“目录序号→标号”直接表，再按补丁表把各引用槽改写成标号。这取代现在逐个查找时线性扫描 `snapshot.members` 的 O(N²) 做法（`host_publish.cpp:320`）。

  空引用、Pending、沿用成员尚无线上编号（写空并记 `missing_reference`）、目标不在成员表（报 Gap）等情况，沿用现有规则；字段能否为空仍按布局源的 nonnull 规定。标号会回收，`use` 用来区分前后两代；客机按本帧随附的成员表（E4）把标号换回自己的实体。

  布局源中 `wire.kind=reference` 的目标都在这张成员表里，只是身份空间不同：

  | 目标（布局源 `target`） | 例子 |
  |---|---|
  | 实体（entities／entity／Entity／entity-members） | Entity 的 parent／child／spawner／target 等，Tear、Pickup、Laser、NPC、Familiar 的引用，EntityPtr，Whip 主体 |
  | Player（player） | twin、backup、HUD 和显示结果里的玩家 |
  | Grid（grid） | Room 的 8 个门槽，`u16[8]` |
  | 房间描述（room-descriptor） | MapFocusResult |
  | 参与者（participant，空间 9）、控制组（control-group，空间 10） | PlayerControlGroup、EntityPlayer 的控制组 |

  其中参与者、控制组、门槽、MapFocus 是合成字段或具名读取：Host 由 handler 直接给出身份，不经过原生指针；编码线程的“身份→标号”一步相同。
- **资源**：资源也按“标号”方式编码，但用的是另一套编号，即资源目录。
  - **编号空间**：8 张表，固定编号 0—7 依次是 anm2-animation-table、image-table、anm2-files、item-config、entity-configs、room-config-visual、shader-table、audio-table（[公共线合同](9-public-wire-contract.md)）。线上写表内序号 u16，表号由字段在生成表里的定义决定，不上线。
  - **与成员标号的区别**：资源目录在同一局内只追加、不回收、不覆盖原号（`resource_directory_rewound`、`resource_identity_rebound` 会直接失败）。身份是内容（路径、配置 type／id 等），不是存活对象。条目描述走可靠通道，客机收到后预载；缺资源时只延后用到它的对象（E4）。
  - **翻译**同样分两步：主线程按指针得到资源身份，写入本份资源目录序号；编码线程改写为表内序号。现在编码线程按 handle 线性扫描 `snapshot.resources`（`host_publish.cpp:320`），改为按 handle 直接查表。
  - 主线程“指针→资源身份”这一步用下面的指针键缓存，避免每帧重新解析路径。
- **资源身份缓存**：改为以**原生指针**为键的跨帧缓存，取代现在含实体身份的键（10.7 记录的跨帧命中接近 0）。
  - ItemConfig、EntityConfig 条目在整局内地址稳定，可以直接缓存。
  - AnimationData 和图像对象可释放并复用地址。缓存命中必须有覆盖资源身份的见证：已证明覆盖重载、释放与来源切换的代次，或当前有界读取窗口内与目录描述等价的完整输入。地址、尺寸、名称长度和前缀都不能单独证明等价。换局、换 scope、资源目录代号变化或资源写水位撤销时作废相应缓存，见 [RE-13](#83-资源释放与跨帧缓存)。

### 3.8 Host 流程

**主线程**，在同一个原生读取窗口内：
1. 对每个根，按生成的复制段做 memcpy。读取走整帧可读区表（H1）和窄 SEH。
2. 按补丁表依次处理：引用（只做到地址→身份，写目录序号）、资源、换算、条件清零；遇到间接子项时递归追加附加区。
3. 任何一步失败，就把镜像缓冲和附加区截断回本根开始前的位置，本根标记为沿用（E10）。全局根失败仍丢整帧。

**编码线程**：
1. **改写引用**：按 3.7 节把引用槽里的目录序号改写为成员标号。比较要在改写之后做，这样标号变化也算字段变化。
2. **按字段比较（每帧一次，与 Peer 数无关）**：把本帧镜像和该成员上一帧镜像比较。
   - **主区**：先判断整个成员是否没变；变了再逐字节比较得到差异位图，然后只遍历置位的位，经字节→字段号表得到变化字段。具体做法见 3.8.1。
   - **附加区**：附加段的位置随前面各段长度变化，不进字节位图。容器类字段先比 tail_bytes，相同再对整段做向量化比较。
   - 规模（推算）：每份镜像约 300—600KB，向量化比较约 10—20µs；定位变化字段的开销只和变化字节数成正比。整个过程单线程完成，不需要多线程。
3. **版本戳**：字段变了，就把它的版本戳记成所属流的当前版本（world 字段用 World 版本，body 字段用 Body 版本）。每个成员另记各流的最大版本戳。
   - 新建、换身份（identity 或 use 变化）、换布局时，没有上一帧镜像可比，所有字段的版本戳设为当前版本。成员槽复用时，版本戳一并重置。
   - 沿用的根（E10）镜像不变，版本戳也不变。
4. **按 Peer 选字段**：对每个 Peer 的每条流：
   - base=0 时，所有成员都用 `set_mode=2`；
   - 成员该流的最大版本戳不大于该 Peer 已 ACK 的版本，就跳过整个成员；
   - 否则发送版本戳大于 ACK 版本的字段。
   - 联合结构路径对 Player 配对投影和控制组整发的现有规则，改为对相应字段用 `set_mode=2`。
5. **组装**：拼接记录头、字段集合、值区和附加段，然后整消息 zstd。不排序、不查找、不逐字段编码。

这一套取代原来“每个 Peer 一份基线镜像、逐 Peer 逐范围做 memcmp”的做法：Host 只需保留本帧和上一帧两份镜像，加上每个字段的版本戳。代价是值从 A 变到 B 又变回 A 时，基线还是 A 的 Peer 会多收一次这个字段，不影响正确性。

**Body**：Player 的 body 字段直接取自同一份镜像，版本戳按 Body 的采样时刻更新。B1 的拓扑与绑定核对规则不变。

#### 3.8.1 向量化实现

构建为 MSVC v143 Win32（`mod/CMakeLists.txt:4`），默认 `/arch:SSE2`。做法：用 MSVC 内建函数手写，SSE2 作为基础实现，运行时检测到 AVX2 时切换；不引入 SIMD 库，不依赖编译器自动向量化，不用 AVX-512，不开多线程。

**内核**（Host 编码线程与客机后台共用同一套，客机用于 3.9.2 第 4 步）：

| 内核 | SSE2 | AVX2 | 说明 |
|---|---|---|---|
| ① 成员是否整体未变 | 两份镜像逐 16 字节异或，按位或累加，最后判断是否为 0 | 每次 32 字节 | 静止成员一遍判定完，不生成位图 |
| ② 字节差异位图 | `_mm_cmpeq_epi8` 加 `_mm_movemask_epi8`，16 字节得 16 位，取反后置位表示该字节变了 | `_mm256_cmpeq_epi8` 加 `_mm256_movemask_epi8`，32 字节得 32 位 | 位图按 u32 存放 |
| ③ 定位变化字段 | 标量：`_BitScanForward` 找下一个置位的位 → 查字节→字段号表 → 标记该字段 → 清掉位图中该字段其余字节的位 → 继续 | 同左 | 开销与变化字节数成正比，与字段总数无关；遇到 `0xFFFF` 的字节说明清零规则失效，计数并按失败方式 8 处理 |
| ④ 按 Peer 挑字段 | `_mm_cmpgt_epi32` 加 `_mm_movemask_ps`，一次比 4 个版本戳是否大于 ACK 版本 | 一次比 8 个 | 直接得到“要发的字段”位图；同一局内的版本号小于 2³¹，有符号比较足够，换局时版本重置 |
| ⑤ 字段集合编码 | 两级位图：组字与 0 比较后 movemask 得顶层位图；序号差列表：`_BitScanForward` 遍历；个数：`__popcnt`，不支持 POPCNT 时查表 | 同左 | 3.2.3 的两种编码都由同一张字段位图生成 |
| 附加段整段比较 | 同 ① | 同 ① | 先比 tail_bytes |

**实现约束**：
1. **AVX2 隔离**：AVX2 内核放在单独的 `.cpp`，只给这个文件加 `/arch:AVX2`（MSVC 不能给单个函数指定目标指令集）。
   - 该文件不得包含会被其他文件共用的 inline 函数或模板，否则链接器可能选中 AVX2 编译出的那一份，在不支持 AVX2 的 CPU 上崩溃。
   - 内核以 `extern "C"` 普通函数导出。AVX2 文件内由编译器自动插入 `vzeroupper`；SSE2 文件中不写 `_mm256` 内建函数。
2. **运行时检测**：启动时检测一次，定好函数指针表，之后不再检测。
   - AVX2 要同时满足三条：`__cpuid` 报告 AVX2，`OSXSAVE` 置位，`_xgetbv(0)` 显示操作系统保存 YMM 状态；
   - POPCNT 单独检测；
   - SSE2 是 Windows 8 以后的硬性要求，不检测。
   - 检测结果写进诊断日志。
3. **32 位环境**：XMM/YMM 只有 8 个，循环最多展开 2 倍；不用 `_BitScanForward64`、`__popcnt64`、`_tzcnt_u32`（需要 BMI1），统一按 u32 处理。
4. **只读自有缓冲**：向量读只用于 Host、客机自己的镜像，不直接对游戏原生内存做向量读。镜像按 32 字节对齐分配，末尾补零到 32 字节；读取一律用非对齐读（`loadu`）。
5. **两条路径结果一致**：SSE2 与 AVX2 必须给出逐位相同的位图。E2E 诊断模式下可以强制使用 SSE2 路径，由离线还原工具对拍两端镜像，覆盖两条路径（3.10）。

**校验**：Host 默认不跑字段校验，只在 E2E 诊断模式下对镜像跑生成校验，用来尽早发现采集错误（L2）。

### 3.9 客机流程

L7 已定：客机与 Host 同轮改造，不做中间的转码层。

**现状**：解码在后台线程（`client_shadow.cpp:430`、`:723` 调 `DecodeBody`），主线程依次走 Prepare、暂存、Describe、Install，再加上 10.5 静止记录和 10.6 快速路径（写程序表、整批快速帧、吸收）。这条链以字段为单位，消费 `DecodeBody` 产出的字段视图。已迁移布局改为按镜像工作；未迁移的全局根（L3）继续走原链。

#### 3.9.1 保留不动的部分

- 引用和资源的线上语义：成员标号、资源表内序号（u16）；
- 字段的 world／body 归属（原块的 `sequence`，L8 后由字段承载）；
- 成员身份随帧（E4）、资源目录与预载、事件队列、显示委托；
- 对象新建、Morph（E6）、退休，以及按批次转交的根与承载所有权。10.6 节说明过：渲染成员表、绘制顺序、房间名册和退休拆边都按批次维护，本方案不改这一点；
- 具名写入器：SetReference、资源 owner、Shared holder／Weapon 槽重建、到期帧与 Time 换算、Sprite 文件／动画／图层写入等；
- 根标量首次写入前的快照与撤场还原；
- 写前核对对象存活与实例代次、SEH 兜底、按对象隔离失败（E3）。

#### 3.9.2 后台：解码、校验与快照

1. **解码**：核对记录头和字段集合（`set_mode` 合法，序号严格递增且小于字段数，只含本流字段）。把值区按字段覆盖到该成员基线镜像的副本上；附加区按 3.5 节重组。核对附加区游标正好停在 `record_bytes`，并核对各段 tail_bytes。
2. **校验**（L2）：
   - 单字段校验（finite、boolean、range、enum）只对收到的字段运行；
   - 跨字段校验（count_groups、计数上限、tail_bytes）对收到字段所在的写入组、在覆盖后的镜像上运行；
   - 收到的引用和资源字段必须能在本帧表中解析。
   - 校验失败的对象本帧跳过，其余对象照常。
3. **快照**：新镜像进入快照环（E2）；未变成员共享上一份镜像，不复制。
4. **算写入集合**：用与 Host 相同的向量化比较（3.8），把新镜像和“该实例上次实际写入的镜像”比较，得到变化字段，再扩展到它们所在的写入组。
5. **票据**：交给主线程的票据中，每个成员带新镜像、需要写的写入组集合，以及是否需要全量写（3.9.4）。

校验和比较都在后台做，不占主线程。

#### 3.9.3 主线程：一次 Manager 调用内写入

阶段顺序沿用现有事务，平铺写入器占据原来“Entity／Grid／Player 纯值与具名写入”的位置：

1. 对象准备：按成员表新建、Morph、退休；新建对象标记为全量写。
2. 未迁移的全局根按原链安装。
3. 对每个平铺成员：
   - 核对对象存活与实例代次；
   - 对需要写的写入组，按生成的写段做复制。写段是“镜像偏移→原生偏移→长度”，按写入组归类，已排除 ①⑥⑦、全部指针槽、容器头和需要 setter 的字段；
   - 按补丁表顺序执行原生操作：②SetReference、③资源 owner、④原生 resize 与元素写入、⑤owner 重建与递归、⑧具名写入器。只执行属于需要写的写入组的槽；
   - 帧相关换算（到期帧、Time）每帧都执行，不看是否变化；
   - 按镜像里的全部引用槽登记引用边，供退休拆边使用，不只登记变化字段中的引用槽。
4. 显示安装、音频、事件回放和发布，沿用现有顺序（构图类显示仍最后安装）。

#### 3.9.4 只写变化，还是全量写

默认只写相对“同一实例上次实际写入的镜像”有变化的字段所在的写入组。以下情况全量写，即写全部写入组：

- 新建、重建、Morph、完整基线、缺席后补写；
- 该对象上一次写入失败或只写了一部分（发布前标记为待重写，沿用 10.5 失败方式 10 的处理）；
- 轮转刷新：按成员号加 World 版本对 32 取余为 0 时全量写，用来修正本地显示代码对已同步字段的改写（漂移）。这取代 10.5 条件 6 和 10.6 的强制刷新。

#### 3.9.5 容器与承载

- 容器在写段内用原生 resize／assign（游戏分配器）调整，重分配后**重新取元素基址**再写元素，不沿用写前的地址。现有“值向量、EntityPtr deque、绘制节点链表原位变长”的处理沿用。
- 独占容器需要换承载时，在写段构造新原生容器并接入，再写元素，与现有做法相同。
- 容器字段未变时不写；变了但元素个数相同时，不调用 resize，原位写元素。

#### 3.9.6 已迁移布局退役的客机部件

字段暂存、Describe、静止记录分类（10.5）、写程序表与整批快速帧、吸收（10.6）。这些部件只继续服务未迁移的全局根。漂移扫描改为：对写段按镜像 memcmp 原生字节，具名字段沿用抽样。

### 3.10 诊断

- **离线还原工具**：读取生成表，把任意一条平铺记录还原成逐字段视图。这代替现在 `missing_captured_value` 一类的字段级诊断。
- **计数**：
  - 主线程：每根程序耗时（采样）、镜像字节、补丁数、附加区字节；
  - 资源缓存：命中、见证失败、作废；
  - 启动时：CPU 检测结果与选用的内核路径（SSE2／AVX2、POPCNT）；
  - 编码线程：比较耗时、变化字段数、按 Peer 跳过的成员数、`set_mode` 三种编码的分布与字段集合字节、组装耗时；
  - 客机：校验拒绝原因、字段集合解码拒绝、写入组数、写段字节、原生操作数。
- **按字段计数**：离线还原工具按字段汇总一段时间内的上线次数和字节，用来找出频繁变化的字段和整段重发的大容器。

### 3.11 内存（推算）

- **每颗泪弹的镜像**：EntityTear 原生大小 0x848；去掉不同步的字节后，加上 4 个 Sprite 的层数组，估计 1—2KB。
- **Host**：本帧和上一帧两份镜像，加上每字段 4 字节的版本戳。300 颗泪弹约 0.6—1.2MB 镜像加约 300KB 版本戳；原来按“每个 Peer 一份基线镜像”估算约 2.4MB。
- **客机**：快照环 K=8。未变成员按引用共享镜像，不逐份复制。
- 两侧都要纳入三池内存总额，超出时按现有规则退化。第 15 步给出实际高水位。

## 6. 失败方式

| 编号 | 失败方式 | 处理 |
|---|---|---|
| 1 | 指针漏分类，Host 地址原样上线 | 3.3 节的生成期检查；未覆盖就生成失败 |
| 2 | `未知` 字节被复制，客机又写回 | 未知字节不进复制段；客机写段只含状态类字节 |
| 3 | 身份与成员表不属同一时刻：主线程身份来自本帧，编码线程却拿另一帧的成员表解析；或标号回收后，客机按旧表把标号解释成另一代实体 | 引用目录随 packet 封存，只按该 packet 对应的成员表解析；客机只用本帧随附的成员表（E4）；身份含 `use` 区分前后代 |
| 4 | 资源地址被释放后复用，缓存给出错误句柄 | 见证值核对，换局、换 scope、目录代号变化时整体作废；生命周期由 RE-13 定 |
| 5 | 容器头模板与 MSVC 实际布局不符 | RE-13 核对；客机不写容器头，所以最坏情况是 Host 读错，表现为该根失败，不会写坏客机内存 |
| 6 | count／tail_bytes 不一致或超上限 | 客机按对象隔离；Host 预算检查，超限该根失败 |
| 7 | Host、客机的附加区遍历顺序不一致 | 双方由同一张生成表驱动；游标必须正好停在 `record_bytes` |
| 8 | 条件不成立的字段残留旧字节，产生假差分 | ⑨ 条件清零 |
| 9 | 同一字符串因 cap 不同出现两种编码 | 按 size 判断（3.4） |
| 10 | 换算 handler 依赖镜像以外的上下文（FrameContext 等） | handler 显式声明输入；输出写进镜像，差分照常 |
| 11 | 根失败后镜像或附加区没有回卷干净 | 截断到本根开始的位置，再写沿用标记（E10） |
| 12 | Body 字段与客机当前 World 镜像不属同一拓扑 | 沿用 B1 的拓扑与绑定核对，不一致就跳过这一拍 |
| 13 | 新旧布局版本混用 | 整数版本 85，握手精确匹配 |
| 14 | Host 校验后移，采集错误要到客机才暴露 | E2E 诊断模式在 Host 跑同一套生成校验 |
| 15 | 字段表映射错误：两个字段的镜像范围重叠，或漏掉需求字段 | 生成期检查：字段镜像范围两两不相交，并覆盖全部需求字段 |
| 16 | 复制段合并时跨过了易变的本地字节，清零成本高或产生假差分 | 生成器只跨填充字节合并；其余间隙断开复制段 |
| 17 | `loaded=false` 时仍去读层数组 | 3.6 节规定跳过；layer_states 为空指针时也跳过 |
| 18 | 共享 owner 的动态类型未知 | 该根失败（E10），不能当作“不存在” |
| 19 | 客机绕过 SetReference 直接写 EntityPtr | 写段排除全部指针槽；② 只走 setter |
| 20 | 大块 memcpy 跨入不可读页 | 读取走 H1 区表加窄 SEH；失败只影响该根 |
| 21 | 镜像内存超出三池总额 | 第 15 步记录高水位；超出时按现有规则退化，并上报 |
| 22 | 迁移布局与未迁移布局混在同一份 ordinary 里，编码线程分派错误 | 按布局表标记分派；未知标记直接拒绝 |
| 23 | 新旧两套客机写入并存，同一字段被写两次，或某个布局两边都不写 | 按布局表的平铺标记分派；已迁移布局只走 3.9 写入器，10.5／10.6 只服务未迁移布局 |
| 24 | 两条安装路径在同一批中顺序错乱，例如全局根晚于实体写入 | 沿用现有阶段顺序，平铺写入器只占实体／Grid／Player 那一段（3.9.3） |
| 25 | 上一次写入失败或只写了一部分，下一批因字段未变而跳过，对象长期停在半写状态 | 发布前把失败对象标为待重写，下一批全量写（3.9.4） |
| 26 | 本地显示代码改写了已同步字段，而这些字段长期不变，漂移得不到修正 | 每 32 份 World 轮转全量写；漂移扫描对写段做 memcmp（3.9.4、3.9.6） |
| 27 | 到期帧、Time 等帧相关换算只在字段变化时写，计时冻结 | 帧相关换算每帧执行（3.9.3） |
| 28 | 容器重分配后仍按旧元素地址写，写进已释放内存 | resize 后重新取元素基址；元素个数相同时不 resize（3.9.5） |
| 29 | 只登记变化字段里的引用，目标退休时拆边遗漏，留下悬空指针 | 每批按镜像里的全部引用槽登记引用边（3.9.3） |
| 30 | 根标量没有首次写入前的快照，撤场无法还原 | 沿用现有快照机制，首次写入前补快照 |
| 31 | Host、客机同时改，出错时难以判断来源 | Host 诊断模式跑生成校验（失败方式 14）；客机首因按生成表报到具体字段；离线还原工具可把两端镜像逐字段对比（3.10） |
| 32 | 写入组漏掉依赖字段，客机只写了一半，原生对象处于半新半旧的组合（例如动画号已换、帧还是旧的） | 生成期检查：handler 的输入、输出字段必须同组，否则生成失败；自动规则推不出的在布局源手工声明（3.2.2）；漂移扫描兜底 |
| 33 | 字段集合损坏：`set_mode` 非法、序号不递增或越界、组位图与字段数不符、列出了别的流的字段 | 客机解码时逐项核对（3.9.2），不合法时该对象本帧跳过并计数，按 E3 阈值请求基线 |
| 34 | 版本戳没有初始化或没有重置：新成员、换身份、成员槽复用时沿用了旧戳，导致字段漏发 | 新建、换身份、换布局、槽复用时把所有字段的戳设为当前版本（3.8 第 3 步）；每 32 份轮转全量写可修正客机侧残留 |
| 35 | World 和 Body 的版本戳或 ACK 混用，字段按错误的流判断，导致漏发或重复发 | 每个字段固定一个流（生成期检查），戳只用所属流的版本，只与所属流的 ACK 比较（3.8 第 3、4 步） |
| 36 | 附加段位置随前面各段长度变化，按字节位图比较时把位移误判为变化，或把真实变化漏掉 | 附加区不进字节位图；容器类字段先比 tail_bytes，再整段比较（3.8 第 2 步） |
| 37 | 客机重组附加区时，未变字段的旧整段没有按序号放回原位 | 附加区按序号重新拼接（3.5）；游标结束位置和各段 tail_bytes 核对 |
| 38 | 字段集合的开销超过省下的字节，例如大量字段同时变化时 | 编码器在两种集合编码中取短的，`set_mode=2` 直接发全部字段；第 15 步按 `set_mode` 分布和集合字节评估 |
| 39 | 向量化比较在 32 位构建或旧 CPU 上不可用，或未对齐读取越过镜像末尾 | 至少用 SSE2；AVX2 运行时检测后才启用；镜像按 32 字节对齐、尾部补零，比较不越界（3.8.1） |
| 40 | AVX2 文件里的 inline 函数或模板被链接器选进公共路径，在不支持 AVX2 的 CPU 上执行非法指令 | AVX2 内核单独成文件，不含共用的 inline 函数或模板，以 `extern "C"` 导出（3.8.1 约束 1） |
| 41 | 只看 cpuid 就启用 AVX2，操作系统没有开启 YMM 状态保存，导致崩溃或寄存器内容被破坏；或 POPCNT 不可用时仍调用 `__popcnt` | 三条件检测 AVX2，POPCNT 单独检测，不支持时查表（3.8.1 约束 2） |
| 42 | SSE2 与 AVX2 两条路径给出的位图不一致，同一份数据在不同机器上发出不同的字段 | 两条路径共用同一套位图定义；E2E 诊断模式可强制 SSE2，用离线还原工具对拍（3.8.1 约束 5） |

## 7. 用户决定（2026-11-18）

L1—L6 按推荐，L7 选备选：客机与 Host 同轮改造。同日用户追加 L8：取消块，按字段增量。下列各项保留当时的推荐理由；L2、L5 中的“块”已由 L8 改为字段。


- **L1 主区形态**：推荐**紧凑镜像**，即只含需求字段所在的复制段，合并时只跨填充字节，镜像偏移由生成器分配。备选是原生全量镜像，镜像偏移等于原生偏移，实现最简单，但 Player 等大对象的镜像有 0x2EA0 字节。
- **L2 校验位置**：推荐客机写前只对变化部分跑生成校验（L8 后为收到的字段及其写入组，3.9.2），Host 仅在诊断模式下运行。备选是保留 Host 全量校验，这会把一部分编码成本留在 Host 上。
- **L3 首批范围**：推荐实体、Player、Grid，全局根暂留现有路径。备选是一次迁移全部布局。
- **L4 与 10.7 的关系**：推荐用本方案取代 W1／W2；B1、B2、M2 照做；M1 的资源槽由指针键缓存取代。
- **L5 差分形式**：推荐沿用块差分加整消息 zstd，不加异或。异或差分视第 15 步的带宽再议。**已被 L8 部分取代**：块差分改为字段差分；整消息 zstd、不加异或仍然有效。
- **L6 引用翻译**：推荐沿用现有两步（3.7）：主线程地址→身份，编码线程每帧建一次“身份→标号”散列表，按补丁表原位改写。备选是把成员标号分配挪到主线程，让主线程直接写标号；这要把沿用、回收、epoch 推进逻辑一起搬过去，改动大，收益只是省掉编码线程一次 O(引用数) 的改写。

- **L7 客机改造方式（用户选备选）**：客机与 Host 同轮改造，客机直接按镜像写入（3.9），不做中间转码层。原推荐是分两期：先在后台把平铺记录转成现有正文、主线程不动，再视实测决定。同时大改时出错难以区分来源，由失败方式 31 的措施兜底。

- **L8 差分粒度（用户提出，按推荐细节落定）**：取消块，差分、上线与比较都以字段为单位（3.2）。
  - 字段集合在两级位图（16 字段一组）和序号差列表之间按记录自适应选择，`set_mode=2` 表示全部字段；
  - 写入组由生成器按 handler、资源 owner、容器、owner 槽和跨字段规则自动推出，推不出的在布局源手工声明；
  - 容器、长字符串、owner／Weapon 槽首版各算一个字段，整段比较和上线，不做按元素差分；
  - Host 每帧向量化逐字节比较一次（SSE2 为基础、运行时切换 AVX2，3.8.1），只遍历置位的位、经字节→字段号表定位变化字段，用每字段版本戳为各 Peer 选字段，不再保留每个 Peer 的基线镜像；
  - 记录头改为 `member u16 | layout u16 | record_bytes u32 | set_mode u8`，撤销 2026-11-11“保留 u32 块掩码和 12B 记录头”；
  - 布局源退役 `blocks[]`、块号、32 块上限、预留空块和 Sprite 投影，字段改为自带流属性；
  - 格式变更并入版本 85。

| `unordered_map<int,int>`／`unordered_set<int>`，各 0x20 | `+00` 最大负载因子，`+04/+08` 链表哨兵／元素数，`+0C/+10/+14` 桶迭代器向量的 begin／end／capacity-end，`+18` 桶掩码，`+1C` 桶数。每桶两条迭代器 | 首批实例由 REPENTOGON 1.1.3 的 `ItemSpoofSystem.h` 定义。现有 Win32/v143 `zhlIsaacCS.pdb` 的 int/int map 与 int set 的 `std::_Hash` 类型记录和本机 v143 `xhash` 的 `_Uhash_compare`、`_Hash_vec` 一致。[SDK ABI 声明](../../../mod/src/game/client/player/client_player_sdk_abi.cpp) 和 [HashItems](../../../mod/src/world/binary/entity_containers.cpp) 给出该实例的尺寸、list 前缀及节点 value。 |

扫描 deque 按逻辑下标和该布局的元素步长取有效块。map／set／list 按逻辑迭代顺序读取，unordered 从双向链表取值后按键排序。`vector<bool>` 按位数截取有效位。所有头内地址、桶、proxy、容量及未用位均留在本地。后续生成器可按第 3.4 节输出规范头；元素路径复用已核的计数、范围及生命周期检查。

### 8.2 KAGE 图像智能指针

- 8B 句柄的 `+00` 是 ImageBase*，`+04` 是控制块。控制块大小 0x18，含虚表 `+00`、u16 strong／weak `+04/+06`、mutex `+08`、ImageBase* `+14`。构造 `0x408950` 分配控制块并写 image，`0x402670` 初始化 strong／weak 各为 1。构造允许 image 为空而控制块存在。
- ImageBase 控制块虚表 `0xAAC4D4` 的 `+04` → `0x408580` 只在 strong 非零时增加 strong。复制 `0x4082B0` 成功增持后才复制两字，赋值 `0x408110` 先取得来源，再交换并释放旧句柄。普通增持 `0x408560` 在 mutex 下增加 strong。
- 释放 `0x4081A0` 调计数虚表 `+0x0C` → `0x408500`。strong 从 1 到 0 时以 image 虚表 `+0x60` 析构图像、清控制块的 image，再释放隐含 weak 引用。`0x408490` 在 weak 到零时调用 `0x408CA0` 销毁并释放控制块。最后一个 LayerState 句柄消失时，若原生缓存仍有持有者，图像可以继续存活。
- Host 只在有效读取窗口借读实际句柄；非空 image 应有匹配且活的控制块。控制块、计数和 mutex 均不进镜像。客机由本地资源 owner 持有并赋值句柄。

### 8.3 资源释放与跨帧缓存

| 路径 | J273 静态结论 |
|---|---|
| ANM2 正常加载／重置 | `0x407AF0` 先经 `0x409BB0` 退出旧路径引用，`0x409680` 查或建缓存并借出底层数组，再由 `0x409A40` 增加缓存节点 `+0x50` 的引用。Reset `0x403530` 也退出旧引用。退出旧引用只减计数，零引用的内存由清理路径回收。 |
| ANM2 清扫／退出 | `0x409D40` 遇节点引用为 0，调用 `0x4093C0` 后摘除并释放节点。Lua reset 的 `0x8D5A30` 会调用此清扫。`0x4093C0` 析构并释放步长 0x38 的 LayerData 数组、步长 0x13C 的 AnimationData 数组及其嵌套数组和 null/event 名表。游戏退出 `0x982C90` 与全局资源析构 `0xAA7120` 经 `0x408EF0` 清缓存。 |
| ANM2 条目原地换内容 | `0x4097FE–0x40981C` 在未命中，或命中节点 `+0x14` 标志置位且资源存在性查询返回非空时进入 `0x40A5F0`。`0x40A6FB–0x40A713` 取得条目后先调 `0x4093C0` 再重新装载，调用前未以节点引用为 0 限制。缓存节点本身、原路径和文件名可能保持一致，但借出的数组已换代。 |
| 图像缓存与析构 | `0x931B30` 解析路径，`0x9EEE80` 可复制已有图像句柄，或分配新的 PNG／PCX 对象并登记图像管理器；LayerState 析构 `0x4030E0` 与换图赋值 `0x403C40` 都能释放持有。ANM2 的图像预载表可在 `0x409FC0` 释放缓存引用并移除条目，也随 `0x408EF0` 清空。普通图像管理器的释放回调 `0x9EFE60` 在仅剩管理器引用时进入 `0x9EF7C0` 尝试摘除；最终 strong=0 按 `0x408500` 析构。PNG／PCX 的实际删除入口为 `0xA346F0`／`0xA340B0`，均释放对象存储。 |

**缓存见证。** 指针键可跨对象共享，但缓存只保存纯值描述或目录序号。重载或析构后，分配器可复用地址，这是从释放和再分配路径得到的静态推导。缓存命中时：

- **AnimationData**：在本帧有效读取窗口确认当前 ANM2 文件和动画所属数组。以 `ANM2+0x74/+0x78` 与步长 `0x13C` 核对当前选择的范围、对齐及序号。跨帧复用还须核已证明覆盖重载的代次，或完整比较进入资源描述的文件身份、动画名称、长度、普通／空层的计数、ID 和帧数。相同指针或相同序号可能落在重载后的新版本。
- **图像**：确认当前句柄与实际 image／counter 对应。跨帧复用须有可跨地址复用的生命周期代次，或重新核完整的有效资源身份输入，包括实际图像的类、完整解析路径、使用的几何值，及程序图像的具名 owner／来源。LayerState 路径字段可与实际图像不同，不能代替图像见证。控制块地址与强计数同样可能随分配复用而重复。
- 现有源码未证明覆盖上述全部原生路径的资源代次。见证失配时按当前来源重新解析，无法确认真实来源时沿用 E10 按根回卷。资源写水位、换局、scope 和资源目录寿命沿用 3.7 节。运行时地址复用频率、缓存命中率及开销归第 15 步。

### 9.3 包131：编码线程

- 生成表补上每流字段位图及附加段索引。后台完成编号翻译后，只与同身份、形态、布局和流的上一份镜像比较。主区先整体比较，再以差异位图定位字段。附加段按各字段的实际长度与内容比较，前段长度变化无需重发后段。保留对象镜像和版本戳用于沿用，引用失效的旧镜像只携带沿用标记。清零填充出现差异时按根沿用，并计入 `stream.capture_worker.flat_padding_failures`。
- 每流独立推进 31 位以内的采集版本，状态帧继续使用各 Peer 自己的目标号。已确认目标的发送凭据记录实际发出的采集版本，用它比较字段戳。发送账本与 ACK 为平铺根保留身份、资源依赖等元数据，不保留该 Peer 的平铺基线镜像。若已确认的帧曾沿用该根，包括等待资源目录的投影，恢复发送时整根补齐该流字段。
- [字段集合和记录正文](../../../mod/src/state/flat_encode.cpp)按字段位图的递增序号组装。增量在两级位图和序号差 LEB128 间取短，同长选位图。基线、新建、换身份及补齐按流使用 `set_mode=2`。记录头中的 `record_bytes` 计字段集合、值区和附加区，沿用原来的正文长度语义。混合帧按布局标记使用 9 字节平铺头或旧头，并按真实头长计预算。整消息 zstd 走现有发送链。
- [SSE2](../../../mod/src/state/flat_simd_sse2.cpp)与[AVX2](../../../mod/src/state/flat_simd_avx2.cpp)共用位图定义。AVX2 独立编译为机器码对象，启动检查 CPUID、OSXSAVE 和 XCR0；POPCNT 独立选择硬件或查表。启动日志 `flat_simd` 记录实际选择，E2E 构建可以用 `ISAACCS_FLAT_FORCE_SSE2=1` 强制基础内核。
- Win32 Release 产品 DLL 已纯编译和链接。Tear 的平铺采集及发布由版本 85 合同与布局标记共同选择。现行版本 84 继续发布块记录，客机平铺解码和安装归第 5 步，合同切换归第 8 步，运行验证归第 15 步。

## 10. 第 15 步覆盖与判定

在同一整体验收内续测，不另开编号。场景：

- 300 泪弹 clear／loss／delay 三段，与 r8 对照；
- 100 泪弹下落（有 FX 生灭）、100 敌怪、四身体混合负载；
- costume 变化、Familiar 共享 owner（IsaacsBody、AbyssLocust）、Effect（MrMe、PickupGhost、Trail）、Weapon 换槽；
- 切房、换层、重开 run、暂停恢复、正常停止与退出。

判定：

1. **耗时**：Host 主线程 ordinary 与实体采集的均值和分位数；编码线程每份 ordinary 的耗时与占用率；客机后台解码与校验耗时；客机主线程单帧应用 p95≤2ms／p99≤4ms，并分列写段字节、原生操作数、全量写与只写变化的成员数。
2. **频率**：World 约 30Hz，Body 50—60Hz，客机 59FPS。
3. **一致性**：漂移扫描无新增差异；校验拒绝、沿用、Pending 的原因分布与 r8 相比无异常新增；第 6 节失败方式 1、5、7、23、33 的计数为 0；退休拆边与容器重分配后无访问异常。
4. **资源**：资源缓存命中率、见证失败次数；内存高水位在三池总额以内。
5. **带宽**：clear 段每 Peer 字节率，与 r8 的 21.9KB/s 对照，并在 375,000B/s 以内；分列字段集合字节、`set_mode` 分布、容器整段重发的字节占比（决定是否做按元素差分）。

## 11. 预期与不确定项

- **主线程（推算）**：每颗泪弹从约 300 次小读取变为十几段复制、4 个 Sprite 子程序和少量补丁，估计每根 1—3µs，300 根实体采集在 1ms 左右。拓扑、生命周期和 Body 采集的固定成本不在其中。
- **编码线程（推算）**：每份 ordinary 从 38.5ms 降到 1—3ms，主要是 zstd；向量化比较和定位变化字段合计在 0.1ms 以内。
- **带宽（推算）**：运动中的泪弹每帧从“12B 记录头加整块”降到“9B 记录头、约 7—10B 字段集合、变化字段值”，E1 一项就从 44B 降到 16B。
- **不确定**：
  - 填充以外的间隙数量决定复制段数，要等生成器跑出结果才知道；
  - AnimationData 的生命周期（RE-13）决定资源缓存的命中率；
  - 镜像内存在快照环里的实际共享比例；
  - 不加异或时的带宽是否够用（L5）；
  - 写入组自动规则能覆盖多少，需要手工声明的有多少，要等生成器跑出结果；
  - 容器整段重发的带宽占比（L8 首版不做按元素差分）。
