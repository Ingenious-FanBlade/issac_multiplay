## 1. 完整目标

在官方 REPENTOGON 1.1.3／Repentance+ v1.9.7.12.J273 下，一名房主加三个真实游戏 Client 同时运行、跨设备连接，在同一个权威房间中持续移动、射击、战斗、拾取及交互。四名参与者和多身体沿用 09／20 的关系，不把身体数当连接数。

正式链路为：Host 统一输入 → 唯一 Authority 原生模拟 → 合格的只读状态采集 → 有界不可变目标 → 每 Peer 网络传输 → Client 完整重组／资源准备／主线程原生应用 → 真实 Applied ACK → 后续状态发布。房主日常模拟不等待 Client；录制、日志、文件导出和 Rust 不参与产品状态生效。

本 tx 交付完整初始 Baseline、同房间持续更新、必要的结构变化、同连接的整份 Baseline 恢复，以及正常停止／失败退休。所有必要的 Room／Grid／Entity／Player 最终状态和引用必须有来源、传输、安装与确认。整局／楼层等上下文按声明范围传输和保留；不能把“已收到十一域数据”报告成十一域原生玩法全部应用。20 的精确域位和真实消费者仍是确认依据。

验收先进行 P2（一 Host＋一真实 Client）的**完整 E01—E26及全部子用例**，所有功能、故障、性能、回归、产品路径和退出均先在两人中实际跑通；全部通过后，P4（一 Host＋三真实 Client）才将整套测试扩到四人重跑，增加三 Peer 竞争／公平／隔离及四组八体断言。每个 E 都有完整两人版本，不能以“不适用／待四人”跳过或只做连接冒烟。两人结果不冒称三 Peer 行为已验证；两阶段不拆 tx 或另设审批流程。

本次单房间负载与 10 Mbps 参数是中间交付的可测运行范围，不缩减既有 18—20 adapter，不代替 23—34 的最终完整产品范围。

## 3. 本次方案和相邻 tx 边界

### 3.1 明确采用的方案

1. **完整 Baseline 用于首次构建和恢复**：压缩、可靠分块；单次 Baseline 描述完整目标或精确版本依赖，Client 从冷状态能取得全部必需数据。准备和传输期间 Host 继续模拟。
2. **持续更新用明确子范围的完整快照**：PlayerFast、WorldDynamic，以及变化时可靠发送的完整 Context／Structure／Resource 范围。它们按固定 schema、成员全集、依赖版本和自身采样时刻定义，不是将“相对上一帧的变化字段”改名为全量。
3. **21 不周期重传全域大 Baseline**：原“低频 Baseline＋小范围更新”收敛为初建／恢复 Baseline 加持续小范围完整状态；静止五秒也不自动重采全域。状态不完整或失去依赖时才请求恢复。
4. **PlayerFast 目标 60 Hz、WorldDynamic 目标 30 Hz**；前者只使用实际合格的身体来源，后者来自完整普通窗口。roster 固定 20 Hz，高频 TickProgress／InputAck 服务目标约 60 Hz。详细统计口径及预算见配套合同。
5. **不把完整模型重新展开放在每帧热路径**：冷构建仍复用 18—20；持续目标按已核定布局、实例／资源代次和消费者分组预检，再交同一个 Scene 应用。需要新增 writer 时并入 R03／R04；不运行 gameplay Update 补算。
6. **10 Mbps 为 Host 三客户端总上行**，不是每端 10 Mbps。全流量含控制、状态、基线、重传与 IP／UDP 开销；保留 25% 余量。达不到目标须修复或明确未达成，不暗中减小验收负载或用重复包凑频率。

### 3.2 21／22 责任表

| 能力 | tx-04-21 必须完成 | tx-04-22 继续完成 |
| --- | --- | --- |
| 完整恢复目标 | 冷 Client 的完整 Baseline、依赖取得、真实原生提交；现存连接同房恢复 | 基线轮换、保留窗口、Delta 失效后的系统恢复策略 |
| 传输可靠性 | Baseline／关键上下文的分片 ReceiveAck、选择性重传、去重、进度超时、取消和有界队列 | 在同一传输层上扩展 Delta 生命周期和更广的损伤矩阵，不重复造第二个可靠传输层 |
| 每 Peer 状态 | 已发送／已收到／已应用分开；真实 ACK、预算、慢端独立恢复或退出 | 选择该 Peer 已确认且仍保留的 B，维护多个基线／目标的关联和回收 |
| 持续世界变化 | 对固定子范围发送完整目标，包含完整成员资格、最终值、create／remove／change 的原生应用结果 | `Delta(B,T)` 的对象／字段级完整差异和重建；数值回到 B、跨包最终删除等代数与保留机制 |

**判别方法**：消息若省略字段／成员的含义是“从某个可变旧目标 B 继承”，就是 22 的 Delta；若完整覆盖声明范围，其余值引用具名、不可变、已验证版本的 Context／Resource，属于 21 分层快照。缺依赖时不能任取本地最新值。完整状态中的生命周期不属于可丢表现事件。

23 负责真实切房回访；24—26 负责楼层／整局规则／换层；27 负责完整 HUD、独立音画与声明 Mod；28—29 负责自然生命周期和全部组合；30 负责 late join／断线重连；31 负责合法 Continue；32 负责插值、进一步性能与网络韧性。21 的初始三个 Client 在开局前连接，恢复保持原连接／参与者，不冒称中途加入或重连已完成。基本 HUD 所需最终值与当前原生显示依赖不能推迟到 27。

## 4. 数据流与线程责任

| 环节 | Owner 和约束 |
| --- | --- |
| 采集／稳定身份 | Host 主线程读取游戏／Lua，统一 Registry 映射；普通窗口一次，PlayerPost 按实际身体；同值供所有 Peer，不依赖 Recorder |
| 纯值整理／编码 | 有界不可变自有值可交后台编码／压缩；所有 native 借用在主线程窗口内结束；保持来源序号／依赖，不以编码完成时间冒充采样时间 |
| 网络发送 | 一个网络协调 owner，按每 Peer 和总预算分配；输入／控制不被大基线阻塞；原版 Online／Isaac Sync 完全隔离 |
| 网络接收 | 先查连接／代次／lane／预算，再接纳分块；完整验证、解压、模型准备仅操作自有内存 |
| 原生应用 | Client 主线程唯一 ClientScene：候选、准备、应用、提交、显示、退休；新目标不得覆盖正在执行的原生调用或借用 |
| 确认／统计 | 主线程产生不可变 CommitResult，worker 按当前 Scope 复核后发 ACK；ACK 排队失败只补发确认，不重做原生构造 |

同一房间的完整普通帧与 PlayerPost 必须标明不同采样时间线。独立 PlayerPost 不提升整房 snapshot revision、不修改整房成员全集、不推导 Entity 删除。跨 Player／Weapon／Entity／Grid 的关联变化用同一普通结构提交；60 Hz 独立路径只作用于其声明完整且安全的动态范围。
