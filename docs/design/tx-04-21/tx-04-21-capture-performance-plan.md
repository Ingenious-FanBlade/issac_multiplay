## 1. 建议采用的修复方向

将正式同步来源改为“**主线程在合法窗口读取当前动态值、核对稳定值的有效性；后台持有自有纯值，完成分层和发布构建**”。逐字段减少重复读取，取消正式热路径的 Lua JSON 往返和多轮整树复制。主线程不等待后台或任何 Peer。

保留必要状态的完整性、实际采样时刻、身份和生命周期证言；不能简单把十一域改为轮流跨帧读取，再把不同 tick 的动态值拼成一个完整世界。稳定字段只有在写入路径已经覆盖、能证明目标窗口内没有变化时才允许复用。无法证明稳定的必要字段仍须当前读取，并解决其实际成本。

50 FPS 是本次 Host 运行底线，完整运行帧预算为 **20 ms**，包括原生游戏、渲染及模组开销。已有正常 Player 60 Hz／普通动态 30 Hz 来源目标继续保留，50 FPS 底线不将这些目标自动降为 50／25 Hz。

该方案需要改采集结构，而不只是调整采集间隔。旧日志中秒级开销与毫秒级预算相差很大；目前不能承诺仅靠既有第63轮字符串／数组优化就能达标，也不能把方案中的预算写成测得结果。

## 3. 主线程与后台的边界

建议的数据流：

```text
真实 ordinary / PlayerPost 合法窗口（主线程）
  → 身份、成员、资源代次和 dirty 水位核对
  → 当前动态值 + 合格的稳定纯值块 + 来源证言
  → 封闭自有 CaptureInput，非阻塞交接
  → 单一发布构建 worker：Registry → 分层范围 → 校验／冻结 → Publication
  → 既有共享编码 worker → 各 Peer 既有发送／Applied ACK 流程
```

### 主线程保留的职责

- 所有 Lua、原生对象、getter、对象枚举及原生只读补源均留在已核定的主线程窗口。后台不得保存或调用 `lua_State*`、userdata、Player／Grid／Room／Sprite 指针。
- 在一次合法窗口复制动态终值，保留 session、epoch、run／room、capture、tick、outer、owner、mutation、loss、event watermark、plan revision 以及逐身体 use／shape／binding 见证。
- 使用受限的自有值块写入器，保存字段编号、类型、真实 Null／Empty／缺口、图节点与引用。对 Lua 必须返回的值进行有界复制；不把“Lua 已经生成完整大树”当作最终优化终点。
- 主线程交接的是已经完成且不可再修改的自有值，不是延迟读取对象的任务。批量 reader 的返回边界同样须验证身份和 mutation。
- 帧内统计所有来源工作，包括 ordinary、PlayerPost、dirty 维护、交接、分配与释放；不能只计最后一次 `Capture::Ordinary`。

### 后台承接的职责

- 单一 worker 持有用于发布构建的 Registry、范围版本、Store 和可变构建状态；主线程仅消费不可变状态摘要／Publication。不能让主线程和 worker 同时操作现有 `Capture` 内部容器。
- 生命周期、物理退休、Begin／Stop、Invalidate、Baseline 请求通过有序控制项与 generation 传递。当前 `PhysicalRetire` 的直接调用也必须迁移，不能只把 `Ordinary` 放进线程池。
- 将值分层、图闭合、身份投影、内容比较、范围校验和构建移出主线程。稳定不可变值块可共享；可变构建树使用唯一所有权移交，避免 `Own`／`Tree`／`Freeze` 对相同内容反复复制。
- 校验仍覆盖完整图、字段、身份和依赖。只有封闭构造器保证不存在可变别名的值才能走移交路径；不能仅将 `shared_ptr<T>` 转为 `shared_ptr<const T>` 就删除现有防御性复制。
- 沿用现有异步编码／压缩和共享 Blob，不再叠加一套每 Peer 重做的构建器。网络线程继续只处理有界协议工作。

## 4. 哪些值每窗读，哪些值可以复用

分组按字段语义及实际 writer 决定，不按“整个域都是低频”决定。

| 内容 | 建议策略 | 复用／失效要求 |
| --- | --- | --- |
| Entity／Grid 当前运动、生命、碰撞、机关、姿态；Room 当前运行态；Player 当前终值 | ordinary 同窗读取；已有合格 PlayerPost 继续提供逐身体快源 | 不跨 tick 拼接，不拿旧动态充当新帧；完整枚举与身体资格不省略 |
| 成员、控制组、身体关系、装备结构 | 轻量当前资格／成员核对；结构值按真实变化重建 | 创建／离表／退休、形态、装备、控制与绑定变化立即撤旧资格；沿用完整成员与身份语义 |
| Sprite／ANM 的定义、层结构、贴图和资源元数据 | 按实际资源 owner／use／代次保存不可变值块 | 审核九个既有资源观察入口的覆盖范围；构造、复制、Load／Reload、Reset、贴图替换、Swap、析构、停采后同址重用均不能漏。当前动画选择、帧、颜色和姿态仍是动态 |
| 房间配置、楼层描述、静态查询参数集合 | 已核定不变的部分复用，参数枚举不每次重建 | 同路径、同 seed、同数组长度不能证明未改变；构造修订、布局变更与还原撤销资格 |
| RoomSave 的保存向量、Moving Box／Myosotis 等携带集合 | 按 owner 和内容修订保存自有值；变化时复制相关集合；替换 JSON 判等为有类型的内容比较 | 保存、还原、回溯、交换房间、携带容器和构造变化均需覆盖。保留集合修订与 ordinal 身份，不能推断原生活对象连续性 |
| Player 全 ID 查询矩阵、效果／库存／History | 静态 ID／参数列表缓存；可变结果先按依赖拆分，再用公开批量接口或经核定的只读原生批量来源降低开销 | 不能只盯“获得／移除道具”；临时效果、充能、变身、服装、回滚等也可能改变结果。依赖闭包不完整的结果不得缓存 |
| Exploration／Run／Presentation | 稳定配置与每帧计数、HUD、地图／音画当前状态分开；变化值进入明确的动态范围 | “非原生应用域”只说明 Client 用途，不代表内容稳定。真实帧计数不能为省版本而冻结 |
| 已声明 Mod 状态 | 仅按适配器公开的来源／失效合同优化；没有可靠合同则保持当前读取 | 不检查私有闭包，不臆造第三方状态的 dirty 证言，不把 Lua table 地址当内容修订 |
| Random | 保留已有热路径 AuthorityOnly 例外；冷来源／显式录制继续遵守原合同 | 不为优化主动查询会创建或推进 RNG 的 getter |

REPENTOGON 文档已有 `MC_POST_ROOM_SAVE_STATE`、`MC_PRE_ROOM_RESTORE_STATE`、`MC_POST_BACKWARDS_ROOM_SAVE/RESTORE`、`MC_POST_GLOWING_HOURGLASS_SAVE` 和道具变更回调，可作为候选观察入口。**回调存在不等于所有 writer 都被覆盖**：需要先对照官方源码／本地文档；剩余必要路径再核对 J273 的 ABI、对象寿命和写入点。新增 Hook 只经统一清单注册并常驻，original 保持恰好一次。

RoomSave、查询矩阵和资源是首批重点，因为已有证据指向其规模与重复遍历；不承诺任意大集合都能在一个窗口内重新复制完成。

## 5. 同窗一致性、稳定值刷新与数据合同

建议在内部明确区分两种来源资格：

- `FreshRead`：该字段／块实际在当前合法窗口读取。
- `UnchangedWitness`：值在原 `acquired` 窗口读取；对应 writer 代次、owner／use 与失效水位经当前窗口核对，证明期间未变。

保留原取得时刻，并另记当前验证时刻和真实修改修订。现有 `validity.checked` 不能直接从“本窗全读相等”悄悄改成“本窗没读但认为相等”。需要同步修改来源目录、coverage／freshness 定义及消费检查；凡涉及对端可见语义，显式升级对应 schema／协商合同，不能让旧 Client 按旧含义接收。

稳定大集合可以在多个预算窗口复制自有片段，但只在覆盖全部内容且复制开始至提交的相关修改代次不变后发布该稳定块。任何修改都使受影响候选失效并重新取得，不能只保留其中已读过的槽。该机制只用于可证明稳定的内容，绝不用于跨窗收集运动或其他动态字段。

Baseline 也由一个真实 ordinary 窗口的当前动态值与该窗口全部合格的稳定块组成。准备中的稳定块可以提前积累，不能提前伪报完整 Baseline；稳定块首次建立和失效后的刷新也受主线程预算约束。缺必要块时明确等待／缺口，不把第一次加入或换房的整帧阻塞从50帧统计里隐去。

原有 Player `location.scope`、`entity_scope`、`canonical_state` 等同窗关联保持实际来源值；第一、二项修复只是改变它们所在的范围，并不授权伪造新的 scope 或关闭同窗校验。

## 6. 有界交接与失败处理

- 普通候选采用“一个正在构建＋一个最新待构建”的有界槽。只能替换未开始构建的普通候选，已提交 Publication 与 Peer 活动目标继续按现有规则持有。被合并掉的采样记为真实缺口，不计入发布率。
- 生命周期／失效控制不得随普通候选被覆盖。独立有序队列加单调失效水位；控制溢出或事件丢失立即撤资格，不能继续使用旧 Registry。worker 在构建前后及发布前核对 generation／水位，旧会话结果不得重新发布。
- PlayerPost 候选保留准确 `required_world_sequence`、Structure／Resource 版本和身体见证。不得为了新 ordinary 被合并而将快样本重新绑定到另一个 tick 的依赖；无法满足时记缺口。
- 冷 Baseline 请求独立保留，避免被不断到来的 ordinary 饿死；同一 worker 有界调度。Host 模拟不为等待 Baseline、依赖编码或 Applied ACK 而暂停。
- 不在主线程等 worker、排空队列、join 或释放大型纯值树的最后引用。用可复用槽／有界延后回收处理大对象销毁；队列满时停止接纳并报告原因，不能用无限延后队列把释放问题变成内存问题。
- 来源值、候选、共享块、worker 临时空间、已编码值与在途引用均纳入现有 Values／Wire／Workspace **512／128／128 MiB** 账本；不通过增大三池掩盖持续积压。
- 第一、二项修复使真实动态字段回到正确范围，新增来源关联也占动态字节。实施时核对既有单范围／数据报和带宽限制，必要时按协议已有范围能力分组；不静默删字段或临时提高限制。

预算是协作式的：可在 getter 或有界复制块之间停止，不能强行中断一次已进入的原生 getter。若单个必要原生调用本身超过预算，需要找到语义等价、已核定的更小读取原语／批量来源；仅添加 stopwatch 或超时判断不能保证20 ms整帧上限。若仍无法完成必要采集，明确报告50帧／同步频率未达，不能以长期不发布换得“帧率通过”。

## 7. 实施顺序与主要改动范围

以下属于同一 tx 的实施步骤；中间只做静态审阅，不逐步启动测试。

1. **补齐成本口径与字段责任。** 明确 ordinary、PlayerPost、缓存失效、原生枚举、Lua 调用、值复制和后台构建的边界；字段目录记录来源、变化依赖、失败方式、是否允许稳定复用。增加有界聚合统计，不逐字段同步写日志。
2. **先压最重的重复读取。** 优先处理 Entity 的资源／查询矩阵、RoomSave 全向量与 Room／Level 重复查询。核定 writer 后实现稳定值块和批量 reader；不存在完整依据的字段继续真实读取并列为剩余成本，不先写缓存再假设它安全。
3. **取消正式同步 JSON 往返。** reader 写入带类型的自有值，稳定块直接引用；诊断冷格式仍能从同一份已取得值产生。录制不触发第二次原生读取，也不成为同步成功的条件。
4. **迁移纯值发布构建 owner。** 接入后台 Registry／Store、版本与生命周期控制交接，减少重复树拷贝／判等／计费遍历，接回既有发送和共享编码。快源与 Baseline 一并处理，避免仅 ordinary 改异步后的竞态。
5. **完成静态闭包审阅及文档同步。** 审阅每种取消、退休、资源变化、队列满和内存失败；更新协议／来源目录、性能归约与统一 E2E 用例。用户恢复测试后才构建、部署并继续同 tx 整体验收。

| 模块 | 预计修改职责 |
| --- | --- |
| `mod/observation/.../domains/common/read.lua`、`stream.lua` 与各域 reader | 按语义采集、分离动态与稳定来源、无 JSON 的正式值输出、保留诊断输出 |
| `mod/src/game/world_sources/lua_entity.*`、`observation.cpp` 与必要只读补源 | 有类型的值交接、主线程有效性核对、writer 失效；不把原生对象交给 worker |
| `mod/src/world/common/live_consumer.*`、`world_bridge.*`、来源模型 | 有界 CaptureInput、完整窗口与控制水位、逐身体依赖、Begin／Stop 生命周期 |
| `mod/src/replica/stream_capture.*`、`stream_model.*` 及必要的新构建模块 | 单一后台 owner、不可变共享块、唯一所有权冻结、版本和内存责任 |
| `mod/src/net` 的发布接线 | 接收不可变结果，沿用现有编码／发送／ACK；不新增每 Peer 原生读取 |
| 来源目录／schema、`tools/harness/src/tx21/reduce.rs` 与现有 E2E | 新旧来源资格区分、完整帧与采集成本、真实发布率和缺口统计 |

不预先指定未知原生地址，不将官方公开回调自动当作完整失效依据；新增必要点位在实施中按当前 J273 重新核对。

## 8. 统一 E2E 中如何判断修复有效

正式性能验收需要新增运行数据，但不需要在本方案审阅前重新启动采集。沿用同一个 tx、暂停账本和统一入口，覆盖修复影响及尚未完成项；实机开始前按规范提示用户配合并确认准备状态。

同时满足以下结果才可称“必要采集下守住50帧”，单独满足任一项都不够：

1. **Host 整帧表现。** 在实际游戏窗口内记录帧间隔、逐秒帧数、p95／p99／最大值、超过20 ms的次数与持续长度。稳定游戏期间按20 ms帧预算分析，不用平均50 FPS掩盖长停顿。换房、资源刷新和首次缓存构建单列且保留在全程统计；已知原生加载／手动暂停具名标注，不能将模组新增阻塞一并排除。
2. **采集新增主线程成本。** 每运行帧累加全部采集相关窗口；稳定路径沿既有 p95 ≤2 ms、p99 ≤4 ms目标，另报 wall time、CPU time、最大值及 Lua／原生／复制／回收分项。嵌套计时不重复相加，后台成本单列。采集指标达标不自动代表整帧达标。
3. **真正的新鲜状态。** ordinary／逐身体的真实资格、采样、交接、构建、发送与 Client 应用率均可关联；继续检查30／60 Hz原合同及缺口。心跳、旧范围重发、刷新时间戳均不计新状态。
4. **完整性与缓存失效。** 同目标的必要字段完整，稳定版本不因仅 scope 改号反复重发；Player 同窗校验通过。覆盖创建／移除／形态、装备／效果／双身体、保存／恢复／回溯、资源同路径重载与交换、跨房／换层／停止恢复、队列背压与慢 Peer。漏写入后仍复用旧值视为失败。
5. **网络与内存。** 沿现有单 Peer预算／Host总预算核对动态及依赖大小、延迟、三池计费和积压；并行编码不能靠内存增长维持短时间流畅。

现有第63轮构建不包含本轮第一、二项新修复，也不包含本方案。已有 E01／E02结果保持原事实；协议或协商若受本方案影响，恢复后须覆盖对应 E01影响，不能机械复用旧结果。P4仅在用户实际授权的测试范围内安排。

## 9. 本方案仍不能替代的超时修复

此前第四项风险仍独立存在：Client 在没有结构事务但等待必要 Context／DTO 时，仍可能依据最后真实提交达到2秒恢复；同步 NativePrepare／目标构建也可能自身形成长窗。Host 改快可以降低触发机会，不能证明这些 Client 路径已经修复。

本轮不扩大 Client 超时，也不实施第四项。第三项已获本次会话实施指示；实际50帧、状态频率及不再回菜单的结论留待统一 E2E。

## 10. 2026-11-07实施结果与尚未验证的成本

以下为代码及静态源码事实，不是运行结果。本次没有构建、部署、执行校验脚本或启动游戏。

- **主线程来源。** `read.lua` 的正式 ordinary／PlayerPost 返回同窗值；C++ `CopyLuaSource`复制标量、字符串、图节点及明确空数组，拒绝借用userdata。大型查询结果与表关联数组每64项封闭为自有块，Lua只保留块handle；块仍全部在同一合法窗口取得，不跨tick拼接。正式路径不再执行Lua分层／闭图／JSON编码。Latest／Recorder显式需要时从同一来源编码诊断；诊断失败只记诊断缺口，不撤销正式值。
- **批量读取。** Player的有限ID参数集合在同一根Context内共享；`PlayerScalarQueries`仍逐项调用原公开Lua函数，保留`GetCollectibleNum`的四种bool组合、IgnoreSpoof及回调语义，减少重复Lua闭包与边界调用。RoomSave的Grid向量通过官方`Lua_GridEntitiesSaveStateVector`一次复制八个公开字段；保存集合用有类型的值比较替代JSON判等，集合修订和ordinal身份规则不变。失败标Partial，不重复调用getter试图补成Complete。
- **单一构建owner。** `stream_capture_worker.*`独占Capture／Registry／Store／版本。普通来源为一个在建、一个最新待建；独立冷槽和八个身体槽有界持有候选。256项SPSC控制环传递Begin／Stop／Invalidate／PhysicalRetire，generation与失效水位立即撤资格，构建前后和发布前复核；控制或输出预算失败后需要新的显式Begin。Baseline请求序号冻结在候选交接时，在途旧来源不能满足稍后请求。
- **精确依赖与所有权。** 身体候选冻结所需ordinary的`capture`，仅由同一构建owner将其解析为该来源的精确World／Structure／Resource版本；被合并或失效的来源记身体缺口，不能重新绑定到更新的ordinary。后台`PartitionSource`保持既有字段分层、图闭合和装备拆分；Capture局部唯一DOM可移交冻结，通用Freeze仍深复制并完整校验。
- **预算和回收。** 来源arena、块引用、批次、控制槽、Publication和输出摘要占用既有Values账本；冻结转交预付租约，不能再占另一份同内容预算。来源／范围／发布的最后引用入有界回收队列，存活及待回收owner合计最多16384；容量耗尽拒绝新来源，主线程不排空队列、join或同步析构大树。Values／Wire／Workspace仍为512／128／128 MiB，单范围、MTU、带宽和超时未提高。
- **成本口径。** stage11为后台Build；stage12为每帧主线程采集排他总和，stage13为完整Manager入口间隔，stage14—18分别为Lua／原生／复制／控制／交接。嵌套同类窗口由外层覆盖，生产只记有界聚合。归约器用stage12的wall和CPU检查2／4ms目标，并单列整帧p95／p99／最大值、逐秒帧数及超过20ms的次数和连续长度；后台变快不等于Host帧预算通过。

**未启用任何跨窗`UnchangedWitness`缓存。** 官方`LuaSprite.cpp`的Image替换直接调用`LayerState::SetSpriteSheet`，Sprite／LayerState另有shader设置／清除路径；现有九个ANM Hook不足以证明资源内容不变。公开SaveState向量也可被直接修改，保存／还原回调不覆盖全部writer。当前配置ID、资源定义、RoomSave、动态查询结果和其它必要值仍每窗读取；只在本窗完整读取后对整范围精确判等。逐成员目录新增`capture_freshness`，明确`FreshRead`、依赖、失败方式及禁止稳定复用；没有改变`validity.checked`的既有含义或对端schema，framing／stream／compact仍为2／1／2。

静态依据来自本地官方1.1.3源码：`repentogon/LuaInterfaces/Entities/LuaEntityPlayer.cpp`的GetCollectibleNum包装、`LuaEntitySaveState.h`及Grid保存向量Get绑定、`LuaSprite.cpp`的Image／shader写入；没有新增猜测RVA或原生Hook。尚存成本包括资源／Room与Level配置完整读取、Player当前查询矩阵、RoomSave集合复制，以及后台展开／分层／图校验。它们是否仍超过帧预算必须实测，不能由结构迁移推断已解决。
