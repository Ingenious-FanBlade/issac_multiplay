## 1. 术语与频率口径

- Authority tick：实际已提交的模拟步；普通与 odd 分别计数，不等于渲染帧或墙钟。
- 采样 Hz：获得新合格来源的次数；重复编码／重发同一来源不增加计数。
- 发布 Hz：不同状态序号进入调度的次数。发送 Hz、完整接收 Hz、原生提交 Hz 另外统计。
- UDP 包率：合包、分片及重传后的数据报数，不与上述 Hz 互换。
- 一条完整范围状态可以引用具名且有效的不可变上下文版本；不能从未声明的“当前最新对象”继承遗漏字段。
- 普通完整目标和 PlayerPost 子范围有不同采样序列。独立身体数据不冒充同 tick 的整房世界；绘制版本向量必须可解释。

| 类别 | 默认调度／发布目标 | 来源与触发 | 合并／补发／停止规则 |
| --- | --- | --- | --- |
| PlayerFast | **60 Hz 调度上限，间隔约 16.67 ms** | 普通或 odd 正常完成后的合格身体；逐身体记录实际最后更新 tick、capture kind、关系版本与字段读取依据 | 只合并尚未执行的完整候选；不把未更新／失效身体填成新样本。某身体原生只在普通步更新时如实约 30 Hz，单列资格覆盖；不新增模拟 |
| WorldDynamic | **30 Hz，间隔约 33.33 ms** | 已完成普通窗口的 Room／Grid／Entity 动态范围与完整成员资格 | 只发新普通来源，odd gap 不算完整样本；过期目标可被较新完整范围替代，最终后态须被确认 |
| Context／Structure／Resource | **变化时立即排入可靠发送，无固定周期** | 首次需要、完整成员／shape／装备／资源／关系／必要上下文变化；所有动态消费者依赖明确版本 | 不等下一次低频全域导出；新依赖未就绪不能用旧定义写对象；大范围按预算分块 |
| Baseline | **首次准备／同连接恢复时发送，不周期全域刷新** | 完整合格目标及所有必需依赖 | 一个活动传输和一个最新待选目标；不能每来一帧就取消活动 Baseline；成功应用后追到最新合格动态状态 |
| roster | **20 Hz，50 ms 周期** | 名单／会话状态；资格、generation、停止或暂停变化立即通知 | 立即项优先；周期项可合并成最新完整名单，独立于可靠有序控制序号，不能占住永久缺口 |
| TickProgress | **每次有效 Authority 提交，正常约 60 Hz** | 实际 tick、kind、服务器采样／发送时刻、回显、输入资格／generation | 无新模拟时不伪造新 tick；250 ms 心跳只表连接存活。用于独立驱动输入时序 |
| InputAck | **每个新处理进度，服务机会约 60 Hz** | 真实 accepted／processed 进度 | 与 TickProgress 同包；零进度不伪造 ACK；相同进度允许重传但不计新处理 |
| Client 输入上行 | **新有效服务器步下至多一个新 canonical 命令，正常目标约 60 Hz** | 实际物理采样、服务器进度估计、现有 lead=2、age=0 和启动例外 | 每控制组一个流；原历史冗余有界、边沿去重；暂停／失焦／换代中性，未发送边沿不提前消费 |
| ReceiveAck | **最多 20 Hz 常规反馈** | 新收到的分片位图／范围 | 最后一片、已明确缺片或完成重传可立即反馈；同 transfer 的反馈合并，不能让 ACK 本身变巨型消息 |
| Applied ACK | **最多 20 Hz 聚合动态确认** | 主线程真实已提交范围和版本 | Baseline／结构提交、失败和停止立即报告；累计确认覆盖真实完成，不提升未提交范围 |
| 连接心跳 | **250 ms** | 无其他有效通信时 | 不推进输入时钟／世界序号；活动连接超时沿 3000 ms 初始设置，传输进度超时另算 |

低频名单不能再决定 Client 的 `last_tick` 更新机会。I18 必须先实现 TickProgress 并接入 `InputTiming`；本地单调时钟只估计预计抵达时刻，不创建模拟 tick，不使用两台机器的绝对时钟差。正常缺输入仍中性，不能用保持旧 held 掩盖降频问题。

本地 Wiki 的 `Game:GetFrameCount()` 描述每秒 30 帧，不能据此推定所有玩家消费者都 60 Hz。PlayerFast 资格由 R02 和真实见证决定。没有 PlayerPost 实现时，不得宣布 60 Hz Player 已完成。

## 2. 状态范围及完整性

### 2.1 范围划分

| 范围 | 完整内容与版本责任 | 变化与依赖 |
| --- | --- | --- |
| BaselineManifest | 世界 Scope、schema／能力、采样来源、必需范围清单及精确版本、完整成员／资源需求、事件抑制水位和声明应用域 | 冷 Client 能下载全部依赖，不依赖旧事件或同 seed 本地局；未捕获仍为缺失，不补默认值 |
| Context | 整局／楼层／房间身份、布局／静态几何、必要规则结果、离房／探索等保留上下文；按实际消费者分范围 | 有效期与失效来源逐字段登记。HUD 变化不能使整个 room_save／level descriptors 重发；27 的完整表现仍单独负责 |
| Structure | 当前范围的完整成员集合，稳定 Key／use／shape、类别、身体组／roster／备份、完整装备／关系及构造必需值 | 普通窗口统一版本；create／remove／Morph／换装／引用环属于状态事务；未观察不等于删除 |
| Resource | 具名版本的 ANM／图像／shader／层配置、costume／Weapon 结构定义和消费者映射 | 借用按真实实例代次；不做通用子树去重，也不凭相同路径认为同一原生资源。版本用显式序号，不使用哈希 |
| WorldDynamic | 当前房间非 Player Entity、Grid、Room 的完整动态字段与完整成员资格，含位置／速度／颜色／姿态／生命／可见状态／当前门及机关状态等实际消费者需求 | 每条消息完整覆盖自己声明的范围；多分片齐全后才生效。Player 的公共本体动态字段有唯一所有者，不能两路互相覆盖 |
| PlayerFast | 某个身体固定 schema 的全部快速动态量：公共空间、当前方向／动作、精确 ANM／身体／头／服装／Weapon 展示所需当前量及 R03 确认的其他值 | 不得只发坐标漏掉持续变化的姿态／充能／闪烁。字段若与非 Player 引用必须原子关联，则归普通联合帧，不强行搬到 odd 子范围 |

I01 必须对 18—20 全部被消费成员逐项归属，表中举例不是字段白名单。只有已解释为不变的配置可复用；“值比较麻烦”不是低频理由。当前必需字段缺来源就明确失败并补齐，不删 adapter 或给不支持字段填零。

### 2.2 版本与安装合同

1. Context／Structure／Resource 每次发布都是声明范围的完整替换；范围名、版本、完整性、依赖、采样事实随消息发送。不能采用稀疏“新增对象列表”却隐含继承未知旧集合。
2. WorldDynamic 携带普通 `world_seq/tick/outer`、精确依赖版本、完整成员／shape。PlayerFast 携带 `body_key/body_seq/capture_tick/last_native_update_tick/kind/structure_revision/required_world_seq`。字段名是待实现设计，不表示现有 wire 已支持。
3. 来源时刻不同的上下文可以以有效版本被引用，但必须证明该值在目标普通窗口仍有效；dirty 事件丢失、owner 变化、读取失败或可变字段无完整失效覆盖时，撤资格并重读。不能把几次全量扫描拼成一个虚构同窗 Baseline。
4. 未知依赖有界等待；上下文准备先于依赖它的动态安装。收到较新的 PlayerPost 不能回退其关联世界依赖；普通帧晚到也不能覆盖已经生效的较新同字段身体值。结构换代时旧身体子帧全部失效。
5. Client 保存一个逻辑已提交视图及各范围版本向量，承载于唯一原生世界。跨对象关系／创建／删除／换形在普通事务提交；独立快速身体范围只更新已证明可分离的字段，不形成第二个模拟器。
6. 确认分开：ReceiveAck 确认分片；ContextReady 确认纯值／资源依赖；Applied ACK 确认真实原生范围。Baseline ACK 只有所有必需范围及当前声明域完成才成立。纯值保留域另列，不假装已执行其玩法。
7. 快速流只允许合并未执行的完整目标。原生写入开始后不得更换剩余字段；完整步骤完成再推进，或按实际前缀退休。结构变化可暂时停该范围展示，但不能让频繁更新反复取消，永远到不了提交。
8. 最后静止值／最终删除不能依赖“下一次一定有变化”。发送端保留最后未确认完整范围，静止后每 100 ms 补发，最长 2 s 未收敛请求该 Peer 完整恢复；持续活动由更新完整范围涵盖旧最终变化。重传不计新 Hz。

四端共享的编码内容使用共同 `world_scope=(session,run,floor,dimension,room,scene)`，每 Peer 的 connection／route 保存在 v2 消息封套和发送游标中。旧 v1 把 connection 嵌入完整模型；I03／I04 必须明确升级后的模型适配和校验，不给三端发送同一个错误 connection，也不为改这一字段复制三个巨大 DOM。接收端以当前封套与共同 world_scope 形成完整验证视图，公共 Key 仍不依赖连接序号。

Baseline 的历史表现抑制水位只在该目标真实提交后安装。21 不实现 27 的通用音画事件系统；既有 17—20 已采用的独立表现 handler 仍保留自己的依赖／完成语义。没有实际消费的事件不能用“最大已见 event_id”推进完成水位，状态 Applied ACK 与事件完成范围分开；所有持久结果仍须能由 Baseline 和完整状态恢复。

这不是 Delta(B,T)：接收端不需要某个动态旧 B 的字段来恢复当前完整范围。22 在此基础上增加基于每 Peer 已确认 B 的对象／字段差异、保留与重建；21 的范围拆分、可靠性、ACK 和最终值收敛必须先可用。

## 3. wire、分块和可靠控制

### 3.1 版本化与路由

计划升级真实游戏链的 **ICSR wire v2／ICRF framing v2**，增加 `stream_schema=1` 等具名能力；现有 model／projection v2 不是传输版本，不混同。旧 ICSN Rust 输入工具不因本次工作改协议；旧真实游戏 Client 不具备新能力时明确拒绝。修改严格顶层 schema 时同步两端，不追加字段后让旧 decoder 猜。

握手仍用小预算、nonce 和实际 Peer endpoint 绑定；成功协商后才允许世界 lane 分配。route 表保存完整 Scope，数据包用 connection＋route epoch 定位。初始 `scene_prepare` 经等待路由可靠送达，双方接纳正式 Scope 后再送世界数据；route 控制在依赖未知时仍可处理，不产生等待自身 ACK 的死锁。重组与输入队列同时按路由换代撤销。

新分片头拟固定 **64 字节**：magic 4、version 2、header length 2、connection 8、route epoch 8、transfer 8、wire length 4、decoded length 4、part index 4、part count 4、kind 2、lane 1、codec 1、payload length 2、flags 2、reserved 8。整数小端、保留位为零，字段宽度与限制必须一致。单 UDP payload 上限仍 **1200 字节**，分片净荷最多 **1136 字节**；不能继续用旧 1168 字节预算计算新协议。

同一连接／route 的多个小消息可合包，逐条有长度、kind／lane 和序号；不得跨 Peer 合包，完整数据报仍不超过 1200。合包最多等 **2 ms**，立即资格／停止消息不为凑包延后。可靠控制序列与可合并的 roster／TickProgress 分开，不能把中间丢弃的 roster 留作 ControlWindow 永久缺口。网络等待使用最近到期调度，不把现有 10 ms 轮询常量当 2 ms 合包或 60 Hz 的实现证明。

### 3.2 Baseline 与上下文传输

- 先对有界完整逻辑消息编码，再以 **zstd level 3** 作为默认整消息压缩配置，随后分片；不逐片独立压缩。快速小消息默认不压缩，实测有收益才在既定协商内启用，保留精度。
- 建立 transfer 描述：connection／route、kind、源序号、压缩／解压长度、分片数量、依赖和预计预算；新片必须匹配描述。解压器最大窗口初始 **8 MiB**，压缩器采用匹配窗口；总输出独立受 32 MiB 限制。
- ReceiveAck 用至多 256 片的窗口位图或等价有界范围，分窗口反馈；缺片选择性重发，已收副本冲突明确拒绝。不能每 50 ms 重发几万项完整 JSON 序号数组。
- RTO 初始 **200 ms**，按同机计时的 RTT 估计调整到 **100—1000 ms**；首次补片不等待所有后续分片。完成 ACK 丢失时重发完成记录，不能重复应用。
- **2 s 无新有效分片／确认进度**触发传输重试或换新 Baseline；重复包和重复 ACK 不刷新进度。连接心跳活着不代表 Baseline 有进展。
- 绝对传输截止按 `10 s + 2 × 预计剩余线上字节 / 实际授予字节率` 设置／更新，最多 **120 s**。预算暂停可更新预计时间，但不能突破总上限；超过预算可服务的目标明确报错或恢复，不能用 1 s 固定超时误杀正在有效传输的大消息。
- 每 Peer 一个活动 Baseline＋一个最新待选目标。活动传输正常推进时不被新每帧快照反复取消；仅失效、超时或明确更新策略取消。取消可靠通知，旧 transfer 的迟到片不复活候选。
- 同连接最多一次原生失败后的自动完整重建；失败 owner 未能安全退休时停该 Peer。纯传输恢复可按进度继续，持续无法收敛至绝对期限则退出该 Peer，不永久循环。

## 4. 10 Mbps 计费与分配

### 4.1 总预算

**10 Mbps = 10,000,000 bit/s = 1,250,000 byte/s**，按 Host 对三个远端的总上行计算。25% 留给链路／其他进程／突发余量，本模组持续发送预算 **937,500 byte/s = 7.5 Mbps**。此预算内已经包含模组自己的重传；不能再用 25% 余量当不计费的补片通道。

计费采用每实际发送数据报 `UDP payload 字节数 + 28` 的 IPv4／UDP 口径；如使用 IPv6 则加 48，隧道额外头须在场景中说明并相应收紧。当前真实链使用 IPv4。这里不声称计入以太网物理层；E2E 限速必须使用相同计费口径。

三 Peer 公平基准各 **312,500 byte/s**，分配如下；都是包含数据报、分片头及 IP／UDP 的线上字节，不是未压缩字段体积。

| 每 Peer 类别 | byte/s | 三 Peer 合计 | 频率下的平均线上预算 |
| --- | ---: | ---: | --- |
| 控制／TickProgress／InputAck／可靠控制 | 25,000 | 75,000 | 60 Hz 服务约 416.7 字节／次；包含低频名单及其他控制摊销 |
| PlayerFast | 120,000 | 360,000 | 60 Hz 合计 **2000 字节／次**，是该 Peer 接收全部相关身体的总额 |
| WorldDynamic | 120,000 | 360,000 | 30 Hz **4000 字节／次** |
| Baseline／上下文／补片保留 | 47,500 | 142,500 | 按需限速，不能抢走其他 Peer 已保留的高频服务 |
| **合计** | **312,500** | **937,500** | **7.5 Mbps** |

两个高频预算同时相加，不能各自重复使用全部 312.5 KB/s。四组八身体使用同一 120 KB/s Player 总额；预算不是每个身体 2 KB／帧。初期未开始展示的 Peer 可借用自己空闲的动态份额，Baseline 理论可得约 **287,500 byte/s**；仍在展示的其他 Peer 保留自己的份额。低频无任务时可借给当前动态，重传出现时归还。所有借用受 Host 总令牌约束。

按用户要求先进行的两人 E2E，只有一个远端 Peer，但**测试配置仍将该 Peer 限为上述 312,500 byte/s 基准及同样的 lane 分配**；Host 总上行限速仍为 10 Mbps。这样先验证相同单 Peer 工作档，不能把空闲三端预算全部借给一个 Client 后外推四人可用。此为验收配置，产品其他人数的空闲份额借用可显式设置，不能影响四人基准。两人通过后，四人再实际验证三份预算同时竞争和全局公平。

调度使用总桶＋每 Peer 桶，总桶 burst 初始 **24 KiB**、每 Peer **8 KiB**；任意窗口满足 `字节 ≤ 速率 × 时间 + burst`。采用有界轮转，控制／停止先行，其次必要结构／当前玩家／其他玩家／世界动态，且给上下文和补片保底。不能为了优先级无声删掉同一完整范围里的成员；超量时合并整个未执行目标或进入明确降级／恢复。

### 4.2 可解释的 Baseline 时长

按 64 字节分片头与 IPv4／UDP 28 字节计，满片效率为 `1136 / 1228`，尚未包含其他逻辑消息头；实际时长必须用真实发送字节归约。

| 示例压缩后消息 | 估算线上字节 | 287.5 KB/s 初建约需 | 47.5 KB/s 恢复保留约需 |
| --- | ---: | ---: | ---: |
| 90 KiB | 约 100 KB | 0.35 s | 2.1 s |
| 1 MiB | 约 1.13 MB | 3.95 s | 23.9 s |

这些是预算算式，不是对 20 当前 17.4 MB 投影的压缩实测。21 必须测当前四人／八身体负载的真实编码／压缩体积、采集／解码 CPU 和资源准备时间；不能把上表网络时间称为“连接到画面就绪”的总时间。单房间基准负载以压缩 Baseline **不大于 1 MiB、初次准备到画面就绪不大于 10 s**为验收目标。体积包含冷 Client 从零取得全部必需 Context／Structure／Resource 消息的压缩后总和，不仅是 manifest，也不假设已有网络缓存；游戏安装自带且版本匹配的资源文件不通过网络重发。超过时如实判未达，不把 32 MiB 保护上限当性能承诺。

## 5. 有界缓存与计算预算

2026-11-07用户决定：完成重复预留／寿命修复后，将值、Wire、工作区三池分别从256/64/64 MiB翻倍为512/128/128 MiB。以下为当前额度；单条消息、节点、MTU、发送率及超时不随之扩大，旧失败事实按当时额度保留。

| 范围 | 当前保护上限／策略 |
| --- | --- |
| 未协商握手 | 仍至多 64 KiB、4096 节点、2 候选；端点／nonce／速率受控，不能预分配世界规模 |
| 已授权可靠世界消息 | 压缩与逻辑编码分别最多 32 MiB，最多 32768 分片；沿用 64M 节点／深度限制作为上限，不按报文扩大；解压窗口另限 8 MiB |
| 快速完整范围 | 单逻辑消息最多 64 KiB、32K 节点；常态预算远小于保护上限。超限不拆成失去完整性的小半目标 |
| Host 纯值／已应用／候选 | 实时复制自有展开值总池 512 MiB；共享不可变源，按 Peer 仅持有版本／发送游标，不深拷贝三份 |
| Host 编码／分片／重传 | 全部 Peer 共用 128 MiB 上限，活动共享 blob 和真正的每 Peer 副本分别计费；队列满先撤过期未发候选 |
| Codec 工作区 | Host 合计 128 MiB；与前两池合计复制侧自有内存不超过 768 MiB；不含游戏原生资源，需单独统计 |
| Client 全链 | 对应 512 MiB 展开值＋128 MiB 压缩／分片＋128 MiB 工作区，总计 768 MiB；A、正在应用 T、依赖、缓存必须共同计费，不能每项各领 512 MiB |
| 候选／主线程 | 每 Peer 至多 1 个正在准备／应用目标和 1 个最新动态候选；可靠依赖最多 2 个活动 transfer；控制／输入各保留原有有界容量，终态用不可丢粘性状态 |
| 重复版本记录 | 每范围有界记录近期 128 次接纳／提交及其必要原值；不计算摘要；相同序号不同 payload 明确冲突，较老目标拒绝，不永久保留整包历史 |

这些是复制自有内存上限，不代表 32 位游戏进程一定有足够地址空间。分配失败必须停止该目标并安全收口；全进程 private／working set、原生资源和复制池分别观测。最新 20 的约 2 GB 进程峰值使减少重复 DOM 成为实际要求，不能把扩大上限当优化。

稳定热路径的初始 CPU 目标：Host 新增采集／发布主线程窗口 p95 ≤ **2 ms**、p99 ≤ **4 ms**；Client 动态预检／安装窗口 p95 ≤ **2 ms**、p99 ≤ **4 ms**。绘制、压缩、完整 Baseline 和结构变更另计；结构路径不得以统计排除为由任意阻塞输入／窗口。持续大于目标必须定位、优化或报告未达，不能以 32 后续性能任务覆盖当前实时缺口。

## 6. Scope、输入与停止

连接身份固定，世界路由单独换代；准备前撤旧输入资格与待发边沿，worker 清旧 Intent／历史，主线程接受真实新 roster／TickProgress 和 binding generation 后才恢复。旧包不重新贴新 route；旧 InputAck／AppliedAck 不推进新代次。

暂停、Host 控制台／ImGui／菜单、Client 失焦／本地 UI 屏蔽按既有规则中性，状态可维持最后真实已提交值。恢复不补发被屏蔽边沿。Host 的普通／odd 实际消费者缺席要单列，不能将“收到输入”当“每身体均消费”。

Client 超过 **500 ms** 没有可应用的新动态范围时显示陈旧／暂停状态，超过 **2 s** 请求完整恢复；明确原生暂停不误报丢网，但仍不生成新模拟样本。结构替换从已完整收到、声明不同结构／资源版本的精确World目标开始准备；实际新增依赖接纳、原生退休／构建步骤才推进该事务，仍受 **2 s无进度／120 s绝对期限**，不以轮询或普通新值续期，陈旧提示仍按最后真实提交计算。每Peer保留一个活动目标到真实Applied ACK，最新候选独立合并；不等待Authority或其他Peer。缺必要结构、写后失败、Scope 冲突立即撤销受影响展示资格。停止和退出不等待无法满足的世界依赖；原生资源／Lua／图形借用退尽之前不能交还 Off。Hook 常驻，不恢复字节、不重新注入。

## 7. 必须暴露的观测量

按 Peer 和 lane 分开：实际 payload／线上字节、包数、合包条数、分片／补片／重复、压缩前后长度、首次准备／收齐／解码／原生提交时刻、不同源序号的 capture／publish／receive／apply 次数、各身体 actual-update／可读／缺席次数、输入 sequence／target／accepted／processed／原生消费、route／generation、当前依赖／完整范围／真实 ACK、队列高水位、各内存池和 CPU 阶段。

总量和逐 lane 包数的归属要避免合包重复计费：记录一次物理数据报总额，按消息实际编码字节和头摊销归属各 lane，归约总和应相等。对不同设备的时刻只用回显区间和明确误差估计延迟；E2E 以同一 Authority tick／目标版本对齐状态，不能直接相减各端 GetTickCount。

生产默认只有有界聚合状态，不开启逐 tick／query 全量日志或录制。E2E 显式启用诊断，至少安排关闭录制和细日志的连续窗口证明正式链独立工作；正常材料用后清理。
